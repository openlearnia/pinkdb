# Releasing pinkdb

The release train is tag-driven. A `v<version>` tag builds the CLI and server
matrix, smoke-tests every artifact, publishes one GitHub release with a
`SHA256SUMS` manifest, and (on the same tag) builds and publishes the extension
catalog for every supported platform. The same shell code runs locally, so a
release can be rehearsed without GitHub.

Nothing here is a substitute for reading the workflow: `.github/workflows/release.yml`
is thin orchestration over `scripts/release/*`, and
`.github/workflows/publish-extensions.yml` fans the extension matrix in to one
catalog writer.

## Tag procedure

1. Bump the version in **all three** manifests to the same value:
   `crates/pinkdb/Cargo.toml`, `crates/pinkdb-cli/Cargo.toml`,
   `crates/pinkdb-server/Cargo.toml`. The prepare job refuses a tag that does
   not match any of them.
2. Land the bump on `main` and wait for CI.
3. Push an annotated tag: `git tag -a v0.2.0 -m "pinkdb 0.2.0" && git push origin v0.2.0`.
4. Watch the **Release** workflow. Its `prepare` job resolves the version and
   matrix; the `build` jobs package and smoke each artifact; the single
   `publish` job validates the fan-in and creates the GitHub release.
5. Watch **Publish extensions**. Its build matrix runs in parallel; one
   `publish` job then writes the catalog, verifies the Ed25519 signature and
   artifacts, and deploys the Worker once.

A manual `workflow_dispatch` of **Release** with a `version` input is the
recovery path when a tag run failed before publishing. It does not let a
different version through: the input is checked against Cargo.toml exactly like
a tag. **Publish extensions** keeps its own manual dispatch inputs
(`name`, `version`, `platform`) for a single extension or a platform backfill.

## CLI and server matrix

CLI assets:

| variant | cargo features | what it adds |
| --- | --- | --- |
| `default` | default (`json`, `datetime`, `math`) | REPL, CSV, `.pink` + WAL, built-in functions |
| `lean` | `--no-default-features` | no linked json/datetime/math extensions |
| `pinklake` | `pinklake` | `.lake` over `.pink` data files |
| `pinklake-s3` | `pinklake,s3` | pinklake + `s3://` storage |
| `vortexlake` | `vortexlake` | `.lake` over Vortex data files |
| `vortexlake-s3` | `vortexlake,s3` | Vortex lake + `s3://` storage |

Server assets:

| variant | cargo features |
| --- | --- |
| `default` | default (blocking transport) |
| `async-server` | `async-server` (tokio transport) |
| `tls` | `tls` (rustls; sync transport only) |

Platforms and runners:

| os-arch | runner | note |
| --- | --- | --- |
| `linux-x86_64` | `ubuntu-latest` | native |
| `linux-aarch64` | `ubuntu-24.04-arm` | native arm runner |
| `darwin-aarch64` | `macos-latest` | native arm64 |
| `darwin-x86_64` | `macos-latest` + `rustup target add x86_64-apple-darwin` | cross-build; smoke under Rosetta |

`scripts/release/matrix.py --kind all` is the single definition of these 36
rows (24 CLI + 12 server). The prepare job also uses it to compute the expected
asset count; the publish job refuses to publish if any job's artifact is
missing.

If `ubuntu-24.04-arm` is unavailable to the organization, the fallback is a
self-hosted arm64 runner, or a cross-build with a documented `qemu`/linker
setup — do not silently drop `linux-aarch64` from the matrix. If the
`macos-latest` arm runner cannot install/run Rosetta, the fallback for
`darwin-x86_64` is an Intel `macos-13` runner (or a self-hosted Intel Mac); the
workflow fails closed rather than publishing an unexecuted cross artifact.

### Asset names and contents

```
pinkdb-<version>-<os>-<arch>-<variant>.tar.gz
pinkdb-server-<version>-<os>-<arch>-<variant>.tar.gz
<asset>.sha256
SHA256SUMS
```

- `os` is `linux` or `darwin`.
- `arch` is `x86_64` or `aarch64` (`install.sh` normalizes `arm64` to
  `aarch64`).
- `variant` is the slug in the tables above (`pinklake-s3`, not `pinklake,s3`).
- Each tarball has one top-level directory named after the asset, containing
  the `pinkdb` or `pinkdb-server` binary, `README.md`, and any `LICENSE*` file
  present at the repository root.
- `SHA256SUMS` has one standard `hash  filename` line per tarball, sorted by
  filename. Per-asset `.sha256` sidecars are generated by `package.sh`; the
  publish job regenerates the combined manifest and cross-checks every sidecar.

## Smoke gates

`scripts/release/smoke.sh` runs before an artifact is packaged, so a build job
cannot upload anything that has not executed:

- CLI, every variant: `--version` and `SELECT 42`.
- CLI `default`: `json_valid('{}')`, `exp(1)`, and `strftime` on a TIMESTAMP.
- CLI `lean`: `SELECT 42` succeeds and `json_valid`/`exp` are refused (the
  default-feature functions are genuinely absent).
- CLI lake variants: `.help` advertises `.lake save`; `pinklake` reports the
  pinklake data format, `vortexlake` does not; `*-s3` variants advertise
  `s3://` URLs. No network is touched.
- Server: start with `--host 127.0.0.1 --port 0`, wait for the documented
  `listening on HOST:PORT` line, connect with `python3` over TCP, then stop.
- Server `async-server`: starts with `--transport async`, and refuses
  `--transport async` + TLS flags with the "does not support TLS" error (the
  H-2 no-silent-plaintext rule).
- Server `tls`: starts with a throwaway self-signed certificate and refuses
  `--transport async` (this build has no async feature).
- Server `default`: refuses `--transport async`.

A cross-built `darwin-x86_64` binary is run through `arch -x86_64`; if Rosetta
is missing the smoke fails rather than being skipped.

## Immutable publishing policy

Releases and catalog coordinates are immutable:

- The publish job runs `gh release view "$TAG"` first and **fails** if a
  release for that tag exists. It never edits, deletes, or re-uploads an asset.
  Retrying a failed release means bumping the version, not reusing the tag.
- The release is created as a **draft**, every asset and `SHA256SUMS` is
  uploaded, and only then is the draft flipped public. A failed upload leaves
  the draft hidden; it still exists, so the next attempt must use a new
  version.
- Extension coordinates (`name` + `version` + `platform`) are skipped if the
  live index already has them, and `ext-repo/publish.py` independently refuses
  them. To change an extension's bytes, bump its version. The per-platform
  matrix means a tag can add `linux-x64`/`linux-arm64`/`darwin-x64` entries for
  a version whose `darwin-arm64` entry was published earlier; it never
  overwrites the earlier entry.

## Secret scoping

- Build jobs (release and extensions) have `permissions: contents: read` and no
  secrets at all.
- Only the release `publish` job has `contents: write`, via the automatic
  `GITHUB_TOKEN`/`secrets.GITHUB_TOKEN`. It has no Cloudflare or signing
  secrets.
- In the extension workflow, `CF_API_TOKEN`/`CLOUDFLARE_API_TOKEN` and
  `CF_ACCOUNT_ID`/`CLOUDFLARE_ACCOUNT_ID` are passed only to the publish and
  Worker-deploy steps; `PINKDB_EXT_SIGNING_KEY` is passed **only** to the
  publish step. The filter, verification, and deploy steps never see it.
  Publishing without the key is refused.
- There is no `pull_request` trigger on either publishing workflow, so a fork
  cannot cause a write.

## Local rehearsal

Build, smoke, and package one variant for the host (or a target triple):

```sh
scripts/release/package.sh --kind cli --variant default
scripts/release/package.sh --kind cli --variant lean
scripts/release/package.sh --kind server --variant default
scripts/release/package.sh --kind cli --variant pinklake --target aarch64-apple-darwin
```

The output goes to `dist/`; the script prints the asset name, path, SHA-256,
and byte size. Use `--skip-smoke` only for packaging experiments.

Run the installer harness (fake release tree; no GitHub access):

```sh
tests/install/run.sh
```

Fast release-tooling tests (no cargo build):

```sh
tests/release/test_package.sh
```

Validate the workflows locally:

```sh
actionlint .github/workflows/release.yml .github/workflows/publish-extensions.yml
python3 -m py_compile scripts/release/matrix.py scripts/release/extensions.py
bash -n scripts/release/*.sh tests/install/run.sh tests/release/test_package.sh
sh -n install.sh
```

## Extension publishing (same tag)

A `v<version>` push to the extension workflow builds the catalog matrix:
`linux-x64`, `linux-arm64`, `darwin-arm64`, and `darwin-x64` (cross-built on
the arm runner). Each build job:

1. runs `make -C ext-sdk/c all`, `make -C ext-sdk/go all`,
   `make -C ext-sdk/rust all`, and every `extensions/*/Makefile`;
2. checks every library's architecture with `file` (this is what makes the
   cross-built `darwin-x64` entries trustworthy);
3. runs the C, Go, and Rust SDK smoke scripts on native platforms;
4. stages catalog candidates and writes a manifest with
   `scripts/release/extensions.py discover`.

The catalog candidates are unchanged from the previous single-job workflow:

- the C/C++ SDK examples: `math_ext`, `string_ext`, `cpp_ext`;
- `extensions/string` (`libstring_ext`), the only `extensions/*` directory with
  a Makefile and a built library.

**Known gap:** the Cargo-built core extensions (`json`, `math`, `datetime`,
`arrow`, `parquet`) are linked into the CLI and have no catalog Makefile /
discovery path; they are not published as loadable artifacts today. The Go and
Rust SDK examples are built and smoked but are not catalog entries (the Rust
example's `librust_string_ext` is a different artifact from the C
`string_ext`). Adding those to the catalog requires a naming and ABI decision
first, so this wave documents the gap instead of publishing ambiguous names.
`windows-x64` is representable in catalog format v1 but no Windows build exists,
so the workflow refuses it by name.

One `publish` job downloads every staged directory, verifies each manifest's
SHA-256, skips coordinates already in the live catalog, runs
`ext-repo/publish.sh` for the rest (which signs the exact `index.json` bytes
with Ed25519), runs `ext-repo/verify.sh` against the local mirror and the live
catalog, and deploys the Worker exactly once. Concurrent catalog writes cannot
happen by design: the concurrency group is global and `cancel-in-progress` is
false.

## Windows

Windows is **not supported** in this release:

- the workspace has no Windows CI or linker setup and the server's TLS/network
  paths have not been exercised there;
- therefore there is no `windows-*` release asset, no `install.ps1`, and
  `install.sh` refuses MSYS/MinGW/Cygwin with a clear message.

Do not add a Windows asset or installer until a Windows build and smoke job
exists. The extension catalog's `windows-x64` tag is reserved but unused.

## Verifying a download

```sh
sh install.sh --version 0.1.0 --variant default --dry-run   # plan only
sh install.sh --version 0.1.0 --variant default             # verify + install
```

`install.sh` fetches `SHA256SUMS` from the release, requires an entry for the
exact asset, downloads to a temporary file, verifies SHA-256 (fail closed),
rejects unsafe archive paths, extracts to a temporary directory, and installs
atomically to `${PREFIX:-$HOME/.local}/bin/pinkdb`. It never uses `sudo` and
never pipes a download into a shell. `--force` replaces an existing binary;
without it an existing install is refused.

Manual verification:

```sh
curl -fsSLO https://github.com/openlearnia/pinkdb/releases/download/v0.1.0/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

Extension catalogs are signed with Ed25519 (`index.json.sig`) and verified by
the CLI before any artifact request; that mechanism was already implemented in
`ext-repo/publish.py` and `ext-repo/verify.sh` and is used unchanged. Release
binaries are authenticated by the checksum manifest only — there is no binary
signing beyond SHA-256 in this wave.

## Resetting a failed publish

There is no overwrite path. If a release or catalog publish failed midway:

- GitHub release: bump the version and tag again. Delete the hidden draft
  manually only if you are certain it contains no public assets, then reuse the
  version if policy allows; the workflow itself will always refuse an existing
  release.
- Extensions: the publish job's per-coordinate skip makes a re-run after a
  transient failure safe for coordinates that succeeded. A coordinate that was
  uploaded but not verified may need a version bump because its bytes are now
  immutable.
