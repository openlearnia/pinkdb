# PinkDB — Bug & Gap Review

**Scope:** all six crates (`pinkdb`, `pinkdb-cli`, `pinkdb-server`, `pinkdb-ffi`,
`pinkdb-ext-loader`, `pink-lake`), the bindings, the extension SDK/repo and the CLI.
**Method:** six parallel read-only code reviews (engine, SQL front-end, persist/WAL/crypto,
lake core, lake crypto/S3/CLI, server/FFI/CLI), then hand-verification of every P1 finding
against the source. Findings I read myself are marked **[verified]**; the rest are
high-confidence reads from the sub-reviews.
**Repo state:** note that the git snapshot at session start showed an unresolved merge
conflict in `crates/pink-lake/src/lib.rs`; that is **resolved** in the current tree
(`git ls-files -u` is empty, no conflict markers anywhere) — not a finding.

> This is a **findings report only** (documented bugs/gaps + severity), per the chosen scope.
> No remediation steps are included.

## Severity summary

| Band | Count | Themes |
|---|---|---|
| P1 — high (crash, data loss, at-rest leak, wrong results, remote DoS) | 10 | join panic, window pushdown, WAL truncation, non-atomic `save`, lake commit on legacy head, delete-file overflow, plaintext decrypt temp file, server OOM, RANGE-frame wrong results, ALTER depth guard |
| P2 — medium (correctness edges, availability, security hygiene, doc drift) | ~25 | interval hashing, spurious conflicts, S3 retry/degrade, FFI unwind, binding coverage, CLI quote/output handling |
| P3 — low | ~6 | cosmetic messages, spec-divergence, doc comments |

The engine documents exact behavior very aggressively (README + module docs), so most items
below are cases where **the code disagrees with a documented guarantee** — the sharpest kind
of bug report for this repo.

## 1. Core execution engine (`crates/pinkdb/src`)

### P1 — Filter is pushed **below a Window**, changing window results **[verified]**
`crates/pinkdb/src/optimizer.rs:898`
`push_one_level`'s `Window` arm pushes any conjunct whose columns are all `< input_cols`
under the window. When a `Filter` sits above a `Window` (an outer query over a windowed
derived table / subquery), SQL requires the window to see **all** input rows; pushing the
filter recomputes `ROW_NUMBER/RANK/SUM/FIRST_VALUE/…` over only the surviving rows.
The module doc lists the push targets and conspicuously omits `Window` (the safe push would
be partition-key conjuncts only).
**Trigger:** `SELECT x, rn FROM (SELECT x, ROW_NUMBER() OVER (ORDER BY x) rn FROM t) s WHERE x > 3;`

### P1 — JOIN equi-key extraction underflows on a comparison operand that mixes both sides **[verified]**
`crates/pinkdb/src/sql/binder.rs:2802-2821` + `crates/pinkdb/src/plan.rs:1360`
`side()` returns `Some(true)` only when *all* columns are left-side, otherwise `Some(false)` —
it cannot distinguish "all right-side" from "mixed". A mixed operand is treated as a
right-side key and passed to `shift_columns(expr, left_cols)`, which does `index - by`; the
left-side columns (index < `left_cols`) underflow.
**Trigger:** `SELECT * FROM sales s JOIN sales o ON s.id = o.id + s.id;`
Debug: `attempt to subtract with overflow` panic at bind. Release: wraps to `usize::MAX-2`,
hash join reads a non-existent column. (Pure equi / pure non-equi joins are fine and tested;
this mixed case is untested.)

### P1 — `ALTER TABLE … ADD COLUMN … DEFAULT <expr>` bypasses the AST-depth and parameter-rank guards
`crates/pinkdb/src/sql/mod.rs:218-256` (`max_ast_depth` → `_ => {}`) and `:425-466`
(`take_statement_children` → `_ => {}`); same omission in
`crates/pinkdb/src/sql/peg_parser.rs:318-350` and `:446-478`; intended support pinned at
`crates/pinkdb/src/sql/binder.rs:3526-3535`.
The pre-parse nesting estimate only counts parens/CASE/unary, so `1+1+1+…` estimates depth 1;
the guard normally rejects the chain at 64 but never descends into the ALTER default, so
binding recurses over a left-deep expression and blows the stack.
**Trigger:** `ALTER TABLE t ADD COLUMN c INTEGER DEFAULT 1+1+1+… ;` (~100k `+1`).
Separately: a `?` in the default keeps its byte-offset (never renumbered to a rank), so
prepared `ALTER … DEFAULT ?` fails with `internal error: no parameter slot N`.

### P1 — Unbounded plan depth from long JOIN / UNION chains
`crates/pinkdb/src/sql/mod.rs:338-343` and `:279-281` push each join/union branch at a **flat**
`depth+1`, but `bind_union_chain` (`binder.rs:4099-4128`) and the join folder
(`binder.rs:4481-4525`) fold branches into a **left-deep nested** plan. `plan_schema`
(`binder.rs:4236`), `exec::eval`, `fold_plan` and `Drop` then recurse down that spine, which
the AST-depth guard does not bound.
**Trigger:** ~10⁴–10⁵ `UNION ALL` branches, or a very long `a JOIN b ON … JOIN c ON …` chain.
(`bind_pair_types` is also O(N²) — it re-walks the accumulated left plan each step.)

### P1 — RANGE frame with an offset and a NULL ordering key ignores the frame's lower bound
`crates/pinkdb/src/exec/window.rs:346-360` (running accumulator) vs `:513-523` (`range_frame`
NULL branch).
The incremental accumulator assumes the frame is always `[0, hi]` and never reads `lo`; but
when the current ordering key is NULL and the frame has an offset, `range_frame` returns a
NULL peer group with `lo > 0`. The incremental path sums `[0, hi]` while the per-row recompute
correctly uses `[lo, hi]` — the two paths disagree.
**Trigger:** `SELECT SUM(v) OVER (ORDER BY k RANGE BETWEEN UNBOUNDED PRECEDING AND 1 FOLLOWING) FROM t;`
where `k` contains NULLs.

### P2 — Right operand of comparison / `LIKE` / `BETWEEN` rejects `||`
`crates/pinkdb/src/sql/peg_parser.rs:1404-1409`. The grammar docs (and `concat_expr`, `:1391`)
place `||` above additive / below comparison, but only the *left* operand uses `concat_expr`.
**Trigger:** `WHERE a = b || c`, `WHERE a || b = c || d`, `LIKE 'x' || '%'` fail to parse, though
`a || b = c` parses.

### P2 — SELECT alias shadows a real input column *within the same SELECT list* (wrong results)
`crates/pinkdb/src/sql/binder.rs:4530-4538`, `:4611-4615`, `:1176-1191`. Aliases are populated
and `allow_alias` stays true while binding the select items, so a later item resolves to the
earlier alias instead of the input column.
**Trigger:** `SELECT id*2 AS id, id FROM t;` → `(id*2, id*2)`; `SELECT a AS b, b FROM t` → `(a, a)`.
(Standard SQL only exposes aliases in ORDER BY/GROUP BY/HAVING.)

### P2 — Set-op type unification rejects a bare `NULL` arm
`crates/pinkdb/src/sql/binder.rs:4154-4157` calls `coalesce_common` directly, unlike
COALESCE/CASE which skip `Literal(Null)` (`:702-710`).
**Trigger:** `SELECT NULL UNION ALL SELECT 'x';` → `incompatible types INTEGER and VARCHAR`.

### P2 — Smaller correctness edges
- **`round(decimal, i64::MIN)` negation overflow** — `expr.rs:1808` `let drop = (-digits) as u32;`
  after only a `digits >= 0` guard. Debug panic; release silently wrong.
- **`timestamp - timestamp` unchecked `i64` subtraction** — `expr.rs:1391-1405` (extreme
  timestamps span ~±9.2e18 µs; difference overflows). Every other temporal path uses `checked_*`.
- **Unchecked index in non-exec `rewrite_through_project`** — `optimizer.rs:408-410` indexes
  `&exprs[*index]` where the executor twin uses `.get(*index)?` (`exec/mod.rs:2050`).
- **INTERVAL hashing disagrees with comparison order** — `vector.rs:659-665` +
  `aggregate.rs:67-76` encode raw `(months, days, micros)`, but `compare_values`/`interval_cmp`
  normalize (1 month == 30 days). So `'1 month'` and `'30 days'` compare `=` and sort as peers,
  yet GROUP BY / DISTINCT / JOIN / INTERSECT treat them as distinct — the same class bug the
  float `-0.0`/NaN path explicitly fixed (`vector.rs:622-634`).
- **CASE / COALESCE evaluate every arm eagerly** — `expr.rs:2421-2429`, `:2451-2467`. A row whose
  selected branch is safe still errors on an unselected branch's row-dependent error
  (`CASE WHEN x <> 0 THEN y/x ELSE 0 END` raises division-by-zero on `x = 0`).

### P2 — Stale / false docs
- `aggregate.rs:1-5` says "SUM over integers accumulates in i64 (wraps)"; the code uses exact
  i128 and **errors** on BIGINT overflow (`aggregate.rs:722-739`).
- `exec/mod.rs:97-104` claims each uncorrelated subquery "evaluates once"; under `par_iter`
  (`exec/mod.rs:1082/1303/1187`) the check-then-insert `Mutex<HashMap>` race lets two chunks
  both evaluate it. Results stay correct; the guarantee is false.

## 2. Persistence, WAL & engine crypto (`crates/pinkdb/src`)

### P1 — Plaintext WAL mid-file corruption silently truncates all later records **[verified]**
`crates/pinkdb/src/wal.rs:2346-2350`. A plaintext record with a CRC mismatch unconditionally
`break`s, so the caller truncates at that offset. This is only safe at EOF; a bit flip in a
middle record (bit rot, partial page, bad sector) discards every still-intact committed record
after it. The **encrypted** path deliberately hard-errors on an auth failure with bytes
following (`wal.rs:2333-2343`), so the two paths have asymmetric durability for the same fault.
**Trigger:** flip one bit inside a non-final record of a `SyncPolicy::Sync` log, reopen.

### P1 — `save` / `save_with_key` are non-atomic and take no transaction guard **[verified]**
`crates/pinkdb/src/persist.rs:2314-2317` and `:2323-2334` use `std::fs::write` (truncate in
place, no temp + rename, no fsync) and only call `ensure_wal_healthy` — they happily serialize
the store mid-`BEGIN`, unlike `checkpoint_with_guard` (`wal.rs:4105-4109`).
**Triggers:** (a) `BEGIN; INSERT …; db.save(p); ROLLBACK;` then reopen → rolled-back rows
resurrected; (b) `db.save(bound_path)` while the WAL has records, then reopen → WAL replayed on
top of the checkpoint (duplicate rows / `table already exists`). `save_snapshot` enforces the
bound-path rule; plain `save` does not. An interrupted `save` also leaves a corrupt checkpoint.

### P2 — Session databases leak into the optimistic-commit validation set **[verified, mechanism unconfirmed]**
`crates/pinkdb/src/db.rs:797-799` adds every `txn.wal_dbs` entry (populated per buffered write
statement with its session db, `db.rs:437-441`) via `ours.add_database(db)`. The docs
(`db.rs:275-278`, `plan.rs:366-372`) say this set exists only for `CREATE`/`DROP DATABASE`
names and promise **table-level** conflict granularity. If `FrameSets::conflict_with` treats
`ours.dbs` as a wildcard, any frame touching a table in that session db conflicts.
**Trigger (per review):** process A `BEGIN; INSERT INTO main.t …`, process B autocommits
`INSERT INTO main.u …` (disjoint), A `COMMIT` → spurious `write conflict on main.u`.
*Action:* confirm `FrameSets::conflict_with` semantics before treating as confirmed.

### P2 — Smaller durability edges
- **New/recreated WAL files are never directory-fsynced** — `wal.rs:1376-1402` (`create_file`
  fsyncs contents only); `sync_parent_dir` runs only after checkpoint renames
  (`wal.rs:1881/1948/1954`). A fresh database's first WAL, or a recovery-recreated WAL, can lose
  its dirent on crash even under `Sync`.
- **Unchecked LSN `+ 1`** — `wal.rs:1695` (`append`) and `:1643` (`scan_increment`) overflow at
  `u64::MAX` (debug panic / release wrap); elsewhere the code uses `checked_add`.
- **`pos + n` overflow in record decoders on 32-bit** — `wal.rs:2196-2201`, `:2091-2113` use
  unguarded `usize` addition (unlike `parse_records`' `checked_add`).
- **`header_torn` reclassifies a future/unsupported container version as torn** — `wal.rs:2934-2947`:
  `HeaderError::Container(_)` (incl. `unsupported container version N`) on a short file is
  overwritten by `create_file`, discarding records; the plaintext path treats `BadVersion` as
  never-torn (`:2940`).
- **`.pink` string offsets truncate to `u32` with no error** — `persist.rs:1192-1202` +
  `Writer::str` `:534-537`; a >4 GiB chunk of VARCHAR bytes wraps offsets and emits a file that
  writes successfully but fails to decode (`bad string offsets`). The WAL encoder guards every
  length with `u32::try_from`; the `.pink` writer does not.

## 3. `pink-lake` core

### P1 — A commit on a `format_version` 1–3 head publishes an **unreadable** catalog **[verified]**
`crates/pink-lake/src/incremental.rs:1482-1494` (also `:1510-1523`, `:1674-1675`).
`try_publish_commit` does `entry.files.extend(...)` + `entry.rows = …` on an existing entry but
never normalizes `entry.format` or converts a legacy `FileRef::Path`. The new manifest is
written with `format_version = 5`, and `read_manifest` rejects `(4|5, Path(_))` ("lists a data
file without its row count") and `(4|5, None)` ("does not declare a data file format").
**Trigger:** open a v1/v2/v3 lake, then `Commit::append` / `WritableAttachment::commit` /
drop / `set_partition`, then `Lake::open` → error. (Delete-only is accidentally refused later
at `:1583`; appends/drops/spec changes are not. Tests only ever commit to v4/v5 heads.)

### P1 — `delete_file::decode` overflow / unbounded allocation from a corrupt delete file **[verified]**
`crates/pink-lake/src/delete_file.rs:69` and `:76`.
`count * 8` overflows `usize` for `count ≥ 2^61` (debug: panic; release: wraps, so a crafted
`count` passes the `bytes.len() != expected` check), then `Vec::with_capacity(count)` aborts.
The module promises malformed delete files are a clean `Corrupt`.
**Trigger:** a 16-byte `.pinkdel` with a giant count header in `data/…`, then read the table.

### P1 — Decrypted plaintext is written to a shared temp dir and left on crash **[verified]**
`crates/pink-lake/src/storage.rs:416-438` (`CryptoStorage::local_copy`, keyed branch) writes the
unsealed `.pink` data file to `std::env::temp_dir()/pink-lake-dec-<id>.pink` (default perms on
`/tmp`); `S3Storage::local_copy` (`s3/mod.rs:919-938`) does the same. The temp copy is removed
only when `LocalCopy` drops, so a crash/`SIGKILL` leaves the plaintext of an "encrypted" lake on
disk, readable by other local users. Documented as "stage 1", but it is a genuine at-rest leak.

### P2 — `is_container` heuristic silently skips encryption **[verified]**
`crates/pink-lake/src/crypto.rs:239` (`is_container` = `starts_with(ENC_MAGIC)`) +
`crates/pink-lake/src/storage.rs:319-325` (`sealed`): in a keyed session the bytes are stored
**as-is** (no encryption) if the first 8 bytes are `PNKLAKE1`; the later keyed read then fails
closed (`plain()` → `WrongKey`/`Tampered`), so the object is both unencrypted at rest **and**
unreadable. Not reachable with today's JSON/Vortex/`.pink` writers, but the heuristic should be
an explicit "already sealed" marker.

### P2 — Attach `COUNT(*)` fast path can disagree when delete files overlap
`crates/pink-lake/src/attach.rs:1543` (`rows: entry.rows`) vs `incremental.rs:1013-1016` (dedup)
and `lib.rs:2241-2250`. `read_manifest` validates `sum(deletes.count) == data_rows - entry.rows`
and that each delete targets a listed file, but does not forbid two delete files hitting the
**same** data file; `entry_layout` dedups merged positions, so a decode yields more rows than
`entry.rows`. `Lake::load` catches this (`num_rows() != entry.rows` → `Corrupt`), but attach
never re-checks and reports a wrong `COUNT(*)`.

### P2 — Smaller lake edges
- **Full save resets `schema_version` when the predecessor manifest is unreadable** —
  `lib.rs:1196` + `:2372-2386`: `previous = None` → `next_schema_version` returns 1, discarding
  the real counter (documented as monotonic lake-wide).
- **`read_manifest` partition error prints the wrong name** — `lib.rs:2203-2208` shadows the
  table `key` with the loop's partition key, so the message says `table "<key text>"`.
- **Container version mismatch reported as `Tampered`** — `crypto.rs:~558-571`: a newer-version
  container is not corrupt; the caller sees "corrupt or tampered" instead of an upgrade error.
- **Sealed manifests are bound to nothing** — `storage.rs:239-251` (`crypto_domain`): snapshots
  and catalog authenticate under domain `Manifest` / binding `""`, so `snapshots/5.json` also
  authenticates at `snapshots/2.json`. Mitigated by the declared-`version`-vs-filename check
  (`lib.rs:1938-1946/1976-1979`), but a same-version manifest from another lake (same key) is
  accepted — a deliberate cost of the `catalog == snapshot` byte-identity invariant, worth
  knowing as a rollback/replay surface.

## 4. `pink-lake` S3 backend & CLI lake

### P2 — `429`/`503` are retried even for conditional PUTs
`crates/pink-lake/src/s3/mod.rs:1256-1260`: the `429 | 503` arm ignores the `conditional` guard
that the `500|502|504`/transport arm applies, contradicting the module docs (`s3/mod.rs:45-55`).
**Trigger:** an intermediary returns `503` after `If-None-Match: *` committed → retry sees its
own object → `412` → `put_new` returns `Ok(false)` → bogus `Conflict` for a save that succeeded.

### P2 — A `400 InvalidRequest` permanently "degrades" the endpoint
`crates/pink-lake/src/s3/mod.rs:1544-1553` (`is_unsupported_conditional`). `InvalidRequest` is
generic; once `note_conditional_unsupported` fires (`:495-502`) the `degraded` flag is sticky
and the default mode refuses **every** later write with `UnsupportedEndpoint` until reopen.

### P2 — Smaller S3/CLI edges
- **`lake_key()` falls back to plaintext on an invalid `PINKDB_KEY`** — `pinkdb-cli/src/lake.rs:94-102`:
  on `Err`, `cli_error!` only prints and sets `HAD_ERROR`, returns `None` → plaintext open.
  Violates the function's own "never a silent plaintext lake" contract; masked today by the
  startup `exit(2)` check (`main.rs:1093-1101`), so latent.
- **Crafted `binding_len` panics on 32-bit** — `crypto.rs:589-597`: `pos + binding_len`
  overflows `usize`; safe on 64-bit.
- **SigV4 trims but does not collapse internal whitespace** — `s3/sigv4.rs:90-95` vs the mock's
  `collapse_spaces` (`mock_s3.rs:1143-1158`); a signed header value with a double space would
  `SignatureDoesNotMatch` on AWS.
- **`PINKDB_LAKE_RETRY_BACKOFF=inf`** — `pinkdb-cli/src/lake.rs:179-188` accepts `inf`
  (`Ok(v) if v >= 0.0`), which can hang the retry loop.
- **`.lake partition` lacks the in-transaction guard** the other mutating lake commands have —
  `pinkdb-cli/src/lake.rs:875-999` (`let _ = db;`).
- **`S3Config` `Debug` prints the access-key id** (secret + session token are redacted) —
  `s3/mod.rs:172-191`; and server-provided ETags are copied into `if-match` unvalidated
  (`s3/mod.rs:1157/769`).

## 5. Server, FFI, CLI & bindings

### P1 — `ExecutePrepared` value-count OOM amplification (unauthenticated, pre-handshake) **[verified]**
`crates/pinkdb-server/src/protocol.rs:251-262`. The guard `count > r.remaining()` bounds the
count only by remaining *bytes* (each `NULL` tag = 1 byte) but then pushes `count` `Value`s
(~32 B each). A ~60 MiB frame of `0x00` tags materializes ~2 GiB (≈3 GiB peak with realloc);
`Vec::with_capacity(count.min(1024))` does not prevent the loop from growing it. Decoding runs
**before** the "expected a Hello" check (`server.rs:346-359`), so no handshake is needed, and
OOM abort is not catchable by `catch_unwind`. With `DEFAULT_MAX_CONNECTIONS = 128` this is a
remote DoS.
**Trigger:** first frame `len≈60 MiB, type=EXECUTE_PREPARED(5), handle=0, count=0x03938700`,
then that many `0x00`.

### P1/P2 — `Rows` decode over-allocation (client side)
`crates/pinkdb-server/src/protocol.rs:498-516`. `row_cost = columns.max(1)`, so `columns == 0`
degenerates to `count ≤ remaining+1`; each row is a `Vec<Value>` (and a 32 B `Value` when
`columns == 1`). ~60 MiB of zeros materializes ~1.4 GiB (`columns=0`) to ~3.6 GiB (`columns=1`).
**Trigger:** a hostile/compromised server sends one such `Rows` frame to a `--host` CLI client.

### P2 — Server/FFI/bindings edges
- **`read_batch` has no cap** — `client.rs:229-301` accumulates every `Rows` frame until
  `BatchDone`; a hostile server can stream unbounded rows and OOM the client.
- **Client has no read/write timeout** — `client.rs:79-121` sets only `TCP_NODELAY`; a stalling
  server hangs remote mode forever (the server side has an idle timeout, the client does not).
- **`reject_over_limit` writes on the accept-loop thread with no timeout** — `server.rs:264-270`
  (small frames, low impact, but on the wrong thread).
- **`pinkdb_open_memory` is not under `catch_unwind`** — `pinkdb-ffi/src/lib.rs:395-399` (every
  other entry point is); same for `build_result`/`Box::new` at `:432-433`, `:584`. A panic there
  unwinds across the `extern "C"` boundary (UB), despite the crate header claiming the fully
  guarded boundary.
- **`is_loopback_host` mis-parses IPv6 brackets** — `repo/config.rs:211-227`: `[::1]evil.com` is
  treated as loopback, bypassing the plain-`http` refusal.
- **Repo `save_repositories_to` writes its temp file with `fs::write`** (predictable
  `…tmp-<pid>` name, follows symlinks) — `repo/config.rs:114`, unlike the artifact path which
  correctly uses `create_new` (`client.rs:217-220`).
- **Bindings miss new tags/kinds** — Python `_value_to_python`/`_TYPE_NAMES` lack DECIMAL (tag 8)
  / INTERVAL (tag 9) (`bindings/python/pinkdb/__init__.py:252-293`) and the `ALTERED_TABLE` kind
  (16) (`:58-75`); Go `valueToGo` / kind map (`bindings/go/pinkdb.go:352-380`, `:85-102`) same.
  `SELECT 1.5::DECIMAL(4,2)` fails in Python; `ALTER TABLE …` surfaces as `"unknown"`.
- **CLI `.save`/`.open` ignore quoting** — `pinkdb-cli/src/main.rs:706,748` use
  `split_whitespace().next()` instead of the quote-aware `take_token`/`unquote` used by
  `.read`/`.import`, so `.open "my db.pink"` breaks.
- **CLI prints stored VARCHAR verbatim** — `main.rs:841-854` writes terminal escape sequences
  from untrusted rows straight to stdout (output injection).
- **Repo path validation is Unix-only** — `repo/catalog.rs:121-130` (`is_safe_component`) allows
  `:` and Windows reserved names / trailing dots, contradicting the "cannot escape `extensions/`"
  claim on Windows.
- **`next_handle += 1` unchecked** — `server.rs:478` (wrap → handle collision; not reachable).

### P2 — Doc drift (verified against code)
- `pinkdb-server/src/protocol.rs:47-52` — version history mislabels DECIMAL/INTERVAL as "v5"
  (it is v6) and `PROTOCOL_VERSION = 7` skips v6; the header contradicts itself.
- `pinkdb-ffi/include/pinkdb.h:20-22` — claims only one handle may open a durable file; the code
  and the wave-45m Python test allow many.
- `README.md:1929-1930` — "no FULL joins and CROSS joins are rejected" contradicts
  `README.md:103-104/175` and the parser/binder (`ast.rs:283-293`, `peg_parser.rs:1311-1316`);
  the limits bullet is stale (likely meant to describe `NATURAL`/`USING`, which *are* rejected).
- `pinkdb-ffi/src/lib.rs:600-636` — `value_from_pink` rejects DECIMAL/INTERVAL (read-only by
  design, but the error is generic and asymmetric with `Cell::from_value`).

## 6. Checked and believed correct (bounds the search)

- **WAL encryption:** per-unit counter (`prefix||u32`), counter 0 = key-check, fresh random
  prefix on create/fork and on every keyed full open; checkpoint-vs-WAL domain strings bound into
  every unit's AAD. **No (key, nonce) reuse found.**
- **Checkpoint state machine:** `.tmp`-before-roll and publish-before-remove ordering is correct
  and idempotent across the `{no tmp, stale roll}` and `{tmp, roll, empty/torn live WAL}`
  windows; generation cross-checks and the `u64::MAX` guard are present.
- **Container parsing:** every length/slice is bounds-checked; terminal zero-length segment
  enforced as last frame (segment-boundary truncation rejected); no `with_capacity` from an
  unvalidated header field.
- **Lake publication ordering / atomicity:** data → `commits/<v>` → `snapshots/<v>` →
  `catalog.json`, stray-delta healing, stray-snapshot refusal, degraded-endpoint reconcile —
  consistent between save and commit paths.
- **Diff / merge-on-read** (`diff_table`, `rebuild_logical`, `apply_file_deletes`, `entry_layout`)
  and **zone-map pruning** (`zone.rs`: every `PruneOp` bound is conservative; partition scalars
  used only for identity keys; bucket labels never used to prune) — correct.
- **Schema records / ALTER / time travel** (`schema.rs`, `physical_name`, epoch stamping) and
  **stats fast paths + CRC** (delete gating, DOUBLE NaN/`-0.0` gates) — consistent with docs.
- **Hash join** build/probe/outer/full assembly and NULL handling; sort byte-encoding incl. NULL
  placement; `UNION/INTERSECT/EXCEPT [ALL]` multiplicities; CTAS/INSERT staging.
- **`sql/split.rs`** statement/parameter splitters mirror the grammar's trivia/quote/comment
  rules — no splitter defect found.
- **Server frame handling:** `read_frame` grows by arrival (no pre-alloc from the untrusted
  length), `Reader::take/remaining` cannot under/over-read, panic isolation works,
  `LOAD EXTENSION` is correctly gated off by default (no unauthenticated RCE).
