Server & protocol

pinkdb-server is a separate workspace crate (so the core stays lean): a TCP server plus a blocking client for a hand-rolled binary protocol — no external dependencies, zero async (one std thread per connection), no unsafe. Release binary: 1.84 MB.

Build and run

# in-memory server on 127.0.0.1:5433
cargo run --release -p pinkdb-server

# durable server: same checkpoint + WAL guarantees as the embedded path
cargo run --release -p pinkdb-server -- --file sales.pink

# explicit bind address and port (0 picks an ephemeral port)
cargo run --release -p pinkdb-server -- --host 127.0.0.1 --port 5433

pinkdb-server --help lists the flags: --host (default 127.0.0.1), --port (default 5433), and --file (a durable .pink: the checkpoint loads and the sidecar WAL replays on restart; in-memory when omitted). On startup the server prints its listening address and runs until terminated:

pinkdb-server v0.1.0 listening on 127.0.0.1:5433 (in-memory)

Both modes share the wave-22 durability path: rows acknowledged to a client survive a server crash and are replayed on the next start with --file.

Remote CLI mode

cargo build --release -p pinkdb-cli --features client
./target/release/pinkdb --host 127.0.0.1:5433

Every SQL statement is sent to the server and rendered with the same box-drawn output and timing line as the embedded REPL. SQL — including USE, CREATE DATABASE, and BEGIN/COMMIT — works unchanged; the file and catalog dot-commands (.import, .save, .open, .databases, .tables, .schema) are unavailable and report Error: <cmd> is not available in remote mode. The feature is opt-in; the default build rejects --host with “built without the client feature”.

Protocol

One TCP connection is one session. Every message is a frame: a u32 little-endian length prefix + a u8 message type + body. Frames larger than 64 MiB are rejected before allocation, and every inner length (strings, columns, rows, values) is validated against the bytes remaining in the frame — a malformed or truncated peer can never make the decoder read out of bounds or over-allocate. The protocol version is 2.

DirectionFrames
Requests Hello { protocol_version } (required first; a mismatched version is rejected with a clear error), Execute { sql }, Ping
Responses HelloOk { server_version, protocol_version }, Pong, and per statement a result group: ResultSet { names, types }, then chunked Rows { count, columns, values... }, then Done { kind }
Batch terminator exactly one BatchDone { statements } frame after a successful Execute batch, so neither side parses SQL just to count statements; a failing statement ends the batch with a single Error { message } instead, and the connection stays open

Rows are encoded with typed values: a tag byte + payload for NULL/BOOL/I32/I64/F64/VARCHAR/DATE/TIMESTAMP, plus a DataType tag byte. The client reconstructs pinkdb's public QueryResult/Value/DataType, so remote results render exactly like local ones. Each connection gets its own Connection, so multi-database sessions (USE, transactions) are isolated per TCP client. After a decode or transport error the client marks itself broken and fails fast on later calls instead of reading a desynchronized stream.

Robustness

  • 16 MiB stack per connection thread. The engine's depth guards reject hostile statements before they can recurse.
  • Transient accept errors never stop the server. EMFILE/ENFILE/ECONNABORTED/ENOBUFS are logged and retried with a 10 ms → 1 s backoff, so an fd spike no longer kills the process.
  • 128 concurrent connections (DEFAULT_MAX_CONNECTIONS). Over the cap the server sends a best-effort Error frame and closes, bounding fds/threads.
  • Panics are isolated. A panic while executing one statement is caught, logged, and reported as an Error frame; the connection and every other client stay alive. A poisoned store lock is logged once and recovered, so one bad statement cannot permanently DoS the database (the state may be inconsistent — recovery is loud).
  • No read/write timeouts. A slow or stalled client holds one thread and one fd until it disconnects; the connection cap bounds that pressure.
  • Depth guards. Statements nested deeper than 24 units (parens, CASE, prefix unary) or with an AST deeper than 64 nodes are rejected with a clean Parse error before bind/execute/drop can recurse.

Security posture

No authentication, no TLS, no authorization in this wave

Anyone who can open a TCP connection to the port gets the full SQL surface of the served database (queries, writes, DDL) on the one shared store. The server binds 127.0.0.1 by default and must stay on localhost or a trusted network: do not expose it to the internet or to untrusted clients.

  • TLS (rustls + certificate config) is on the roadmap as wave 45; users/roles with Argon2id password hashes (RBAC) are wave 47.
  • pinkdb-server has no encryption-key option: its --file must be a plaintext database (an encrypted one is refused at startup), and PINKDB_KEY is ignored by the server.
  • In remote CLI mode, PINKDB_KEY is reported as inert instead of being silently ignored.
