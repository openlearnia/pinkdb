Guide: encrypted databases

Encrypt an entire database at rest — checkpoint and WAL — with AES-256-GCM and an Argon2id-derived key, using the opt-in encryption feature.

1. Build with encryption

cargo build --release -p pinkdb-cli --features encryption

The default build links no crypto at all; this feature adds the audited RustCrypto crates aes-gcm and argon2 (about 70 KB over the default on a thin-LTO release build). Unencrypted files stay byte-identical either way.

2. Use PINKDB_KEY in the CLI

export PINKDB_KEY='correct horse battery staple'
./target/release/pinkdb
pinkdb> .import sales.csv sales
pinkdb> .save sales.pink          -- writes an encrypted checkpoint
pinkdb> .quit

$ ./target/release/pinkdb           # fresh process
pinkdb> .open sales.pink           -- decrypts; the durable WAL uses the same key
pinkdb> SELECT COUNT(*) FROM sales;
  • The passphrase is stretched with Argon2id (defaults m=19 MiB, t=2, p=1); the salt and parameters are stored in the file header, so raising the defaults later keeps old files readable.
  • PINKDB_KEY must be valid UTF-8. A set-but-invalid value is a hard error (exit 2) instead of a silent fallback to plaintext.
  • Unset, behavior is byte-identical to an unkeyed build.

3. Use it from Rust

use pinkdb::{EncryptionKey, PinkDb};

let key = EncryptionKey::from_passphrase("correct horse battery staple");

db.save_with_key("x.pink", &key)?;                        // encrypted snapshot
let db = PinkDb::open_with_key("x.pink", &key)?;          // decrypts
let db = PinkDb::open_durable_with_key("x.pink", &key)?;  // encrypted WAL

// multi-connection open:
// let db = pinkdb::Database::open_with_key("x.pink", &key)?;

A raw 32-byte key is also accepted — see EncryptionKey.

4. How the container works

  • The file becomes a PINKENC1 container (version 2): a plaintext header (KDF parameters, salt, a random per-container nonce prefix, an AEAD key-check block) followed by AEAD-sealed payloads. The WAL container carries a small plaintext publish block so the multi-process refresh can work. Nothing but those small blocks is readable in the clear — rows and SQL text are ciphertext.
  • Each open re-seals the WAL under a fresh random nonce prefix, so a record discarded by a truncation can never reuse a (key, nonce) pair.
  • Header parameters are validated on read against a small multiple of the defaults (m ≤ 76 MiB, t ≤ 4, p ≤ 4), so a crafted header cannot make an open burn minutes deriving.
  • Checkpoint containers end with a terminal zero-length segment, so a container cut at a segment boundary is rejected instead of loading a silently shorter database.

Gotchas

  • A wrong key says so: the key-check block fails with wrong key, never “corrupt file”.
  • Encrypted and plaintext never mix. A keyed open refuses a plaintext checkpoint/WAL and a plaintext open refuses an encrypted one, so a key can never be silently ignored. Without the feature, opening an encrypted file reports file is encrypted; build with the encryption feature.
  • The mode and key are fixed at open for a live store; changing set_encryption_key afterwards is refused at the next checkpoint (cannot change encryption mode on a live store; reopen it instead), and a snapshot save refuses a target in the other mode or under a different key.
  • Not exposed everywhere yet: the C ABI takes only a path, so the Python/Go bindings and C embedders open plaintext databases; use the Rust API or the CLI for encrypted stores. pinkdb-server has no key option — its --file must be plaintext.
  • Lakes are not encrypted. PINKDB_KEY applies to .pink databases and their WAL, not to lake data files or objects.
