Roadmap

What pinkdb ships today, what is being worked on, and what is planned. This page is the product view; the change-by-change engineering log — with measurements and benchmark notes — lives in ROADMAP.md on GitHub.

Shipped#

  • Analytical engine

    Columnar vectors, vectorized execution over ≤2,048-row chunks, and parallel operators. CSV import with per-column type inference.

  • SQL surface

    DDL/DML, INNER/LEFT/RIGHT equi-joins, CTEs, derived tables and uncorrelated subqueries, window functions, aggregates, CASE/CAST/COALESCE/LIKE, dates and timestamps, UNION, views, snapshot transactions, multiple databases. Differentially tested against DuckDB.

  • Persistence

    Single-file .pink v4 columnar format with delta, dictionary, ALP and LZ encodings; bit-exact round trips; a write-ahead log with atomic checkpoints and crash recovery.

  • Multi-process databases

    Any number of local processes can open a durable database read-write; writers serialize on a per-operation write lease and readers refresh from the WAL.

  • At-rest encryption

    Optional PINKENC1 containers — AES-256-GCM with Argon2id key derivation — covering the checkpoint and the WAL.

  • Lake layer

    JSON catalog plus immutable snapshots; full snapshots per save; Vortex or lean .pink v4 data files; version restore. Read-only attach answers exact COUNT/MIN/MAX from stored statistics.

  • Object storage

    s3:// lakes on AWS S3, Cloudflare R2 and other S3-compatible endpoints, with atomic conditional writes for conflict detection.

  • Network server

    pinkdb-server over a framed binary protocol (version 4) with a remote CLI mode, durable --file mode, connection caps and idle timeouts.

  • Bindings

    Rust natively; a C ABI (v1) with a hand-written header; dependency-free Python (ctypes) and Go (cgo) wrappers.

  • Extensions

    Runtime-loadable native scalar functions (ABI v1), in-repo C/C++ and Go SDKs, and the hosted extension catalog with one-command .install.

In progress#

  • Durable multi-process hardening. The first slice — any process read-write, per-operation write lease, lock-free epoch refresh, WAL v3 — is shipped. The follow-up round is a stability focus: chaos soaks, fuzzing, and closing the known gaps around replay and recovery edge cases.

Planned#

Server security and operations

  • TLS for the network server (rustls + certificate configuration), so remote clients can connect over an encrypted transport.
  • RBAC: users and roles with Argon2id password hashes, CREATE USER/CREATE ROLE/GRANT/REVOKE on databases and tables, session login and per-connection enforcement; grants persisted and WAL-logged.
  • Async I/O at the boundary: an optional async storage layer (object stores / S3) and/or async server variant, feature-gated — a documented carve-out where only the I/O boundary goes async; the executor stays synchronous.

SQL and the engine

  • SQL completeness: multi-way, composite and non-equi joins, CROSS/FULL joins, INSERT ... SELECT, CTAS, IF [NOT] EXISTS, OFFSET, NULLS FIRST/LAST, INTERSECT/EXCEPT, COUNT(DISTINCT), EXPLAIN, SHOW/DESCRIBE, RANGE window frames.
  • Prepared statements and parameters: placeholders, a bind API, and the front-end support that follows (protocol, FFI, Python, Go).
  • Functions and types: lag/lead/ ntile/first_value/last_value, remaining scalar gaps, DECIMAL and INTERVAL types.
  • Schema features: declarative primary/foreign keys and constraints (metadata used by the optimizer), indexes with zone-map support, and materialized views.
  • Optimizer work: projection pushdown, LIMIT short-circuiting, join build-side choice, filter-through-aggregate.

Lake

  • Incremental saves and .lake gc: appending changes instead of full-snapshot rewrites, with garbage collection for retired versions.
  • Scan pruning: per-chunk statistics and filter/zone-map pruning for attached lakes (the planned third stage of the lake-scan work) plus lean projection pushdown.
  • SQL access to lakes: a lake_scan table function and time travel over published versions.
  • Faster decode: bulk typed lake decode on the open path.

Extensions and distribution

  • Rust extension SDK: a safe wrapper and registration macros for first-party extensions (including a deterministic/volatile flag so the engine never WAL-logs volatile calls).
  • Core extensions: json, string, math and datetime function packs.
  • Extension trust: Ed25519 artifact signatures, SQL INSTALL, Linux artifacts.
  • Extensions on wasm: a pluggable loading model for wasm targets (native dlopen cannot work in the sandbox).
  • Packaging: a Python wheel and a standalone Go module.

Performance

  • Recurring tuning rounds against the committed query benchmark, following the existing profile-first approach.

Deferred#

Not currently scheduled:

  • Parquet read support (pinkdb-parquet).
  • JS/wasm, Node-native and Java bindings.
