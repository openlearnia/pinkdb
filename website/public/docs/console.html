The warehouse console

pinkdb-server can serve a web console next to its binary protocol: SQL worksheets, a catalog browser, the run history and an ask box for the data agent. It is off by default and compiled only into a build with the ui feature; the browser app is Rust (Leptos) compiled to WebAssembly and embedded in the binary — nothing comes from a CDN.

Start it#

Shell
cargo build --release -p pinkdb-server --features ui
./target/release/pinkdb-server --file warehouse.pink --enable-ui
# pinkdb-server: warehouse console on http://127.0.0.1:8080 (worksheets)

The console asks for sign-in with the store's users, whose grants then apply to every statement. A store without users starts in first-run setup: the server prints a setup code, and the account created with it becomes the administrator. Each user can add a TOTP second factor and create personal access tokens for scripts (Authorization: Bearer pdbt_…). --ui-tls-cert and --ui-tls-key serve HTTPS and allow a non-loopback address; --ui-read-only limits everyone to queries.

What you see#

The screens below are described rather than pictured.

  • The top bar holds the database statements run in, a read-only badge when the console is, the user name, Ask and Log out.
  • The left panel has three tabs. Catalog lists each database with its tables (and row counts), views, materialized views, indexes (hash and HNSW), triggers, macros and attached lake tables; a table opens to its columns, with types, and its statistics on hover (NULLs, distinct estimate, min … max). + inserts a name at the cursor, ▶ opens a worksheet with the first 100 rows, ⏱ on a lake table opens time travel and the change feed. Worksheets lists your saved worksheets and those shared with you; History lists your runs, newest first.
  • The worksheet is a tab with a title, Run all, a share with field and a saved/unsaved mark, then the editor: SQL highlighting (keywords, strings, numbers, comments, functions and types in their own colours) and a completion list of keywords, functions, databases, tables and columns that follows the cursor.
  • The results show one tab per statement. A query's grid has the column names with their types underneath, numbers right-aligned and NULLs in italics; it scrolls through 10,000 rows smoothly because only the visible rows exist in the page. Clicking a cell opens it whole on the right, JSON pretty-printed. Chart draws bars, a line or points for any x and numeric y column; Profile shows bars for parse, bind, optimize, execute and log time; an EXPLAIN shows its plan as an indented tree of operators. CSV and JSON download the result. A failed statement shows its text and the error in red; a running query shows a spinner and Cancel.
  • The ask panel opens on the right: a provider list (no provider is chosen for you unless the server names one), an optional model, the question, and then the run as it happens — grey progress lines, a card per statement the model ran with its reply and a Copy SQL into worksheet button, and the answer.

Access, imports and storage#

  • Access (a sidebar tab) lists users, roles and grants — an administrator sees everyone, anyone else only themselves and their roles. Administrators get forms: a new user (the password never reaches the run history), a new role, and a grant of a table privilege, CREATE on a database, a role membership or ADMIN; each grant row has a revoke button. Every action is a statement run as you, so RBAC decides.
  • Import (the top bar, or the Storage tab) opens a dialog with two tabs. From a path or URL takes a server path, an https:// URL or an s3:// key, previews the first rows with their types, and loads them into a table — create, replace or append. Upload a file sends a CSV or Parquet file from your machine; the server parses it and writes the rows as you.
  • Storage shows what the server stores into: memory, a durable .pink file, or a lake catalog (.pink, SQLite, Postgres) with its data location (local or S3) and published version. Passwords in a catalog URL are shown as ***. A Checkpoint button folds the WAL into the file.

Imports from a path or URL need a server built with --features ui,parquet,httpfs, and an administrator (file and URL reads are administrator-only). An upload needs only the CREATE privilege on the database (or INSERT to append).

Keys#

KeysDoes
Ctrl/Cmd+Enterrun the statement at the cursor, or the selection
Shift+Ctrl/Cmd+Enterrun the whole worksheet

Ctrl/Cmd+Ssave now (worksheets also save as you type)

Security#

The console runs SQL as you

Server-side sessions with an HttpOnly, SameSite=Strict cookie; a CSRF token and an Origin check on every state-changing request; a Host check against DNS rebinding; a strict Content-Security-Policy with no inline script; values and names rendered as text, never markup; request, body and per-session query limits. The console binds loopback only and never serves a store with users unauthenticated. The agent's provider key stays on the server.

The ask box#

Shell
cargo build --release -p pinkdb-agent
PINKDB_AGENT_PROVIDER=zai ZAI_API_KEY=… ./target/release/pinkdb-server \
  --file warehouse.pink --enable-ui \
  --agent-extension ./target/release/libpinkdb_agent.dylib

The agent runs as the logged-in user, read-only unless the server was started with --agent-allow-writes. With --memory-extension its turns go to the user's agent memory, and --memory-distill-every SECS distills them in the background.

The full reference — endpoints, limits, flags — is docs/server-ui.md.
