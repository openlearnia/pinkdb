Guide: multi-process writers

A durable .pink database can be opened read-write by several local processes at once. Writers serialize on a short-held write lease; readers never block and never see uncommitted rows.

1. Build the default CLI#

Nothing extra is needed — durability is in the default build:

Shell
cargo build --release -p pinkdb-cli
./target/release/pinkdb

2. Two writers, one file#

Open a terminal for each process — start the REPL, then .open the same durable database in each:

SQL
# terminal A
pinkdb> .open db.pink
pinkdb> CREATE TABLE t (n INTEGER);
pinkdb> INSERT INTO t VALUES (1);

# terminal B — same file, separate process
pinkdb> .open db.pink
pinkdb> INSERT INTO t VALUES (2);

# terminal C — a reader
pinkdb> .open db.pink
pinkdb> SELECT COUNT(*) FROM t;
┌──────────┐
│ count(*) │
│ BIGINT   │
├──────────┤
│ 2        │
└──────────┘

Each process keeps its own in-memory store. A writer takes the file's write lease for the operation — refresh, execute, append, fsync, publish — and a reader checks a publication epoch with a single pread, replaying the WAL frames it has not seen only when the epoch changed. Refresh happens at statement boundaries and before BEGIN, never mid-statement.

3. Concurrency semantics#

  • Writers serialize, per operation. Two processes never write the WAL at the same instant; the lease is held for one statement, or from BEGIN to COMMIT/ROLLBACK for a transaction (so cross-process transactions serialize too).
  • Readers never block and never observe uncommitted rows. A replaced WAL or checkpoint triggers a full rebuild on the next refresh that preserves views and attachments.
  • A busy database waits up to the busy timeout — 5 s by default — then fails with a clear database is busy error:
Shell
PINKDB_BUSY_TIMEOUT_MS=20000 ./target/release/pinkdb
# or, in Rust:
#   Database::set_busy_timeout(Duration::from_secs(20))
#   DurableOpenOptions { busy_timeout: ..., .. }
  • Crash safety: the OS releases the lease on exit or crash, so there is no stale-lock cleanup. A killed writer's committed records are recovered from the WAL by the next open.
  • Checkpoints refresh first, under the lease, so a checkpoint can never publish a state that omits another process's committed records.

4. From Rust#

Rust
use pinkdb::{Database, LockMode};

// shared in-process store, one Connection per thread
let db = Database::open("db.pink")?;
let mut writer = db.connect();
writer.execute("INSERT INTO t VALUES (42);")?;

// tune the wait for another process's lease
db.set_busy_timeout(std::time::Duration::from_secs(10));

// explicit embedded options (CLI parity):
// let db = Database::open_with_options("db.pink", DurableOpenOptions {
//     policy: SyncPolicy::Sync,
//     busy_timeout: Duration::from_secs(5),
//     lock_mode: LockMode::Required,
// })?;

Gotchas#

  • flock is assumed to work. An open on a filesystem that reports locking unsupported fails closed (LockMode::Required, the default), with LockMode::UnsafeSingleProcess as the explicit opt-out.
  • No network-filesystem detection. A filesystem that accepts flock but does not honor it across hosts (NFS/SMB) is not caught — keep multi-process databases on local storage. Windows is untested.
  • A failed WAL append is fail-stop: every later statement and save is refused until the database is reopened, which recovers exactly the durable prefix. Nobody can observe or persist the non-durable state.
  • Encrypted stores are covered too: the same lease keeps two writers off one encrypted WAL, where concurrency would risk nonce reuse.
  • Cross-process conflicts are per statement. BEGIN..COMMIT keeps its snapshot-isolation semantics; overlapping commits abort with a write conflict you can retry — and the CLI retries a whole one-call transaction automatically (PINKDB_TXN_RETRIES, default 3; 0 reports the first conflict instead). Commits validate their touched (and read) sets, so disjoint writers do not conflict at all.
