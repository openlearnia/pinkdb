2026-11-03#

Wave 136 (step c-1) — a lazily opened store reads only its footer ✅

An open no longer reads the data region: chunk bytes come from the file when a statement decodes them.

  • Open: open reads the two header slots and the footer, through a new StoreSource (a file with positioned reads, or memory for wasm, in-memory stores and encrypted files, whose container is decrypted whole). TPC-H SF1 (323 MB) now opens at 27.8 MB peak RSS in 0.01 s instead of 339 MB in 0.07 s; QuackLab's v7 store (15.6 MB) at 7.1 MB instead of 25.6 MB.
  • Checksums on first read: a column chunk's CRC32C and page index are verified the first time its bytes are read — streamed in 128 KiB blocks, so no buffer the size of the chunk — and cached. A damaged chunk now fails the statement that reads it, with the same message as before; a damaged footer still fails at open.
  • Checkpoint holes wait for their readers: an incremental checkpoint may overwrite a range only once the chunk descriptors that named it are gone; a range superseded while a snapshot or a running scan still reads it stays free for one more checkpoint. Reuse is granted only when the open-lock sidecar says no other process has the store open: a checkpoint subtracts a live reader's sub-ranges from the free list, a store that loses the sidecar fails its next statement closed, and another process's checkpoint resets the cached checksums of the chunks this store reads.

Wave 136w — faster checkpoints, commits and Parquet loads ✅

  • Incremental checkpoints: a checkpoint rewrites only the row groups that changed, into freed space or at the end of the file, and publishes them through the other header slot. TPC-H SF 1: CHECKPOINT after a one-row UPDATE 2.03 s → 0.09 s (DuckDB 0.08 s), after a 1,000-row INSERT 0.10 s, with nothing changed 1.92 s → 0.06 s. Freed space is reused (50 update-and-checkpoint rounds grow the file 3.9 %); past 50 % free space the next checkpoint compacts. Encrypted stores still rewrite in full.
  • Group commit: concurrent sessions share one WAL sync. SET wal_sync_method = 'full' | 'fsync' | 'fdatasync' picks the sync call; full (the default) flushes the drive cache on macOS, fsync is DuckDB's choice (2,000 single-row commits on macOS: 7.75 s with full, 0.13 s with fsync).
  • Parquet loads decode typed batches in parallel: lineitem SF 1 from Parquet 5.3 s → 1.0 s, on par with DuckDB, with 44 % less peak memory.

HUGEINT, and SUM typed like DuckDB ✅

  • SUM over INTEGER, BIGINT and HUGEINT returns HUGEINT, as in DuckDB, so large sums no longer overflow; AVG(HUGEINT) is DOUBLE.
  • HUGEINT values are stored, logged, sent over the wire protocol (version 17) and returned to the C API and the Node, Python and Go bindings (as exact decimal text).

Wave 136 (step c-0) — GROUP BY state bounded by groups for wide keys ✅

A GROUP BY on VARCHAR keys whose state would grow with the input rows now keeps one entry per group.

  • Memory: QuackLab's od_pairs_rollup (245,570 rows, 30,303 groups, two VARCHAR keys) peaks at 13.4 MiB instead of 91 MiB; pinkdb-server on the QuackLab chart load (16 clients x 10 rounds) peaks at 412 MB instead of 1,060 MB.
  • Known regression, to be fixed by step c-0b: the bounded path is serial, so od_pairs_rollup at 12 threads takes 63 ms instead of 13–21 ms (1 thread: 47 -> 66 ms). Integer-key aggregates (all of TPC-H) are unchanged, and results are bit-identical.

Fixes ✅

  • A reopened store starts in its default database; USE is per-connection, as in DuckDB.
  • Lakes DuckDB v2.0.0 can open: pinkdb writes DuckLake catalog version 1.1 (the 2.0 alphas' 1.1-dev1 is refused, as DuckDB refuses it), restores ducklake_schema.parent_schema_id, names 128-bit columns int128/uint128, and types inlined rows in a Postgres catalog as DuckDB does. A test compares every catalog table with a snapshot of DuckDB v2.0.0's.

2026-11-02#

Wave 133 — lake scans stream, prune to pages, and stay within the memory limit ✅

A query on a lake database reads only what it needs, in parallel, and never holds a whole table.

  • Streaming: every lake scan (plain, aggregate, sort, both join sides, AT (VERSION => …)) runs through the pipeline executor one row group at a time; the engine no longer decodes and caches a whole table on first use. Store scans and lake scans share one pull-based source.
  • Pruning: files by catalog statistics, row groups by Parquet footers, and pages by the Parquet page index, which pinkdb now writes and reads; projections, filters and join-filter bounds all reach the scan.
  • Reads: only the projected columns' byte ranges, coalesced, from local disk or object storage, several files in parallel.
  • Memory: decoded lake data is charged to the memory pool like store data, so memory_limit bounds a lake query and fails it cleanly when exceeded.
  • EXPLAIN ANALYZE prints each scan's reads, and pinkdb_scan_io() reports the last statement's per-source reads and bytes (replacing pinkdb_lake_decodes()).

DuckDB's own test corpus, and what it found first ✅

  • pinkdb-slt (tools/sqllogictest) runs DuckDB's sqllogictest files against pinkdb and reports pass rates per area; a committed baseline makes a regression fail the gate. 444 → 451 of DuckDB's 4,233 test/sql files pass so far ([docs/sqllogictest-baseline.md](docs/sqllogictest-baseline.md)).
  • PRAGMA in DuckDB's forms (show_tables, table_info, database_list, version, the pragma_* functions; DuckDB's test-only pragmas accepted).
  • Settings: SET/RESET/current_setting with DuckDB's names; default_null_order and default_order are honoured; an unknown setting is an error, as in DuckDB.
  • GROUP BY ALL, ORDER BY ALL, count(), CHAR(n), range/date/ timestamp as column names, read_csv_auto, ATTACH ':memory:'.
  • HUGEINT: literals beyond BIGINT, casts, arithmetic with DuckDB's overflow errors, comparisons; storing it and sending it to clients come next.

Wave 136 (steps a–b, through b-4) — a memory limit, a lazily opened store ✅

Opening a saved store no longer decodes it, and a statement that would outgrow the process's memory budget fails with an out-of-memory error instead of being killed by the OS. Results are unchanged.

  • SET memory_limit = '2GB' (alias max_memory, -1 = no limit) sets one process-wide budget: 80 % of the memory the process may use — physical RAM, or the tighter cgroup limit a container imposed — and no limit on wasm32. Hash-join builds, hash aggregates, sorts and the other large operators reserve the chunks they hold against it and release them on drop; over the limit the statement fails with DuckDB's out-of-memory error. A profile reports the limit and the statement's peak, on the wire protocol's v16 Profile frame.
  • Lazy open: the footer now records every chunk's row count (footer version 7), so opening a .pink file checksums the column chunks and installs descriptors without decoding a page. A chunk is decoded on first read, and a scan decodes only the columns the query asks for. A version-6 or older file is refused with the documented older-pinkdb error — there is no v6 reader and no conversion.
  • Eviction: a decoded chunk is charged to the budget and can be dropped again under pressure, least recently used first, so a store larger than the budget still scans. Dirty and pinned chunks are never evicted.
  • Copy-through .save: a checkpoint re-encodes only the chunks changed since the last save and copies the rest byte for byte.
  • COMMIT that cannot take the store's lease now aborts the transaction, so the caller's retry can BEGIN again instead of tripping over "already in a transaction".

Wave 136 (steps w1–w2) — the .pink v7 layout: two header slots, streamed writes ✅

A .pink file no longer ends with a trailer, and a save no longer builds the whole file in memory. Existing v7 files are unreadable after this change — the layout is the v7 format; a v6 file is refused with the older-pinkdb error.

  • Layout: offsets 0 and 4096 hold two 4 KiB header slots (magic PINKDB07, iteration, footer offset/length/CRC32C, file length, slot CRC32C); the data region starts at 8192 and the footer follows it. A reader takes the valid slot with the higher iteration, so a torn write leaves the previous state readable, and a ranged reader (the lake) needs two requests — the first 8 KiB, then the footer. Where the lake catalog already records the footer location, its single request still works.
  • Streamed save: .save and CHECKPOINT write the data region one row group at a time through a positioned writer, copy unchanged chunks byte for byte, then the footer, then slot 0 — so the writer's peak memory is a row group rather than the whole file. A save of an unchanged store is still byte-identical.
  • free_ranges: the footer gains a sorted list of data-region ranges no row group references (empty today; the append-only checkpoint fills it). Readers parse it, range-check it and otherwise ignore it.

Wave 135 (steps a–d) — pipelines, string keys, big GROUP BYs ✅

QuackLab's mart refresh SELECTs run 1.5–2.9× faster than after wave 140, and the refresh's peak memory fell by about a third. Results are unchanged.

  • Pipelines: aggregates and every other query root now push chunks through filters, projections and join probes (inner, left, right, semi, anti, mark) in parallel without materializing intermediate join results. SET pipeline_execution = false runs the previous executor, for comparison.
  • VARCHAR join and GROUP BY keys of up to 12 bytes are hashed and compared as their 16-byte string views, without touching the string bytes.
  • COALESCE is evaluated a vector at a time.
  • GROUP BY with millions of groups merges per-chunk partial tables without copying their keys and without a final sort: 17–21 % faster on QuackLab's 1.9M-group fact roll-up, 250 MB less memory.

pinkdb opens the DuckLakes stock DuckDB writes and writes ones DuckDB reads, with QuackLab's own attach sequence.

  • ATTACH 'ducklake:…' with sqlite:, postgres:<conninfo> and postgres:postgresql://… catalogs and DuckLake's options (DATA_PATH, READ_ONLY, SNAPSHOT_VERSION, CREATE_IF_NOT_EXISTS, DATA_INLINING_ROW_LIMIT); options pinkdb lacks are refused by name.
  • Secrets: CREATE [OR REPLACE] [PERSISTENT | TEMPORARY] SECRET for s3, r2, gcs and postgres, DROP SECRET, duckdb_secrets(), which_secret(). Lake data, read_csv/read_parquet over s3:// and Postgres catalogs use the matching secret. A password in an ATTACH string is kept as a secret; no secret value reaches the WAL, statement history, SHOW or errors.
  • Reading DuckDB's lakes: catalog versions 1.1-dev1 to 1.3, DuckLake's path rules (including absolute paths), Parquet delete files and inlined deletes.
  • Writing for DuckDB: the catalog tables have DuckDB's exact columns and types, and ducklake: lakes write Parquet data and delete files (server feature parquetlake).
  • DuckLake's functions in SQL: ducklake_snapshots, table_info, list_files, table_changes / insertions / deletions, options, settings, current_snapshot, last_committed_snapshot, and CALLs for flushing inlined data, expiring snapshots, compaction, cleanup, set_option (including CALL db.set_option(…)) and commit messages. The CLI's matching .lake dot-commands are gone.

Wave 126a — decimal literals typed like DuckDB ✅

1.5 is now DECIMAL(2,1), as in DuckDB, instead of DOUBLE, so arithmetic with decimal columns keeps DuckDB's types and exact values: x - 1.5 over a DECIMAL(15,2) column is DECIMAL(16,2), 0.1 + 0.2 is 0.3, and unaliased column names keep the literal as written ((10 / 4.0)). Literals with an exponent (1e3) or more than 38 digits stay DOUBLE; array literals keep DOUBLE elements. Filters against a column convert the literal once, so queries run as fast as before.

Wave 140 — QuackLab's ETL hot spots ✅

QuackLab's ETL on its NYC-taxi benchmark (local storage) went from 68 s to 1.8 s for the 1.87M-row initial batch (DuckDB: 2.2 s on the same machine), from 43 s to 1.5 s for the next batch and from 15 s to 1.4 s for a one-row correction. Results are unchanged.

  • Foreign-key checks over a UNION: a correlated EXISTS, NOT EXISTS, IN or scalar subquery whose body reads a derived table (a UNION, UNION ALL, DISTINCT, a projection, a GROUP BY on the correlated key) now runs as a join instead of once per outer row. QuackLab's staging check over 1.92M rows: 5 s → 7 ms.
  • MERGE matches with a hash table, evaluates ON, the clause conditions and the SET / INSERT values a chunk at a time, skips target chunks that cannot match, and writes in bulk. One source row into 1.92M rows: 6.6 s → 0.09 s; 960k matched rows: 45 s → 0.7 s; 1.92M inserts into an empty table: 0.24 s. UPDATE … FROM and DELETE … USING probe the same way.
  • CREATE TABLE … AS SELECT and INSERT … SELECT append whole column vectors instead of one row at a time (1.92M × 18 columns: 1.5 s → 0.06 s).
  • Fixed: RETURNING, a data-modifying CTE and a REFERENCING transition table failed with "vector overflow" past 2048 rows.

Wave 139 — QuackLab leftovers: defaults, uuid(), TEMP tables ✅

QuackLab's golden fixtures now run with their column defaults as written (117 of 117, no workaround left in the harness).

  • Column defaults are expressions, evaluated for every row that takes them: DEFAULT now(), DEFAULT uuid(), DEFAULT 'now()' (which, as in DuckDB, creates fine and fails at insert), the DEFAULT keyword in VALUES and UPDATE … SET, INSERT … DEFAULT VALUES, and ADD COLUMN … DEFAULT per existing row. information_schema.columns shows the written expression.
  • uuid(), gen_random_uuid() and random() in writes, replayed exactly after a crash: each statement's values come from a seed recorded in the WAL.
  • A UUID type, with DuckDB's text forms, ordering, Parquet encoding and DuckLake type name.
  • CREATE TEMP TABLE: per-session, never persisted, found before persistent tables of the same name, as in DuckDB. A durable local write that reads one is refused; loading a lake from one is allowed.
  • Fixed: now() inside a procedure body, DO block or trigger action did not replay with its original instant; x IS NOT NULL and similar expressions are now named as in DuckDB.
  • Formats: .pink footer version 5, wire protocol 15.
  • LIST and STRUCT are scoped in docs/nested-types-plan.md, not built: QuackLab's SQL uses neither.

2026-10-30#

Wave 129 — QuackLab's DuckDB dialect ✅

pinkdb now runs every statement of QuackLab's golden fixtures that DuckDB runs (114 of 114, up from 56), given schemas and three-part names — those are their own wave.

  • Fixed wrong results: COUNT(*) FILTER (WHERE c …) over a subquery whose only use of c is the filter failed with column 0 out of range.
  • Stars: *, t.* and db.t.* may sit anywhere in the SELECT list, including a derived table's s.*, and take EXCLUDE (…). A selected t.x is named x, so a view or derived table over it exposes x.
  • DDL: column DEFAULT in CREATE TABLE (a constant, evaluated once); CREATE OR REPLACE TABLE / VIEW. CREATE TEMP TABLE is refused with a reason.
  • DML: DELETE FROM t AS alias; INSERT, UPDATE and MERGE apply DuckDB's assignment casts ('1.5' into DOUBLE, 2.5 into VARCHAR, 2.4 into BIGINT).
  • Literals and clocks: TIMESTAMP '2026-01-01'; CURRENT_TIMESTAMP, CURRENT_DATE, now(), today() — one instant per transaction, recorded in the WAL so a replay reads the same instant.
  • Functions: string_agg, median, quantile_cont(x, p) / quantile_disc(x, p), contains, uuid() / gen_random_uuid() (read queries only), and the range() / generate_series() table functions (integers, or timestamps by an interval). PIVOT … ON … [IN (…)] [USING …] [GROUP BY …], as a statement or a subquery.
  • read_csv takes name = value options and reads gzip files (compression = 'gzip' or a .gz path).
  • The string extension (split_part, regexp_*, starts_with, …) is linked into the CLI by default, and the server now links json, datetime, math and string too. An INTEGER argument widens into an extension's BIGINT parameter (split_part(s, ',', 1)) and a DATE into a TIMESTAMP one (dayofweek(d)).
  • QuackLab's DSL functions: regexp_matches(s, p) and regexp_extract(s, p [, group]) take DuckDB's short forms; regexp_replace, lpad, rpad, concat_ws, dayofmonth, weekofyear and date_diff / datediff are new.

Wave 124c — databases and lakes in the console ✅

  • The Storage page lists every database with its storage (local, lake, lake · read-only), location, lake version and status, and gives administrators New database (local, or a lake — managed under the data directory, or with a catalog and data location), Attach lake (read-only or writable) and Detach (the lake keeps its data). Each dialog shows the SQL it runs.
  • The catalog tree marks lake databases, and an unavailable lake says why.
  • /api/catalog returns each database's storage, location, read_only, version and status.

Wave 124b — the server owns its data ✅

  • A data directory. pinkdb-server keeps everything in --data-dir (default ./pinkdb-data, created on first start): pinkdb.pink (local databases, users, grants, the lake databases' locations), state.pink (console worksheets, credentials, agent, memory), lakes/ (lakes CREATE DATABASE … (TYPE LAKE) makes) and tmp/ (upload staging). --in-memory saves nothing. --file, --catalog, --data and --state are gone: a lake is a database now (see 124a), and the server serves many of them.
  • Lake location policy. A local lake path must be inside <data-dir>/lakes/ or a --lake-root DIR (repeatable; .. and symlink escapes are refused); remote catalogs are postgres:///pink+s3://, remote data s3://; creating, attaching and detaching lakes needs ADMIN. Every server build opens pink: lakes; the catalog-backend features add SQLite, Postgres and S3.
  • Graceful shutdown. SIGINT/SIGTERM stop accepting connections, checkpoint both stores and release the lakes' leases; a killed server's lakes reopen once their lease goes stale.
  • Docker: PINKDB_DATA_DIR (default /data) replaces PINKDB_FILE; make console keeps its data directory in .dev/data.

Wave 124a — lake databases ✅

  • A lake is a database. CREATE DATABASE events (TYPE LAKE [, CATALOG '…'] [, DATA '…']) creates a lake and ATTACH 'lake:<catalog>' AS name [(READ_ONLY, DATA '…', VERSION n)] opens an existing one; DETACH name forgets it (the lake keeps its data). The lake's one schema is the database (main.t in the lake is events.t); a lake with several schemas is refused. CREATE DATABASE … (TYPE LAKE) with no CATALOG puts the lake under the store's lake directory.
  • Writable lake databases publish every commit. Each committed statement or transaction on a writable lake database is one lake version — its data files plus the database's engine metadata (constraints, defaults, indexes, macros, triggers, procedures, materialized views) — and holds the lake's lease: a second writer is refused until the first detaches or its heartbeat goes stale. A read-only one answers from the lake's statistics.
  • A statement or transaction writes one storage — the local store or one lake — never both; a trigger or CALL that tries is undone. A local write that reads a lake records the lake version it read in the WAL, so INSERT INTO local SELECT … FROM lake replays exactly after the lake moved on.
  • Durable stores keep their lake databases. The checkpoint records each database's storage (.pink footer version 3: older files are refused as written by an older pinkdb) and the WAL the ATTACH/DETACH statements; a reopen reopens the lakes. A lake that cannot be opened is listed as unavailable with the reason, and the store still opens.
  • SHOW DATABASES gains storage, location (passwords masked), read_only, version and status; pinkdb_catalog() has one DATABASE row per database with the same facts. pinkdb_lake_decodes() reports a read-only lake's data-file decodes. A lake URL with a password is refused (use PGPASSWORD / AWS_*).
  • CLI: .lake attach, .lake detach, .lake attached and .lake commit are gone — use the SQL above (a writable lake database commits by itself). PINKDB_KEY is every lake's key; the maintenance commands refuse a lake a writable lake database holds.

  • The console falls back to an existing database when the one it was using is dropped (the catalog no longer fails on a database the browser still names).

Wave 121d — sign-in for the console ✅

    The optimizer now knows what is in a table, and a hash join can tell the scan under its probe side which rows cannot match. No query result changed; every answer is checked against DuckDB's rows.

    Wave 120 — correlated subqueries ✅

    Wave 107a — the fixed-size ARRAY type ✅

    • The type. A column can now be FLOAT[N]/REAL[N], DOUBLE[N], INTEGER[N] or BIGINT[N]. FLOAT[N] is a real 4-byte element kind — an embedding column costs 4 bytes per element — and since pinkdb has no FLOAT *scalar* an element read widens to DOUBLE (the one difference from DuckDB, which returns a FLOAT); the DOUBLE[N] → FLOAT[N] cast follows DuckDB 2.0 (round to nearest, a finite value that would become infinite is an error, underflow is silent, text parses straight to f32). Values are stored columnar — one flat buffer of rows × N elements plus a row validity bitmap, and an element bitmap that exists only when some row has a NULL element — so a 768-d or 1536-d embedding costs no per-row allocation. typeof reports DOUBLE[3] and friends. T[] (a variable-length LIST) is a parse error that names the follow-up wave 107a2.
    • Literals and functions. [1.0, 2.0, 3.0] and array_value(…) build an array per row from any expression (columns included) and infer the element type with the numeric tower; [1, 2.5] is a DOUBLE[2]. Element access a[i] and array_extract(a, i) are 1-based and forgiving (out of range, NULL index, NULL array and NULL element all give NULL); len and array_length report N and NULL for a NULL array. Casts run VARCHAR ↔ ARRAY, ARRAY ↔ ARRAY (same length, element type may change) and ARRAY ↔ VARIANT, plus TRY_CAST; a size mismatch is an error that says the size is part of the type.
    • Semantics. Structural equality across element types, with NULL elements comparing structurally (two NULLs at one position are equal); element-wise lexicographic ordering with a NULL element after every value and a NULL array last, shared by ORDER BY, MIN/MAX, GROUP BY/DISTINCT and join keys through a canonical hash key that folds -0.0/0.0 and every NaN.

    Wave 101b — VARIANT in Parquet, shredding and path statistics ✅

    • Shredding. A VARIANT column now splits into typed sub-columns: a metadata dictionary shared by the whole row group, a residual value buffer, and a typed_value group with one column per shredded object path. The policy is inferred per column over all of its rows — a key is shredded when it appears in at least 32 rows and in at least half of them, every occurrence carries the same primitive kind (BOOLEAN, BIGINT, DOUBLE, VARCHAR, DATE, TIMESTAMP), and at most eight keys qualify, most frequent first. Present-but-null keys and every other shape stay in the residual, so {} and {"a": null} remain distinct, and the reader reconciles both buffers exactly.
    • Parquet VARIANT. COPY … TO '….parquet' and read_parquet no longer refuse VARIANT: the writer emits the specification's Variant logical type (specification version 1) and the reader accepts it, including a per-row metadata dictionary and partially shredded files. DuckDB 2.0 reads a pinkdb file and pinkdb reads a DuckDB file; the interop test runs both directions and is skipped when the DuckDB binary is absent.
    • Path statistics and pruning. Every shredded path gets exact min/max and null-count statistics, keyed the way DuckDB spells a path ("a", "user"."id"). So WHERE payload['a'] = 5 or variant_extract(payload, '$.a') = 5 skips files whose bounds exclude the value in .pink and Parquet lakes alike. A SQL catalog stores those facts in DuckLake's own ducklake_file_variant_stats table — one row per summed path per data file, written in the same catalog transaction as ducklake_file_column_stats and deleted with the file by expire and cleanup, on pink:, sqlite: and Postgres catalogs. DuckDB 2.0 attaches a pinkdb-written lake and reads the rows, and pinkdb prunes on rows DuckDB wrote; both directions are tested. Parquet row groups prune too, from the shredded leaves' own statistics, which are trusted only for files whose footer declares the shredding complete (pinkdb.variant.complete).

    Wave 95c — SQL dialect completeness, batch 3 (query forms) ✅

    • LATERAL and comma-separated FROM. FROM a, b is a cross join in the same left-deep list as JOIN, so FROM a, b JOIN c ON a.x = c.z binds like DuckDB. LATERAL (SELECT …) may sit in the head position, after a comma, or after any JOIN (including CROSS JOIN LATERAL and LEFT JOIN LATERAL … ON true). pinkdb binds derived plans without an outer scope, so a lateral subquery that references a column of an earlier FROM item is refused by name instead of silently returning the uncorrelated answer.
    • Ordered-set aggregates. percentile_cont/quantile_cont, percentile_disc/quantile_disc and mode with WITHIN GROUP (ORDER BY …), FILTER before or after the WITHIN GROUP clause, and the DuckDB result types (a DECIMAL percentile stays DECIMAL, an integer one becomes DOUBLE, percentile_disc/mode keep the input type, empty input is NULL, ties in mode pick the smallest value). A non-constant fraction, a missing WITHIN GROUP, or OVER () on an ordered-set aggregate are named errors.
    • TABLESAMPLE / USING SAMPLE with DuckDB's methods — bernoulli, system, reservoir — for n ROWS and n PERCENT, plus REPEATABLE (seed). Sampling is deterministic under a seed (pinkdb's own SplitMix64 stream, so the same seed picks different rows than DuckDB but the same rows every run); a discrete count with bernoulli/system is refused with DuckDB's message. USING SAMPLE 2 ROWS REPEATABLE(7) (no method) is accepted as a superset of DuckDB, which needs the parenthesised method form.
    • Window FILTER and windows built on windows. agg(x) FILTER (WHERE …) OVER (…) skips non-matching rows frame-relatively (DuckDB's answer, NULL where nothing matches); a non-aggregate window function with FILTER is refused by name. WINDOW w AS (…) definitions can now build on an earlier window (OVER (w ORDER BY …), WINDOW v AS (w ROWS 1 PRECEDING)), with DuckDB's merge rules: the base's PARTITION BY/ORDER BY are inherited, a derived clause may fill a gap but not override one, and copying a base that has a frame clause is an error.
    • Row constructors. ROW(a, b) and (a, b) compare field-wise in =, <>, <, <=, >, >= and work as the left side of IN (…) with a value list. DuckDB's semantics are reproduced exactly: row comparison treats NULL as an ordinary value ((1,NULL) = (1,NULL) is true, NULL sorts greater), while IN (SELECT …) keeps three-valued logic. A standalone row and (a, b) IN (SELECT …) are refused by name (pinkdb has no STRUCT type and its IN probe is single-column).
    • AT TIME ZONE and timezone(zone, ts). Folded into one function. pinkdb timestamps are naive and it has no time-zone database, so a UTC-family zone (UTC, GMT, Z, Etc/UTC, +00:00) is the identity on a TIMESTAMP (a DATE/VARCHAR is cast first) and any other zone is refused with a message naming the missing time-zone database.
    • JSON mutation functions. json_set, json_insert, json_replace and json_remove are engine functions with DuckDB's path semantics (missing parents are created, json_insert never overwrites, json_replace never creates, an array index past the end is ignored, $ is the whole document, $."quoted key" works, any NULL argument gives NULL). They accept JSON text or a VARIANT and return the same kind, and a VARIANT value argument needs no ::JSON cast — a documented superset of DuckDB, whose signatures require JSON.
    • Session variables. SET VARIABLE name = <expr>, getvariable('name') and the $name shorthand. The value is spliced at bind time, so a later statement sees it (a variable set inside a multi-statement string is visible to the statements after it). getvariable of an unset name is NULL like DuckDB; $name errors, also like DuckDB. The state is per connection, like DuckDB's session: the embedded handle is one session, every network Connection and every served/MCP session its own, so one client's variable is invisible to — and cannot be overwritten by — another's. Variables are never persisted or WAL-logged, and a logged statement may not read one (replay would bind its text against a fresh session), which the binder refuses by name.
    • FOR UPDATE / FOR SHARE stay refused, with a message naming the reason: pinkdb has no row locks and its MVCC already serializes writers. DuckDB 2.0 rejects the clause too.
    • MERGE and UPDATE … FROM now hash-join their equality keys. The ON / WHERE equality conjuncts build a hash table over the source once and probe it per target row (residual predicates still filter), keeping the old nested loop for anything without an equality key. Measured on 10 000 × 1 000 rows, interleaved: MERGE 3.18 s → 0.05 s (~65×), UPDATE … FROM 3.09 s → 0.006 s (~500×); 100 000 × 10 000: 340 s → 0.47 s and 318 s → 0.03 s; 1 000 000 × 100 000: MERGE 4.9 s, UPDATE … FROM 0.28 s (the nested-loop baseline at that size is an extrapolation of ~9 h, not a measurement). TPC-H Q1/Q6 and a group-by/sort query show no change (interleaved A/B, medians equal).
    • Docs, tests, wire protocol. docs/sql-conformance.md gains the full batch-3 matrix (no form left unassigned) and bench/duckdiff.py 40 new cases (376 pass). The conformance suite adds 26 DuckDB-checked cases plus pinkdb-only cases for the forms whose spelling differs, seeded-sampling determinism and session variables. SET VARIABLE reports PINKDB_STMT_SET_VARIABLE in the C ABI and DoneKind::SetVariable (tag 26) on the server wire, which bumps the protocol to v12.

    Wave 95b — SQL dialect completeness, batch 2 (DML) ✅

    • Upserts. INSERT … ON CONFLICT [(cols)] DO NOTHING | DO UPDATE SET … [WHERE …] with excluded.col (the proposed row) and the target table readable in the SET/WHERE; INSERT OR REPLACE (= DO UPDATE over the columns the statement writes, so unlisted columns keep their stored values) and INSERT OR IGNORE (= DO NOTHING for every key). A conflict target must be a declared PRIMARY KEY/UNIQUE constraint — DuckDB's refusal, verbatim — and a duplicated key inside one statement keeps the first input row. ON DUPLICATE KEY UPDATE and REPLACE INTO stay refused by name (DuckDB has no REPLACE INTO either).
    • Keys are enforced now. Wave 103 left PRIMARY KEY/UNIQUE as metadata; ON CONFLICT without enforcement is incoherent, so INSERT/UPDATE/MERGE check every declared key per statement (crates/pinkdb/src/keys.rs: one hash map per statement, built from the table and updated as rows are staged). A duplicate — or a NULL in a primary key, or a multi-row insert whose rows collide with each other — raises DuckDB's message and the statement leaves the store unchanged. UNIQUE accepts any number of NULLs; REFERENCES stays a declaration (DESCRIBE/FK→PK join elimination only). Cost, measured: 1 M-row INSERT … SELECT into a PK table 0.095 → 0.381 s (median of five, ~3.5 M keys/s); a bulk UPDATE that does not write a key column and a DELETE are unchanged.
    • UPDATE … FROM / DELETE … USING. The source is bound before the target, so FROM/JOIN columns come first in expressions. Several source rows matching one target row: UPDATE … FROM keeps the last one in source order (DuckDB's answer — no error, unlike Postgres), DELETE … USING deletes once.
    • RETURNING on INSERT/UPDATE/DELETE, on ON CONFLICT (scalar subqueries in the projection included) and on MERGE. The rows come from the write funnels, so they are the final image: a BEFORE row trigger's rewrite of NEW is what RETURNING reports, and a DELETE reports its rows in scan order. An ON CONFLICT action that stores the values already there still counts as affected, like DuckDB.
    • MERGE INTO … USING … ON … with WHEN MATCHED [AND …] THEN UPDATE SET … | DELETE, WHEN NOT MATCHED [AND …] THEN INSERT [(cols)] VALUES (…), WHEN NOT MATCHED BY SOURCE [AND …], first matching clause wins, a target row affected by more than one source row refused with DuckDB's "cannot affect the same target row more than once" and the statement atomic. The source is materialized once; matching is a nested loop (a shortcut: comment documents a hash join as the upgrade path).
    • Data-modifying CTEs. WITH x AS (INSERT/UPDATE/DELETE … [RETURNING …]) SELECT … FROM x: the body runs once, at the top level (a nested one is DuckDB's "must be at the top level" error), and its rows are served from an in-memory hand-off (db.dml_cte_outputs) because the evaluator holds the store immutably. COPY as a CTE step stays refused (it is ADMIN-gated as a statement; a CTE step would bypass that gate).
    • AST, parser, binder, plan, executor, EXPLAIN. Statement/LogicalPlan carry conflict/returning/from/using, plus LogicalPlan::Merge and a CteBody::Dml CTE body; the AST walkers (depth guard, parameter renumbering) recurse into all of them; EXPLAIN prints the conflict action and the MERGE clauses.
    • Durability. The WAL logs each statement's SQL text, so every new form replays by re-execution. crates/pinkdb/tests/dml_replay.rs writes upserts, MERGE, UPDATE … FROM, DELETE … USING and a DML CTE, drops the process without a checkpoint, reopens (replay) and compares; then checkpoints and reopens again.
    • Privileges and the MCP.     Wave 100 — Triggers ✅

    • Triggers. CREATE [OR REPLACE] TRIGGER name {BEFORE|AFTER} {INSERT|UPDATE [OF col, …]|DELETE} [OR …] ON table [REFERENCING OLD TABLE AS o NEW TABLE AS n] [FOR EACH {ROW|STATEMENT}] [WHEN (cond)] EXECUTE {PROCEDURE p(args) | <statement>}, DROP TRIGGER [IF EXISTS] name [ON table] and SHOW TRIGGERS [ON table]. Bodies run through the stored procedure machinery (ParamSlots + run_call_statement), so each body statement is bound, optimized and executed like any other statement.
    • Semantics. Triggers of one event fire in creation order; every BEFORE trigger runs before the row change and every AFTER trigger after it. OLD.col / NEW.col are available in WHEN and in the body; a BEFORE ROW trigger may assign NEW.col (the assignment is coerced to the column type and the written value is what lands in the table), OLD is read-only, and there is no row-skipping signal in v1 — returning from a BEFORE ROW trigger always lets the change through. REFERENCING OLD TABLE / NEW TABLE are readable relations (ordinary CTEs to the body, so any query shape works) and are accepted on AFTER STATEMENT triggers only. UPDATE OF narrows to the columns the statement assigns. Recursion is bounded at 16 levels with a clear error; a trigger error rolls back the whole firing statement, including in autocommit.
    • Replay. The WAL still logs the firing statement and nothing else, so a replay re-executes it and the triggers fire again exactly once; a trigger is never logged separately, which is what keeps replay from double-counting. Volatile extension functions are already refused in logged statements, so bodies are deterministic; now()/random() are not builtins in pinkdb.
    • Persistence. Definitions live in a new .pink footer section under flags bit 0x80, written as their CREATE TRIGGER text in creation order so a reopen reproduces the firing order. A file without the bit has no triggers; no old format is read or converted.
    • RBAC. Creating or dropping a trigger needs CREATE on the database — the same requirement as ALTER TABLE and the index DDL. Bodies run with invoker rights: every body statement is re-checked against the firing user, so a low-privilege user cannot use a trigger to write a table they cannot write. SHOW TRIGGERS is a metadata read available to any user.
    • Interactions. Trigger-written tables join the statement's MVCC touched set (a concurrent writer conflicts instead of silently losing), materialized views refresh for triggered changes like any other change, and .lake commit of a writable attachment publishes trigger effects with the rest of the session's writes. Trigger definitions are not carried into a lake (it stores data).
    • Refused, clearly. Triggers on views, on attached lake tables, on a missing table, REFERENCING on a ROW trigger or a BEFORE trigger, unknown UPDATE OF columns, and RETURNING on a triggered table (pinkdb has no RETURNING). CREATE/DROP TRIGGER inside a transaction is refused like the other catalog DDL.
    • No cost without triggers. The DML fast path is untouched: the trigger check is one empty-slice lookup and the batch insert/update/delete code is byte-identical when a table has no triggers. 1,048,576-row INSERT … SELECT 34.4–34.8 ms (HEAD 34.1–34.3 ms) and bulk UPDATE 19.9–20.4 ms (HEAD 20.3–20.5 ms) — both within run-to-run noise.

    • Both bindings gained idiomatic prepared-statement APIs over the FFI: Python db.prepare(sql) → Statement.execute(*params), Go db.Prepare(sql) → Stmt.Execute(args...) — typed parameters, NULLs, reuse and clean close semantics, with native error strings passed through unchanged.
    • No C-ABI changes; the bindings also caught up on the RBAC result kinds (17–23). Python 56 tests, Go 38 (with -race).

    Wave 56 — core datetime extension ✅

    • Ten DuckDB-pinned datetime functions over naive DATE/TIMESTAMP: strftime, strptime, epoch/epoch_ms, dayofweek/dayofyear/week, last_day, age, make_date — hand-rolled civil-date and format engines, zero new dependencies.
    • The extension ABI gained an additive INTERVAL value type so age returns a real interval; datetime joins json as a default CLI feature (--no-default-features for lean). +40 KB on the default binary.

    Wave 53 — core string extension ✅

    • Ten DuckDB-pinned string functions built with the Rust SDK: split_part, reverse, left/right (now parse unquoted), strpos, starts_with/ends_with, regexp_extract, regexp_matches, plus pinkdb's regexp_match (a pinned divergence — DuckDB has no such function) with DuckDB's full option surface.
    • trim/ltrim/rtrim/replace stay core built-ins (extensions can't shadow them). Loaded at runtime; the default CLI binary grows 0 bytes.

    Wave 52 — core json extension ✅

    • Six DuckDB-pinned JSON functions over VARCHAR — json_extract, json_value, json_valid, json_array_length, json_object, json_array — with a hand-rolled parser (zero new dependencies) that matches DuckDB on the messy corners: trailing commas, NaN/Infinity, duplicate keys, canonical number rendering, escapes.
    • json is a default CLI feature (--no-default-features for the lean binary); the functions register through the linked registry, so durable replay resolves them automatically.

    Wave 51 — Rust extension SDK + volatile flag ✅

    • New ext-sdk/rust: declare an extension once (pinkdb_extension!) and get both the native ABI v1 cdylib exports and the wasm/all-target linked registration from safe Rust — typed args, Option NULLs, Result errors, no unsafe in author code.
    • Additive ABI v1 volatile flag: functions can declare themselves nondeterministic, and the engine refuses to call them in any statement it WAL-logs (replay could diverge) with an explicit error; deterministic extensions are unchanged.
    • Fixed: the SDK's ABI exports (pinkdb_extension_abi_version / _name / _init) are now opt-in — pinkdb_abi_exports!() (or the abi-exports feature for dual-artifact crates, as extensions/string does) — because emitting them from linked-only extensions caused duplicate symbols on Linux linkers. Cdylib authors add the macro; linked-only crates need nothing.

    Wave 50 — performance pass ✅

    • High-cardinality GROUP BY / COUNT(DISTINCT) got a typed fast path (no per-row values, chunked output, adaptive one-shot reserve): group_id 15.8 → 4.4 ms and distinct_id 15.6 → 4.6 ms — both now ahead of the DuckDB reference on the same corpus.
    • Byte-slice hashing went word-wise: distinct_lowcard 3.8 → 3.1 ms and join_probe 5.3 → 4.6 ms.
    • Standing battery total 101.5 → 75.7 ms (−25%); all correctness gates unchanged.

    2026-10-18#

    Wave 48 — RBAC: users, roles and enforced grants ✅

    • New users and roles hashed with Argon2id: CREATE USER/CREATE ROLE, GRANT/REVOKE (table SELECT/INSERT/UPDATE/DELETE, database CREATE, global ADMIN), persisted in the catalog + WAL — plaintext passwords never hit disk.
    • The network server gains session login (protocol v9) and per-statement enforcement: an empty catalog trusts connections with a loud startup warning; once a user exists every statement is checked against their grants. Embedded, FFI and wasm use stays trusted by design.
    • Remote CLI gains --user/--password (or PINKDB_PASSWORD); without the tls feature, login passwords cross the wire in cleartext — documented.

    Wave 49 — extensions on wasm ✅

    • Extensions now work on every target through a new linked registration model: extensions register through a safe-Rust API and feed the same engine registry as native ABI v1 extensions. On wasm (where dlopen cannot work), LOAD EXTENSION '<name>' resolves a registered name; unknown names fail with an actionable error.
    • The JS / wasm-bindgen host contract is pinned — surface, SQL↔JS value mappings and sandbox rules, documented in docs/wasm-extensions.md — with no new dependencies added.
    • Native CLI grows ~3.7 KB; the wasm dependency tree gains nothing.

    Wave 46 — network server TLS ✅

    • Opt-in tls feature: the server serves the same protocol over rustls-encrypted TCP (--tls-cert/--tls-key), and the CLI's remote mode gained --tls, --tls-ca-cert and --tls-insecure. Certificate problems refuse startup with precise messages; handshake failures never disturb the accept loop; the default build and dependency graph are unchanged.
    • Still no authentication — TLS encrypts the transport only, which the docs and startup warning state explicitly.

    Wave 47 — async I/O at the boundary ✅

    • pinkdb-server gains an opt-in async-server transport: a tokio listener with one task per connection, engine calls on the blocking pool, and byte-identical protocol frames to the synchronous server (same client works unchanged). --transport sync|async.
    • The "zero async" rule now has its documented carve-out: async lives only at the server I/O boundary — the executor, storage and WAL stay synchronous — and the default build links no runtime (+0.38 MB only with the feature).

    Wave 82 — Rust toolchain upgrade ✅

    • All crates now require Rust 1.97 and compile as edition 2024; CI's MSRV job pins 1.97 (was 1.89 core / 1.95 pink-lake), and the wasm check passes again.
    • Modernized the code where the new edition/compiler asks for it — let-chains (~60 collapsed conditionals), unsafe(...) attribute syntax, reserved gen renames — with semantics unchanged (duckdiff still 171/171).

    Wave 44 — stored procedures ✅

    • SQL procedures: CREATE [OR REPLACE] PROCEDURE p(a INTEGER, …) AS $$ … $$ (typed DECLARE/SET, IF/ELSIF/ELSE, WHILE, nested blocks, RETURN, RAISE), DROP PROCEDURE [IF EXISTS], CALL p(args) — parameters and variables are bound as values, never spliced SQL, so injection-shaped input is inert by construction. CALL is statement-atomic, works in transactions, is persisted per database and replays exactly from the WAL.
    • JavaScript procedures: the sandbox contract ships (pinkdb-js: host API, denied-intrinsics determinism policy, conversions) with a clean refusal — the engine binding (quickjs-ng, ~1.1 MB) is the queued follow-up (wave 81).

    Wave 74 — lake naming sweep ✅

    • The lake builds are now pinklake (the .pink-file lake; formerly lake-lite) and lake (the full lake; later removed), in cargo features, help text, tests, CI, README and the docs site.
    • s3 is pure storage: it implies no lake build — combine it explicitly (pinklake,s3; --features s3 alone has no .lake commands and says so). No old aliases survive.

    Wave 80 — materialized-view refresh policies ✅

    • Manual: REFRESH MATERIALIZED VIEW name (and REFRESH name, plus REFRESH MATERIALIZED VIEWS refreshing every view of the database all-or-nothing); SHOW MATERIALIZED VIEWS lists schedule, last refresh time/count and staleness.
    • Scheduled: CREATE MATERIALIZED VIEW v REFRESH MANUAL | EVERY INTERVAL '5 minutes' | ON COMMIT AS SELECT … — enforced daemonless at statement boundaries (embedded and pinkdb-server alike; never mid-transaction), with automatic refreshes WAL-logged and replay-exact.
    • Fix: MV definitions are now WAL-logged and persisted — previously a durable reopen silently lost them.

    Wave 68 — inlined small writes & CDC ✅

    • Tiny commits (≤ 10 rows by default; per-table limits, PINKDB_LAKE_INLINING_ROW_LIMIT) live in the catalog metadata instead of new data files — scans, stats, time travel, partitions and encryption all see them correctly. .lake flush materializes them into real files and keeps the history.
    • CDC reads: .lake changes (and the library's table_insertions/table_deletions/table_changes) replay each version's deltas as snapshot_id/rowid/change_type rows. Updates read as delete + insert (documented).
    • .lake add_data_files registers existing lake files into a version with exact schema and statistics checks — encrypted lakes included.

    Wave 42 — hash indexes ✅

    • CREATE INDEX [IF NOT EXISTS] name ON t (col) and DROP INDEX [IF EXISTS] name (per-database): a single-column hash index turns col = literal lookups into an IndexScan instead of a full scan — results are identical either way. .pink persistence is queued as the follow-up (wave 79).

    Wave 43 — materialized views ✅

    • CREATE MATERIALIZED VIEW … AS SELECT, REFRESH [MATERIALIZED VIEW] (full recompute) and DROP MATERIALIZED VIEW [IF EXISTS]: stored as a queryable table plus its refresh query, per-database, WAL-logged and persisted.

    Engine fixes and performance

    • Bug-review remediation: server ETag validation, both FFI result-building paths guarded, VARCHAR string-offset-limit refusal, attach row-count re-checks. Performance: COUNT(*) dead-work elimination and fast DISTINCT for integer/date/timestamp keys.

    Bug-review remediation — P1 + P2 ✅

    • P1 (12) — Window filter pushdown (wrong ranks), mixed-operand JOIN keys (panic), ALTER … DEFAULT depth/parameter guards, JOIN/UNION plan depth, RANGE-frame NULL keys, plaintext WAL mid-file corruption (silent data loss), atomic + guarded save, legacy-head lake commits (unreadable catalog), delete-file count overflow, plaintext staging copies, and the server's ExecutePrepared / Rows allocation caps.
    • P2 (engine) — || on the right of =/LIKE/BETWEEN, SELECT-alias shadowing within one list, set-op NULL arms, checked decimal/temporal overflow, an optimizer index guard, INTERVAL hashing, lazy CASE/COALESCE, WAL directory fsync + checked LSN/decoders, the COMMIT conflict set, and unsupported WAL container versions.
    • P2 (lake/S3/CLI/server/bindings) — monotonic lake schema_version, partition error names, container-version classification, conditional-retry guard, SigV4 whitespace, CLI fail-closed key/backoff/partition guards, loopback parsing, atomic + Windows-safe repo files, terminal-escape output escaping, checked prepared handles, an FFI unwind guard, DECIMAL/INTERVAL/ ALTERED_TABLE in the Python and Go bindings, a client batch cap + socket timeouts, off-thread over-limit rejection, and documentation drift.
    • No deferred items: the last two (a .pink VARCHAR chunk over the u32 string-offset limit is refused at serialization; attach recomputes the row count from the deduped delete layout) are fixed too.

    Wave 67 — lake maintenance ✅

    • Compaction: merge_adjacent_files publishes one new version referencing consolidated files — groups of delete-free files sharing partition values and schema epoch (≥2 members) merge into one; source files are never touched (bytes and mtimes pinned by tests) and row counts/zone maps stay exact. rewrite_data_files materializes deletes above a threshold.
    • Retention: expire_snapshots removes old snapshots + commit deltas (explicit versions, older_than, or retain_last — never the current version); cleanup_old_files / delete_orphaned_files delete only unreferenced data/ objects, behind a 2-day age gate and an explicit dry-run/confirm; encrypted lakes included.
    • Introspection: .lake files / table_info / options / settings (+ merge, rewrite, expire, cleanup, orphans).

    Wave 57 — lake encryption at rest ✅

    • With the encryption feature, a keyed session (PINKDB_KEY, consistent with the engine) seals every lake object — catalogs, snapshots, commit deltas, data files, delete files — as PNKLAKE1 AES-256-GCM containers under one Argon2id derivation per session. A Storage-level decorator means commits, deletes, time travel and retry paths are covered with no per-call-site code.
    • The manifest byte-identity invariant survives (seal once, publish the same ciphertext); S3 conditional-write CAS is unchanged; statistics-fast attach on encrypted lean lakes still decodes zero data files.
    • Wrong/missing keys and tampered containers fail closed with authenticated errors (never “corrupt file”); plaintext lakes stay byte-identical and are refused by keyed sessions. Encrypted lake attach reads whole objects in stage 1 (segment-level reads documented as the follow-up).

    Wave 65 — lake schema evolution ✅

    • ALTER TABLE on writable-attached lake tables — ADD COLUMN … DEFAULT, RENAME COLUMN, DROP COLUMN (plus the engine-wide ALTER TABLE support behind it: defaults, NOT NULL rules, DESCRIBE defaults, WAL replay) — published as metadata-only catalog schema versions (format now v5): old data files are never rewritten; they project through rename chains, missing columns materialize their defaults, and dropped columns keep their bytes (row positions unchanged — delete files stay valid).
    • Time travel reads each version with that version's schema and names; writes across versions keep working through the projection.
    • Limits (documented): RENAME TABLE through a lake commit is refused with a .lake save hint; no ALTER COLUMN TYPE / SET|DROP DEFAULT / ADD CONSTRAINT; read-only attachments refuse ALTER.

    Wave 66 — lake partitioning & pruning ✅

    • Lake tables can be partitioned: identity values or bucket(N) labels are recorded per file, commits write one data file per partition value set, and spec changes (.lake partition … by (…) | clear) never rewrite old files.
    • Every v4 data file publishes a CRC-protected zone map in the catalog; the planner prunes whole files for exact predicates — WHERE region = 'x' reads only that partition's file, and disjoint ranges read zero.
    • COUNT/MIN/MAX honesty rules are preserved (fall back once positional deletes exist); pruning stays correct with deletes and across time travel.
    • Limits (documented): bucket labels are pinkdb's own hash (no cross-engine numbers, no bucket-value pruning); year/month/… transforms are refused by name.

    Wave 73 — docs catch-up, changelog & site wiring

    • New Changelog docs page generated from this file (website/tools/make-changelog.py), linked from the sidebar, footer and roadmap page.
    • CI's docs job now regenerates the changelog fragment + the site and fails on a stale diff — regenerate-and-commit is enforced; website/README.md documents the tooling.

    Wave 63 — incremental lake writes ✅

    • Lake commits now append: each commit writes one new immutable data file per table (with its exact row count in the catalog) and never rewrites a published file — a 1M-row lake committed 4 rows in 7.6 KB / 0.54 s with 0 bytes rewritten (vs a 2.6 MB full save).
    • DELETE / UPDATE write positional delete files applied at read time (merge-on-read); every published version also writes a small commit delta manifest.
    • Writable attached lakes: .lake attach <dir> write, mutate with normal SQL, .lake commit publishes the diff; guarded .lake detach; durable sessions replay commits idempotently after a crash.
    • Concurrent-writer retry with DuckLake's settings and defaults (max_retry_count 10, retry_backoff 1.5, retry_wait_ms 100 — rebase on conflict, bounded, clean failure).
    • Fixes after landing: the feature-less build message and the S3 Docker expectations updated for the new catalog format (format_version 4).

    Wave 64 — lake time travel & snapshot metadata ✅

    • Query any published lake version: SELECT … FROM t AT (VERSION => n) / AT (TIMESTAMP => ts) on attached lake tables, with DuckLake-pinned resolution (timestamp = newest snapshot at or before it, inclusive).
    • Per-version records: .lake snapshots lists time, author, message, (tables, rows) and a change summary; .lake save … author '…' message '…' attaches commit metadata.
    • Statistics fast paths work per version: COUNT/MIN/MAX over an older version decode no data files.
    • ducklake_default_version deliberately not mirrored (probed: it selects a new-catalog storage format, not a read default).

    Wave 41 — primary / foreign keys ✅

    • Declarative PRIMARY KEY / UNIQUE / NOT NULL / REFERENCES in column and table form (CONSTRAINT names; RELY / [NOT] ENFORCED accepted and dropped), validated at DDL time like DuckDB.
    • Constraints are metadata-only — writes never enforce them; DESCRIBE reports PRI/UNI markers and nullability.
    • Optimizer: conservative FK→PK join elimination (declarations are trusted, not verified — documented).
