2026-10-25#

Wave 95b — SQL dialect completeness, batch 2 (DML) ✅

  • Upserts. INSERT … ON CONFLICT [(cols)] DO NOTHING | DO UPDATE SET … [WHERE …] with excluded.col (the proposed row) and the target table readable in the SET/WHERE; INSERT OR REPLACE (= DO UPDATE over the columns the statement writes, so unlisted columns keep their stored values) and INSERT OR IGNORE (= DO NOTHING for every key). A conflict target must be a declared PRIMARY KEY/UNIQUE constraint — DuckDB's refusal, verbatim — and a duplicated key inside one statement keeps the first input row. ON DUPLICATE KEY UPDATE and REPLACE INTO stay refused by name (DuckDB has no REPLACE INTO either).
  • Keys are enforced now. Wave 103 left PRIMARY KEY/UNIQUE as metadata; ON CONFLICT without enforcement is incoherent, so INSERT/UPDATE/MERGE check every declared key per statement (crates/pinkdb/src/keys.rs: one hash map per statement, built from the table and updated as rows are staged). A duplicate — or a NULL in a primary key, or a multi-row insert whose rows collide with each other — raises DuckDB's message and the statement leaves the store unchanged. UNIQUE accepts any number of NULLs; REFERENCES stays a declaration (DESCRIBE/FK→PK join elimination only). Cost, measured: 1 M-row INSERT … SELECT into a PK table 0.095 → 0.381 s (median of five, ~3.5 M keys/s); a bulk UPDATE that does not write a key column and a DELETE are unchanged.
  • UPDATE … FROM / DELETE … USING. The source is bound before the target, so FROM/JOIN columns come first in expressions. Several source rows matching one target row: UPDATE … FROM keeps the last one in source order (DuckDB's answer — no error, unlike Postgres), DELETE … USING deletes once.
  • RETURNING on INSERT/UPDATE/DELETE, on ON CONFLICT (scalar subqueries in the projection included) and on MERGE. The rows come from the write funnels, so they are the final image: a BEFORE row trigger's rewrite of NEW is what RETURNING reports, and a DELETE reports its rows in scan order. An ON CONFLICT action that stores the values already there still counts as affected, like DuckDB.
  • MERGE INTO … USING … ON … with WHEN MATCHED [AND …] THEN UPDATE SET … | DELETE, WHEN NOT MATCHED [AND …] THEN INSERT [(cols)] VALUES (…), WHEN NOT MATCHED BY SOURCE [AND …], first matching clause wins, a target row affected by more than one source row refused with DuckDB's "cannot affect the same target row more than once" and the statement atomic. The source is materialized once; matching is a nested loop (a shortcut: comment documents a hash join as the upgrade path).
  • Data-modifying CTEs. WITH x AS (INSERT/UPDATE/DELETE … [RETURNING …]) SELECT … FROM x: the body runs once, at the top level (a nested one is DuckDB's "must be at the top level" error), and its rows are served from an in-memory hand-off (db.dml_cte_outputs) because the evaluator holds the store immutably. COPY as a CTE step stays refused (it is ADMIN-gated as a statement; a CTE step would bypass that gate).
  • AST, parser, binder, plan, executor, EXPLAIN. Statement/LogicalPlan carry conflict/returning/from/using, plus LogicalPlan::Merge and a CteBody::Dml CTE body; the AST walkers (depth guard, parameter renumbering) recurse into all of them; EXPLAIN prints the conflict action and the MERGE clauses.
  • Durability. The WAL logs each statement's SQL text, so every new form replays by re-execution. crates/pinkdb/tests/dml_replay.rs writes upserts, MERGE, UPDATE … FROM, DELETE … USING and a DML CTE, drops the process without a checkpoint, reopens (replay) and compares; then checkpoints and reopens again.
  • Privileges and the MCP. The per-statement gate sees every table: MERGE needs the privilege of each action its clauses spell out plus SELECT on its USING source, UPDATE … FROM/DELETE … USING need SELECT on the source, a DML CTE's target needs its write privilege, and the read pass walks the CTE body. The MCP read-only policy refuses every new statement kind and a WITH whose body writes (tests in serve.rs).
  • Tests. sql_conformance.rs gained 25 DML cases pinned to DuckDB and re-measured on DuckDB 2.0.0 (the same 25 run in bench/duckdiff.py, 336/336 passing), the error cases, key enforcement, RETURNING after triggers, the DML-CTE EXPLAIN, and MERGE's multiple-match; rbac.rs, dml_replay.rs and serve.rs cover the gates. Gates: clippy clean, workspace 1856 passed / 0 failed (8 ignored), -p pinkdb 855 (6 ignored), -p pinkdb-cli --features pinklake,s3,parquetlake 168, wasm32 build, duckdiff 336/336.
  • No regression for existing DML: interleaved A/B against HEAD 6531691 (own worktree + target dir), five rounds, medians — INSERT INTO t2 SELECT * FROM t 1 M rows 0.095 → 0.381 s (the key check), UPDATE t SET v = v + 1 1 M rows 0.025 → 0.025 s, DELETE FROM t WHERE id % 2 = 0 500 k rows 0.019 → 0.019 s (bench/wave95b_perf/).

Wave 93a — one ABI in four SDKs, one conformance fixture, pinned libraries ✅

  • ABI 1.2, negotiated. The extension header gained the size constants and macros a library uses to ask what the host actually publishes — PINKDB_EXT_API_V1_SIZE, PINKDB_EXT_API_FLAGS_SIZE, PINKDB_EXT_API_MINOR2_SIZE, PINKDB_EXT_HOST_HAS_FLAGS() and PINKDB_EXT_HOST_HAS_EXECUTE() — plus pinkdb_ext_copy_api(), which copies only the bytes struct_size promises (the old g_api = *api read past a smaller host struct). The four vendored copies (ext-sdk/{c,cpp,go,rust}/include/pinkdb_extension.h) are byte-identical to the loader's and tests/header_sync.rs fails cargo test if they drift.
  • C, C++, Go and Rust at the same ABI. All four cover register_scalar_flags and PINKDB_EXT_FLAG_VOLATILE (refusing to register a volatile function on a host too old for the flag, instead of silently calling it deterministic), the full type-tag set including INTERVAL's packed months/days with micros, the init-only host-API copy, the name/arity/tag bounds, host alloc/free text ownership, and execute_statement. The C++ SDK is new (ext-sdk/cpp, header-only pinkdb::ext with a move-only owned Text, a Writer for results and an exception guard), and the copy-pasted Go shims became one package (ext-sdk/go/pinkdb). Table functions, scans and copy sinks are still linked-only, and every README says so.
  • One fixture, four SDKs. ext-sdk/conformance/README.md defines conformance_ext: 15 functions, a canonical cf_all row that renders every tag bit-exactly, cf_fail (publishes text, then fails), cf_unwind (panics/thows) and introspection counters. Each SDK builds it, and the loader drives all four (crates/pinkdb-ext-loader/tests/conformance.rs, 11 tests): tag round-trips with NULL, embedded NUL, empty strings and 64 MiB + 1 results refused, error codes, panic containment (a statement fails and the extension still answers afterwards), 100 callbacks from four foreign threads, and struct_size/abi_version negotiation in a child process (old host → refused non-zero with nothing registered as deterministic; full host → all 15 registered). tests/conformance_ownership.rs checks the host allocates and frees exactly once per VARCHAR result and leaks nothing on empty, NULL or error paths.
  • Local libraries can be pinned. --extension-pin PATH=SHA256 (CLI and server, repeatable) installs a SHA-256 allowlist in the loader: once it is set, every load must match a pin — an unpinned library, a hash mismatch, or a file that changed between the hash and the dlopen is refused with the reason. The hash is read from an open file and the file's (dev, ino, len, mtime) re-checked immediately before mapping; the residual check-then-map window (there is no fdlopen on Linux or macOS) is documented. Local libraries are still unsigned: Ed25519 signatures cover .install packages only.
  • Posture, stated and tested. ext-sdk/posture.sh drives the release CLI through the refusals every README promises: LOAD EXTENSION off unless --allow-load-extension/PINKDB_ALLOW_LOAD_EXTENSION=1, --extension-root confinement, bare names and .. and symlinks refused, pins enforced. CI runs it after the four smokes and the C++ build, with the conformance matrix under PINKDB_CONFORMANCE_STRICT=1 so a missing toolchain fails instead of skipping.
  • 93b is separate: SQL INSTALL still does not exist (only the .install dot-command), and no released CLI enables the repo feature.

  • The matrix first. docs/sql-conformance.md lists every query form row 95 scopes, each checked by running it against DuckDB 2.0.0: supported (same answer), divergent (and how), or refused with the exact error — and each assigned to batch 95a, 95b or 95c. A SELECT 1.e2 regression from the new .field postfix is a parse error again.

Wave 76 — CSV import options ✅

  • One option set, two front ends. .import and read_csv now share pinkdb::csv::CsvOptions, so .import f.csv t sep=';' header=true and read_csv('f.csv', sep := ';', header := true) read a file identically — locally, over https:// and from s3://. Named parameters use DuckDB's names (delimiter/sep/delim/separator, quote, escape, encoding, header, nullstr/null, names/column_names, ignore_errors/errors, allow_quoted_nulls, force_not_null); an unknown or unsupported name is an error naming it, never silently ignored.
  • Dialect. delimiter takes any single byte (a literal tab or the \t spelling), quote any byte, escape a byte or off (the default). A multi-byte delimiter is refused instead of truncated.
  • Encodings. latin-1, windows-1252, utf-16le, utf-16be, and the default utf-8; the default (auto) also strips a UTF-8 BOM and switches to UTF-16 on a LE/BE BOM. The decoders are hand-written and stream — no new dependency — so the wave-98c read-ahead and ranged remote reads keep working and the sniff window never needs the whole file.
  • Header and column matching. header=auto applies DuckDB's rule: infer the types over every row and again over the rows below the first; row 1 is a header when the two disagree or when the data is all text. Importing into an existing table matches columns by header name, case-insensitively: missing columns become NULL, and file columns the table has no home for follow the error policy. names= overrides the header, header=false reads the first line as data (column0, column1, …).
  • NULLs. nullstr='NA,N/A' adds tokens, allow_quoted_nulls=false keeps a quoted empty field as '', force_not_null='a' keeps a column's empties as '' (which widens the column to VARCHAR). The default is DuckDB's measured behaviour, not the folklore: an empty field is NULL whether quoted or not. A quoted cell keeps its own whitespace (only unquoted cells are trimmed), so " x " stays " x " while " 1 " still imports as a number.
  • errors=warn (DuckDB's ignore_errors := true, accepted by that name too) skips bad rows — a value that does not parse, or a row with more fields than the header — and .import prints a rejects report (line, column, reason; the first ten plus a total). A read_csv scan has nowhere to print that report, so a scan skips silently: warn means skip, never "count the bad rows". error stays the default: the first bad row fails the import and leaves no table behind, and the error names the line. Storing rejects in a table remains the recorded follow-up.
  • The csv crate is gone. Wave 75 pulled it in for the record reader; the engine's own streaming reader replaced it and the dependency was left behind, unused, with only PinkDbError::Csv(csv::Error) still naming it. That variant is now pinkdb's own PinkDbError::Csv { message, line, column } (the FFI, agent-JSON and Python bindings keep their stable "csv" error kind, and a structural error now names its line), and csv left Cargo.toml and the lockfile (22 lines). Size of the default release pinkdb binary: 4,524,032 → 4,536,208 bytes (+12,176, +0.27 %), which is the new error payload and formatting, not the dependency — re-adding the unused csv crate to the same tree builds a binary 16 bytes *smaller* (build metadata), so it contributed no code.
  • No import-speed regression. The options layer initially cost 7× on .import (18.2 s for TPC-H lineitem, 773 MB / 6 001 215 rows, against 2.54 s before the wave). Two causes: the type sniff walked the *whole* file through the byte-at-a-time record reader, and the parallel batch parser refused any file containing a ", so any quoted column fell back to it. The sniff is now sample-limited (20 480 rows, DuckDB's sample_size; a column with no value in the sample still triggers the exact pass), and the batch parser understands RFC 4180 quoting — fields are split with the quoting rules, "" unescapes, a quoted cell keeps its whitespace — so a file is parsed in parallel exactly as the record reader would read it — a file the scan cannot prove falls back to the reader rather than being read wrong. Measured with the reviewer's harness, interleaved, median of 3: lineitem 2.54 s → 0.87 s, orders (174 MB) 0.42 s → 0.21 s — twice as fast as before the wave, not just within budget. Slower by design, and measured on the same 773 MB file: errors=warn 12.2 s (the rejects report needs the sequential reader), encoding=latin-1 14.2 s, encoding=utf-16 13.3 s (1.5 GB, BOM autodetected) — transcoding and warn still run through the record reader, which is the recorded next target.
  • read_csv scans share it. A table-function scan parsed with the record reader too (7.4 s for SELECT count(*) FROM read_csv('lineitem.csv') against 5.03 s before the wave). It now runs the same batch parser: a file under the 8 MiB sniff window at once, anything larger — a remote object, or a local file past that window — in 8 MiB windows of the wave-98c prefetch, each window cut at its last provable record end so a record can straddle two windows, and a window the scan cannot prove is finished by the reader. 5.03 s → 1.36 s, and the same 33.9 MB file through the test HTTP server 486 ms → 120 ms (local 522 → 77 ms). Values, not just counts, match .import on lineitem (sum(length(l_comment)), sum(l_orderkey), date bounds, sum(l_quantity)).
  • Unchanged: a sampled column that a later row contradicts still falls back to whole-file inference, and a durable import still checkpoints before it returns. An import that appends to an existing table is atomic too: a strict failure restores the table instead of leaving half the file in it.
  • Tests: pinkdb CSV module 34 (from 19), including a DuckDB-oracle test for the empty-field rule and header auto-detection that skips when the α binary is absent; pinkdb-httpfs 62 (local-vs-remote option parity, errors=warn in a scan); 4 new .import CLI tests; workspace 1865 tests / 161 suites, 9 ignored (one of them the scan speed aid).

Wave 101a — the VARIANT type core ✅

  • The type. VARIANT is now a column type: one column, any shape per row — a JSON null, boolean, integer, double, decimal, string, date/timestamp, array or object. Values live in a binary, self-describing encoding (a kind tag per value plus the payload), not in JSON text, and objects keep their keys sorted so equal objects encode identically. typeof(v) reports 'VARIANT'.
  • Casts. Any type → VARIANT; VARIANT → every scalar, with an error that names the kind and the value (cannot CAST VARIANT(VARCHAR) value "hi" to INTEGER) instead of a wrong answer. '{"a":1}'::VARIANT parses JSON — the literal form the parser, the WAL and prepared statements already carry (this is where we differ from DuckDB, where VARCHAR → VARIANT is the identity and the JSON extension is required first). A JSON null reads as SQL NULL for every target except VARCHAR, which keeps the text null, so VARIANT → VARCHAR → VARIANT is lossless for JSON's value model.
  • Functions. variant_type(v), variant_keys(v) (a JSON array of the keys; pinkdb has no list type yet) and variant_extract(v, path) with 0-based JSONPath ('a.b[1]', '$.a[0]') — a missing path is SQL NULL. The JSON extension's functions (json_extract, json_array_length, …) accept a VARIANT and see its JSON text.
  • Semantics, defined and tested. Equality is structural, with numbers comparing by value across kinds (1 = 1.0 = 1.00, '1' ≠ 1). One documented total order serves ORDER BY, MIN/MAX and range comparisons: bool < number < string < date < timestamp < array < object < JSON null, with SQL NULL last. GROUP BY, DISTINCT and joins hash a canonical key that agrees with = by construction. A JSON null is its own group and is never equal to SQL NULL.
  • Persistence. New .pink dtype tag (9) and default-value tag; a VARIANT column survives save/open, WAL replay, checkpoint and ALTER TABLE … ADD COLUMN … DEFAULT. VARIANT chunks carry no min/max statistics. An older build that meets the new tag reports a clear corrupt file: bad dtype tag 9 — no legacy reader.
  • Encodings elsewhere. Wire protocol v11 (new dtype and value tags; a VARIANT rides as a length-prefixed blob so an old client fails cleanly); FFI PINKDB_TYPE_VARIANT (the JSON text); the JS/WASM binding hands it over as a native JSON value. Refused with clear errors: the extension C ABI (like DECIMAL), the Arrow extension, and Parquet write.
  • Lake. A VARIANT column round-trips in a .pink lake data file; a Parquet-format lake refuses it with a message naming wave 101b rather than writing it as text.
  • Not in this wave. TRY_CAST (does not exist anywhere in pinkdb), DuckDB's variant_extract_string/variant_array_length/variant_exists/ variant_normalize/variant_comparator, array/field subscript syntax (v['a']), and Parquet VARIANT — that is 101b, together with shredding into typed sub-columns and statistics on shredded paths. The plan for it, the full tag table, the semantics and every deliberate difference from DuckDB are written in docs/wave-101-plan.md.

    • Wave 72 — Core extension: iceberg ✅

    • iceberg_scan, iceberg_snapshots, iceberg_metadata in a new engine-adjacent crate, extensions/iceberg (pinkdb-iceberg), behind the opt-in iceberg CLI feature (which turns parquet on — the data files are read by that reader). A table location is the table directory, its metadata/ directory or one …/metadata/vN.metadata.json; a directory is resolved through metadata/version-hint.text, else the newest vN.metadata.json. Paths inside the metadata resolve against the table root, so a copied or mocked table works unchanged — what DuckDB calls allow_moved_paths.

The current snapshot, or one named by snapshot_from_id / snapshot_from_timestamp (DuckDB's names); the manifest list, then the Avro manifests, then the live Parquet data files; positional delete files applied; equality deletes refused by name (a documented follow-up — DuckDB applies them, and the test pins that difference); schema evolution by field id, so a renamed column projects under its new name and an added one reads NULL in files written before it; partition-summary pruning (identity transforms) and lower/upper-bound + NULL-count pruning from the manifest entries; count(*) answered from the manifest record counts without opening a data file.

The remote feature (enabled by the CLI's httpfs feature) reads https:///s3:// tables through pinkdb-httpfs — the same path read_parquet uses — with windowed 256 KiB read-ahead for the metadata JSON and the Avro files, then Parquet's ranged reader for the data. A remote table needs a version-hint.text; without one, pass the metadata file.
    • Fixtures without downloads. extensions/iceberg/tests/fixtures/gen.py writes Iceberg v2 tables with the standard library alone — metadata JSON, an Avro container writer and manifests by hand, Parquet through the DuckDB 2.0 binary — for six tables (two snapshots, positional deletes, equality deletes, a delete file older than the data file it names, schema evolution, partitioned), 232 KB committed. The DuckDB 2.0 α oracle compares every fixture's results (13 query/table pairs) and runs whenever the binary is present; a mock S3 and the local HTTP test server prove the remote path with ranged request counts.
    • Cost: the crate's release rlib is 1,165,120 B; the CLI binary grows 254,560 B over parquet (6,475,744 B with iceberg, 8,626,896 B with iceberg,httpfs) and the default binary is untouched — the crate is not in its dependency graph.

    Wave 100 — Triggers ✅

    • Triggers. CREATE [OR REPLACE] TRIGGER name {BEFORE|AFTER} {INSERT|UPDATE [OF col, …]|DELETE} [OR …] ON table [REFERENCING OLD TABLE AS o NEW TABLE AS n] [FOR EACH {ROW|STATEMENT}] [WHEN (cond)] EXECUTE {PROCEDURE p(args) | <statement>}, DROP TRIGGER [IF EXISTS] name [ON table] and SHOW TRIGGERS [ON table]. Bodies run through the stored procedure machinery (ParamSlots + run_call_statement), so each body statement is bound, optimized and executed like any other statement.
    • Semantics. Triggers of one event fire in creation order; every BEFORE trigger runs before the row change and every AFTER trigger after it. OLD.col / NEW.col are available in WHEN and in the body; a BEFORE ROW trigger may assign NEW.col (the assignment is coerced to the column type and the written value is what lands in the table), OLD is read-only, and there is no row-skipping signal in v1 — returning from a BEFORE ROW trigger always lets the change through. REFERENCING OLD TABLE / NEW TABLE are readable relations (ordinary CTEs to the body, so any query shape works) and are accepted on AFTER STATEMENT triggers only. UPDATE OF narrows to the columns the statement assigns. Recursion is bounded at 16 levels with a clear error; a trigger error rolls back the whole firing statement, including in autocommit.
    • Replay. The WAL still logs the firing statement and nothing else, so a replay re-executes it and the triggers fire again exactly once; a trigger is never logged separately, which is what keeps replay from double-counting. Volatile extension functions are already refused in logged statements, so bodies are deterministic; now()/random() are not builtins in pinkdb.
    • Persistence. Definitions live in a new .pink footer section under flags bit 0x80, written as their CREATE TRIGGER text in creation order so a reopen reproduces the firing order. A file without the bit has no triggers; no old format is read or converted.
    • RBAC. Creating or dropping a trigger needs CREATE on the database — the same requirement as ALTER TABLE and the index DDL. Bodies run with invoker rights: every body statement is re-checked against the firing user, so a low-privilege user cannot use a trigger to write a table they cannot write. SHOW TRIGGERS is a metadata read available to any user.
    • Interactions. Trigger-written tables join the statement's MVCC touched set (a concurrent writer conflicts instead of silently losing), materialized views refresh for triggered changes like any other change, and .lake commit of a writable attachment publishes trigger effects with the rest of the session's writes. Trigger definitions are not carried into a lake (it stores data).
    • Refused, clearly. Triggers on views, on attached lake tables, on a missing table, REFERENCING on a ROW trigger or a BEFORE trigger, unknown UPDATE OF columns, and RETURNING on a triggered table (pinkdb has no RETURNING). CREATE/DROP TRIGGER inside a transaction is refused like the other catalog DDL.
    • No cost without triggers. The DML fast path is untouched: the trigger check is one empty-slice lookup and the batch insert/update/delete code is byte-identical when a table has no triggers. 1,048,576-row INSERT … SELECT 34.4–34.8 ms (HEAD 34.1–34.3 ms) and bulk UPDATE 19.9–20.4 ms (HEAD 20.3–20.5 ms) — both within run-to-run noise.

    • "Empty catalog ⇒ trusted" now applies only to embedded/trusted sessions; an authenticated session whose catalog is emptied is denied, not promoted. Role-granted ADMIN is honored consistently, and the server's startup text no longer claims there is no authentication.

    Security hardening — pass 1: extension loading ✅

    • LOAD EXTENSION is off by default everywhere (engine, CLI, C ABI, bindings); enable it explicitly with --allow-load-extension / PINKDB_ALLOW_LOAD_EXTENSION, the new C-ABI switch, or the binding opt-ins.
    • Opening a database file can no longer execute native code recorded in its WAL: replay refuses a recorded LOAD EXTENSION unless the library is already mapped in the process or the new replay opt-in + extension root allow it — otherwise it is a hard, actionable error (the audit's reproduced attack is now a regression test, marker absent).
    • Extensions are path-confined: no bare loader-path names, no .., no symlinked libraries, plus an optional --extension-root on server and CLI.

    Security hardening — low-severity batch ✅

    • Redacted the login password from the server protocol's Debug output (L-2) and the SigV4 canonical request / session token from Signature's (L-11).
    • Constant-time key-material comparison in the encryption layer (L-3).
    • Every lake commit-delta path is validated, and local storage refuses absolute/.. paths (L-12); the stale extracted SigV4 copy is deleted.
    • Checked arithmetic in all .pink RLE decoders (32-bit overflow, L-13).
    • The Cloudflare API token is scoped to the deploy step only (L-14).
    • The four .lake subcommands that bypassed PINKDB_KEY now use the keyed constructor; the S3 test harness pins image digests.

    2026-10-19#

    Wave 75 — core httpfs extension (remote files for every format) ✅

    • New shared transport pinkdb-httpfs: the lake's SigV4 S3 client extracted behavior-identically, plus https GET and byte-range reads, with Fetcher as the contract.
    • Every registered format reads remote paths: CSV (whole-object), Parquet via a ranged ChunkReader (footer/row-group pages — no whole-file downloads when the size is known), Arrow (whole-object, documented). Claims are by extension regardless of scheme; --features parquet,arrow,httpfs composes, and default binaries stay transport-free.

    Wave 77 — SQL macros ✅

    • CREATE [OR REPLACE] MACRO … AS expr and AS TABLE SELECT …, with DROP MACRO [IF EXISTS], parameter defaults and named arguments, expanded by bind-time AST substitution (no dynamic SQL — call-site typing, invoker rights and injection safety hold). Usable in expressions, FROM, aggregates, windows, CTEs, prepared statements, views and other macros; recursion is refused cleanly.
    • SHOW MACROS / DESCRIBE MACRO; macros persist in .pink (flag bit 6, loaded before MVs) and are WAL-logged DDL; invocation keeps table grants enforced. +98 KB on the default binary.

    Wave 70 — core parquet extension (read-side) ✅

    • Parquet reads with the DuckDB surface: read_parquet/parquet_scan (globs, directories, multi-file, union_by_name, hive partitions, filename/file_row_number), four metadata functions, a replacement scan (FROM 'x.parquet'), projection pushdown and row-group-statistics filter pruning with visible counters.
    • Landed with the unified file-format surface: one read path (TableSource) shared with arrow, one grammar (Function + Path), the COPY sink kept separate, and logged file reads replay by re-reading (DuckDB's rule). parquet is opt-in (+1.1 MiB); the default binary pays ~18 KB for the surface.

    Wave 71 — core arrow extension (Arrow IPC) ✅

    • New engine file-format extension surface (pinkdb::filefmt): arrow files work through FROM 'x.arrow', read_arrow/read_ipc/read_feather and COPY … (FORMAT arrow), with durable replay re-reading files and lean builds refusing everything with a precise error.
    • arrow is an opt-in CLI feature (+≈3.0 MiB; the default binary grows only 22 KB for the seam). Round-tripped against pyarrow in both directions; DuckDB has no Arrow support to diff against (documented). The Arrow C Data Interface is pinned as a follow-up. .pink remains the native format.

    Wave 54 — core math extension ✅

    • Seventeen functions via the Rust SDK: exp/ln/log/log2/log10, the trigonometric family, degrees/radians/pi, and the first volatile function — random() refuses to run in any WAL-logged statement (replay could diverge), while reads work normally. sqrt/pow/floor/ceil/ sign/greatest/least remain core built-ins.
    • SDK gained ranged arity (optional/variadic — linked-only by construction), and integer/DECIMAL arguments now widen into DOUBLE parameters like DuckDB. math joins json+datetime as a default feature; +25 KB default.

    Wave 69 — prepared statements in the Python and Go bindings ✅

    • Both bindings gained idiomatic prepared-statement APIs over the FFI: Python db.prepare(sql) → Statement.execute(*params), Go db.Prepare(sql) → Stmt.Execute(args...) — typed parameters, NULLs, reuse and clean close semantics, with native error strings passed through unchanged.
    • No C-ABI changes; the bindings also caught up on the RBAC result kinds (17–23). Python 56 tests, Go 38 (with -race).

    Wave 56 — core datetime extension ✅

    • Ten DuckDB-pinned datetime functions over naive DATE/TIMESTAMP: strftime, strptime, epoch/epoch_ms, dayofweek/dayofyear/week, last_day, age, make_date — hand-rolled civil-date and format engines, zero new dependencies.
    • The extension ABI gained an additive INTERVAL value type so age returns a real interval; datetime joins json as a default CLI feature (--no-default-features for lean). +40 KB on the default binary.

    Wave 53 — core string extension ✅

    • Ten DuckDB-pinned string functions built with the Rust SDK: split_part, reverse, left/right (now parse unquoted), strpos, starts_with/ends_with, regexp_extract, regexp_matches, plus pinkdb's regexp_match (a pinned divergence — DuckDB has no such function) with DuckDB's full option surface.
    • trim/ltrim/rtrim/replace stay core built-ins (extensions can't shadow them). Loaded at runtime; the default CLI binary grows 0 bytes.

    Wave 52 — core json extension ✅

    • Six DuckDB-pinned JSON functions over VARCHAR — json_extract, json_value, json_valid, json_array_length, json_object, json_array — with a hand-rolled parser (zero new dependencies) that matches DuckDB on the messy corners: trailing commas, NaN/Infinity, duplicate keys, canonical number rendering, escapes.
    • json is a default CLI feature (--no-default-features for the lean binary); the functions register through the linked registry, so durable replay resolves them automatically.

    Wave 51 — Rust extension SDK + volatile flag ✅

    • New ext-sdk/rust: declare an extension once (pinkdb_extension!) and get both the native ABI v1 cdylib exports and the wasm/all-target linked registration from safe Rust — typed args, Option NULLs, Result errors, no unsafe in author code.
    • Additive ABI v1 volatile flag: functions can declare themselves nondeterministic, and the engine refuses to call them in any statement it WAL-logs (replay could diverge) with an explicit error; deterministic extensions are unchanged.
    • Fixed: the SDK's ABI exports (pinkdb_extension_abi_version / _name / _init) are now opt-in — pinkdb_abi_exports!() (or the abi-exports feature for dual-artifact crates, as extensions/string does) — because emitting them from linked-only extensions caused duplicate symbols on Linux linkers. Cdylib authors add the macro; linked-only crates need nothing.

    Wave 50 — performance pass ✅

    • High-cardinality GROUP BY / COUNT(DISTINCT) got a typed fast path (no per-row values, chunked output, adaptive one-shot reserve): group_id 15.8 → 4.4 ms and distinct_id 15.6 → 4.6 ms — both now ahead of the DuckDB reference on the same corpus.
    • Byte-slice hashing went word-wise: distinct_lowcard 3.8 → 3.1 ms and join_probe 5.3 → 4.6 ms.
    • Standing battery total 101.5 → 75.7 ms (−25%); all correctness gates unchanged.

    2026-10-18#

    Wave 48 — RBAC: users, roles and enforced grants ✅

    • New users and roles hashed with Argon2id: CREATE USER/CREATE ROLE, GRANT/REVOKE (table SELECT/INSERT/UPDATE/DELETE, database CREATE, global ADMIN), persisted in the catalog + WAL — plaintext passwords never hit disk.
    • The network server gains session login (protocol v9) and per-statement enforcement: an empty catalog trusts connections with a loud startup warning; once a user exists every statement is checked against their grants. Embedded, FFI and wasm use stays trusted by design.
    • Remote CLI gains --user/--password (or PINKDB_PASSWORD); without the tls feature, login passwords cross the wire in cleartext — documented.

    Wave 49 — extensions on wasm ✅

    • Extensions now work on every target through a new linked registration model: extensions register through a safe-Rust API and feed the same engine registry as native ABI v1 extensions. On wasm (where dlopen cannot work), LOAD EXTENSION '<name>' resolves a registered name; unknown names fail with an actionable error.
    • The JS / wasm-bindgen host contract is pinned — surface, SQL↔JS value mappings and sandbox rules, documented in docs/wasm-extensions.md — with no new dependencies added.
    • Native CLI grows ~3.7 KB; the wasm dependency tree gains nothing.

    Wave 46 — network server TLS ✅

    • Opt-in tls feature: the server serves the same protocol over rustls-encrypted TCP (--tls-cert/--tls-key), and the CLI's remote mode gained --tls, --tls-ca-cert and --tls-insecure. Certificate problems refuse startup with precise messages; handshake failures never disturb the accept loop; the default build and dependency graph are unchanged.
    • Still no authentication — TLS encrypts the transport only, which the docs and startup warning state explicitly.

    Wave 47 — async I/O at the boundary ✅

    • pinkdb-server gains an opt-in async-server transport: a tokio listener with one task per connection, engine calls on the blocking pool, and byte-identical protocol frames to the synchronous server (same client works unchanged). --transport sync|async.
    • The "zero async" rule now has its documented carve-out: async lives only at the server I/O boundary — the executor, storage and WAL stay synchronous — and the default build links no runtime (+0.38 MB only with the feature).

    Wave 82 — Rust toolchain upgrade ✅

    • All crates now require Rust 1.97 and compile as edition 2024; CI's MSRV job pins 1.97 (was 1.89 core / 1.95 pink-lake), and the wasm check passes again.
    • Modernized the code where the new edition/compiler asks for it — let-chains (~60 collapsed conditionals), unsafe(...) attribute syntax, reserved gen renames — with semantics unchanged (duckdiff still 171/171).

    Wave 44 — stored procedures ✅

    • SQL procedures: CREATE [OR REPLACE] PROCEDURE p(a INTEGER, …) AS $$ … $$ (typed DECLARE/SET, IF/ELSIF/ELSE, WHILE, nested blocks, RETURN, RAISE), DROP PROCEDURE [IF EXISTS], CALL p(args) — parameters and variables are bound as values, never spliced SQL, so injection-shaped input is inert by construction. CALL is statement-atomic, works in transactions, is persisted per database and replays exactly from the WAL.
    • JavaScript procedures: the sandbox contract ships (pinkdb-js: host API, denied-intrinsics determinism policy, conversions) with a clean refusal — the engine binding (quickjs-ng, ~1.1 MB) is the queued follow-up (wave 81).

    Wave 74 — lake naming sweep ✅

    • The lake builds are now pinklake (the .pink-file lake; formerly lake-lite) and lake (the full lake; later removed), in cargo features, help text, tests, CI, README and the docs site.
    • s3 is pure storage: it implies no lake build — combine it explicitly (pinklake,s3; --features s3 alone has no .lake commands and says so). No old aliases survive.

    Wave 80 — materialized-view refresh policies ✅

    • Manual: REFRESH MATERIALIZED VIEW name (and REFRESH name, plus REFRESH MATERIALIZED VIEWS refreshing every view of the database all-or-nothing); SHOW MATERIALIZED VIEWS lists schedule, last refresh time/count and staleness.
    • Scheduled: CREATE MATERIALIZED VIEW v REFRESH MANUAL | EVERY INTERVAL '5 minutes' | ON COMMIT AS SELECT … — enforced daemonless at statement boundaries (embedded and pinkdb-server alike; never mid-transaction), with automatic refreshes WAL-logged and replay-exact.
    • Fix: MV definitions are now WAL-logged and persisted — previously a durable reopen silently lost them.

    Wave 68 — inlined small writes & CDC ✅

    • Tiny commits (≤ 10 rows by default; per-table limits, PINKDB_LAKE_INLINING_ROW_LIMIT) live in the catalog metadata instead of new data files — scans, stats, time travel, partitions and encryption all see them correctly. .lake flush materializes them into real files and keeps the history.
    • CDC reads: .lake changes (and the library's table_insertions/table_deletions/table_changes) replay each version's deltas as snapshot_id/rowid/change_type rows. Updates read as delete + insert (documented).
    • .lake add_data_files registers existing lake files into a version with exact schema and statistics checks — encrypted lakes included.

    Wave 42 — hash indexes ✅

    • CREATE INDEX [IF NOT EXISTS] name ON t (col) and DROP INDEX [IF EXISTS] name (per-database): a single-column hash index turns col = literal lookups into an IndexScan instead of a full scan — results are identical either way. .pink persistence is queued as the follow-up (wave 79).

    Wave 43 — materialized views ✅

    • CREATE MATERIALIZED VIEW … AS SELECT, REFRESH [MATERIALIZED VIEW] (full recompute) and DROP MATERIALIZED VIEW [IF EXISTS]: stored as a queryable table plus its refresh query, per-database, WAL-logged and persisted.

    Engine fixes and performance

    • Bug-review remediation: server ETag validation, both FFI result-building paths guarded, VARCHAR string-offset-limit refusal, attach row-count re-checks. Performance: COUNT(*) dead-work elimination and fast DISTINCT for integer/date/timestamp keys.

    Bug-review remediation — P1 + P2 ✅

    Wave 67 — lake maintenance ✅

    • Compaction: merge_adjacent_files publishes one new version referencing consolidated files — groups of delete-free files sharing partition values and schema epoch (≥2 members) merge into one; source files are never touched (bytes and mtimes pinned by tests) and row counts/zone maps stay exact. rewrite_data_files materializes deletes above a threshold.
    • Retention: expire_snapshots removes old snapshots + commit deltas (explicit versions, older_than, or retain_last — never the current version); cleanup_old_files / delete_orphaned_files delete only unreferenced data/ objects, behind a 2-day age gate and an explicit dry-run/confirm; encrypted lakes included.
    • Introspection: .lake files / table_info / options / settings (+ merge, rewrite, expire, cleanup, orphans).

    Wave 57 — lake encryption at rest ✅

    • With the encryption feature, a keyed session (PINKDB_KEY, consistent with the engine) seals every lake object — catalogs, snapshots, commit deltas, data files, delete files — as PNKLAKE1 AES-256-GCM containers under one Argon2id derivation per session. A Storage-level decorator means commits, deletes, time travel and retry paths are covered with no per-call-site code.
    • The catalog.json == snapshots/<v>.json byte invariant survives (seal once, publish the same ciphertext); S3 conditional-write CAS is unchanged; statistics-fast attach on encrypted lean lakes still decodes zero data files.
    • Wrong/missing keys and tampered containers fail closed with authenticated errors (never “corrupt file”); plaintext lakes stay byte-identical and are refused by keyed sessions. Encrypted lake attach reads whole objects in stage 1 (segment-level reads documented as the follow-up).

    Wave 65 — lake schema evolution ✅

    • ALTER TABLE on writable-attached lake tables — ADD COLUMN … DEFAULT, RENAME COLUMN, DROP COLUMN (plus the engine-wide ALTER TABLE support behind it: defaults, NOT NULL rules, DESCRIBE defaults, WAL replay) — published as metadata-only catalog schema versions (format now v5): old data files are never rewritten; they project through rename chains, missing columns materialize their defaults, and dropped columns keep their bytes (row positions unchanged — delete files stay valid).
    • Time travel reads each version with that version's schema and names; writes across versions keep working through the projection.
    • Limits (documented): RENAME TABLE through a lake commit is refused with a .lake save hint; no ALTER COLUMN TYPE / SET|DROP DEFAULT / ADD CONSTRAINT; read-only attachments refuse ALTER.

    Wave 66 — lake partitioning & pruning ✅

    • Lake tables can be partitioned: identity values or bucket(N) labels are recorded per file, commits write one data file per partition value set, and spec changes (.lake partition … by (…) | clear) never rewrite old files.
    • Every v4 data file publishes a CRC-protected zone map in the catalog; the planner prunes whole files for exact predicates — WHERE region = 'x' reads only that partition's file, and disjoint ranges read zero.
    • COUNT/MIN/MAX honesty rules are preserved (fall back once positional deletes exist); pruning stays correct with deletes and across time travel.
    • Limits (documented): bucket labels are pinkdb's own hash (no cross-engine numbers, no bucket-value pruning); year/month/… transforms are refused by name.

    Wave 63 — incremental lake writes ✅

    • Lake commits now append: each commit writes one new immutable data file per table (with its exact row count in the catalog) and never rewrites a published file — a 1M-row lake committed 4 rows in 7.6 KB / 0.54 s with 0 bytes rewritten (vs a 2.6 MB full save).
    • DELETE / UPDATE write positional delete files applied at read time (merge-on-read); every published version also writes a small commits/<v>.json delta manifest.
    • Writable attached lakes: .lake attach <dir> write, mutate with normal SQL, .lake commit publishes the diff; guarded .lake detach; durable sessions replay commits idempotently after a crash.
    • Concurrent-writer retry with DuckLake's settings and defaults (max_retry_count 10, retry_backoff 1.5, retry_wait_ms 100 — rebase on conflict, bounded, clean failure).
    • Fixes after landing: the feature-less build message and the S3 Docker expectations updated for the new catalog format (format_version 4).

    Wave 64 — lake time travel & snapshot metadata ✅

    • Query any published lake version: SELECT … FROM t AT (VERSION => n) / AT (TIMESTAMP => ts) on attached lake tables, with DuckLake-pinned resolution (timestamp = newest snapshot at or before it, inclusive).
    • Per-version records: .lake snapshots lists time, author, message, (tables, rows) and a change summary; .lake save … author '…' message '…' attaches commit metadata.
    • Statistics fast paths work per version: COUNT/MIN/MAX over an older version decode no data files.
    • ducklake_default_version deliberately not mirrored (probed: it selects a new-catalog storage format, not a read default).

    Wave 41 — primary / foreign keys ✅

    • Declarative PRIMARY KEY / UNIQUE / NOT NULL / REFERENCES in column and table form (CONSTRAINT names; RELY / [NOT] ENFORCED accepted and dropped), validated at DDL time like DuckDB.
    • Constraints are metadata-only — writes never enforce them; DESCRIBE reports PRI/UNI markers and nullability.
    • Optimizer: conservative FK→PK join elimination (declarations are trusted, not verified — documented).
