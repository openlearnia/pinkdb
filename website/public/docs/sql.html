Reference

SQL reference

The SQL surface pinkdb implements today — DDL/DML, joins, CTEs, subqueries, window functions, aggregates, prepared statements and transactions — plus an honest list of what is not supported yet.

DDL and DML#

SQL
CREATE TABLE t (id BIGINT, name VARCHAR, price DOUBLE);
CREATE TABLE db1.t (...);            -- qualified: any db.table target works
CREATE TABLE t2 AS SELECT ...;       -- CTAS
CREATE TABLE IF NOT EXISTS t (...);  -- IF [NOT] EXISTS on CREATE/DROP TABLE
INSERT INTO t VALUES (1, 'x', 9.5), (2, NULL, 3.0);
INSERT INTO t SELECT ...;            -- INSERT ... SELECT
INSERT INTO t VALUES (1, 'y', 2.0)
  ON CONFLICT (id) DO UPDATE SET price = excluded.price  -- upsert (or DO NOTHING)
  RETURNING id, price;                                   -- final rows, after triggers
INSERT OR REPLACE INTO t VALUES (1, 'y', 2.0);  -- = DO UPDATE over the given columns
INSERT OR IGNORE  INTO t VALUES (1, 'y', 2.0);  -- = DO NOTHING
UPDATE t SET price = price * 1.1 WHERE id > 1;   -- SET exprs see pre-update values
UPDATE t SET price = s.price FROM s WHERE t.id = s.id;   -- UPDATE ... FROM
DELETE FROM t WHERE price IS NULL;               -- NULL never matches
DELETE FROM t USING s WHERE t.id = s.id;         -- DELETE ... USING
MERGE INTO t USING s ON t.id = s.id              -- MERGE
  WHEN MATCHED THEN UPDATE SET price = s.price
  WHEN NOT MATCHED THEN INSERT VALUES (s.id, s.name, s.price);
BEGIN; UPDATE t SET price = 0; ROLLBACK;         -- flat snapshot transactions
CREATE DATABASE db1;                 -- new, empty database
DROP DATABASE db1;                   -- the last database cannot be dropped
USE db1;                             -- per-session current database (default: main)
DROP TABLE t;  DROP VIEW v;
CREATE VIEW v [(cols)] AS SELECT ...;  -- session-local, rebound per use
CHECKPOINT;                          -- persist + roll the WAL (durable databases)

Declarative constraints are accepted in column and table form (PRIMARY KEY, UNIQUE, NOT NULL, REFERENCES u(x) / FOREIGN KEY ... REFERENCES ..., with an optional CONSTRAINT name prefix):

SQL
CREATE TABLE orders (
  id     INTEGER PRIMARY KEY,          -- implies NOT NULL
  code   VARCHAR UNIQUE,
  user_id INTEGER NOT NULL REFERENCES users(id),
  note   VARCHAR,
  CONSTRAINT uq UNIQUE (user_id, code)
);

The declarations are validated at DDL time like DuckDB's (the referenced table must exist and the referenced columns must be exactly one of its PRIMARY KEY or UNIQUE constraints), and DESCRIBE reports them (PRI/UNI markers plus nullability). PRIMARY KEY and UNIQUE are enforced: a duplicate, or a NULL in a primary key, is an error, checked per statement against the declared keys — so a statement that would introduce one aborts whole (including across the rows of a multi-row INSERT). REFERENCES/FOREIGN KEY stays a declaration: the optimizer trusts it for FK→PK join elimination, but writes do not check it.

The DML forms match DuckDB 2.0. ON CONFLICT [(cols)] needs a matching declared PRIMARY KEY/UNIQUE constraint and DO UPDATE may read the proposed row as excluded.col; INSERT OR REPLACE is DO UPDATE over the columns the insert names, so unlisted columns keep their old values, and INSERT OR IGNORE is DO NOTHING. RETURNING works on INSERT/UPDATE/DELETE, ON CONFLICT and MERGE, and reports the final row — a BEFORE trigger's rewrite included. When several source rows match one target row, UPDATE … FROM keeps the last one in source order (DuckDB's behaviour), DELETE … USING deletes once, and MERGE refuses the statement with a "cannot affect the same target row more than once" error. MERGE clauses are tried in order and the first whose AND condition holds wins; WHEN NOT MATCHED BY SOURCE deletes target rows no source row matches. A WITH clause may hold data-modifying statements (WITH x AS (INSERT … RETURNING …) SELECT … FROM x); they run once, at the top level.

UPDATE and DELETE are statement-atomic: the statement sees the pre-update values and either applies completely or not at all. BEGIN / COMMIT / ROLLBACK run on a whole-store snapshot: commits to disjoint tables all succeed, and overlapping writes abort the second committer with a write-conflict error instead of a silent lost update.

duckdb conventions

Integer overflow is an error (not a wrap), int / int is a DOUBLE, DOUBLE → integer casts round half away from zero, and SUM over integers is computed exactly. DECIMAL arithmetic follows DuckDB's promotion rules: + - * keep the scale with 38-digit caps, / widens to DOUBLE.

SELECT#

SQL
SELECT [DISTINCT] expr [AS alias], ...
FROM t [JOIN u ON t.x = u.y]      -- INNER / LEFT / RIGHT / FULL [OUTER], CROSS
  | FROM a JOIN b ON ... JOIN c ON ...   -- multi-way (n-ary) joins
  | FROM t, u [JOIN v ON t.x = v.z]  -- a comma is a CROSS JOIN in the same
                                  -- left-deep chain (ON sees the items left of it)
  | FROM LATERAL (SELECT ...) AS s -- LATERAL subqueries (uncorrelated only)
  | FROM t USING SAMPLE 10 ROWS   -- TABLESAMPLE / USING SAMPLE: n ROWS | n PERCENT,
  | FROM t TABLESAMPLE BERNOULLI(10 PERCENT)  -- bernoulli | system | reservoir,
                                  -- REPEATABLE (seed) for a deterministic draw
  | FROM db1.t                    -- qualified tables resolve in that database
  | FROM (SELECT ...) AS s         -- derived tables (alias required)
  | FROM (VALUES (1,'a'), (2,'b')) t(x, y)  -- VALUES, column aliases optional
  | FROM 'file.csv' / read_csv(...) -- extension table functions (waves 70-75)
  | WITH [RECURSIVE] w AS (SELECT ...) ...  -- CTEs, incl. WITH w(a, b) AS column
                                  -- aliases; RECURSIVE needs an anchor plus a
                                  -- UNION [ALL] step (bounded, see below)
[WINDOW w AS (PARTITION BY ... ORDER BY ...), ...]   -- a window may build on
                                  -- another: OVER (w ORDER BY x), WINDOW v AS (w ROWS ...)
WHERE expr                        -- IS [NOT] NULL, IS [NOT] DISTINCT FROM,
                                  -- BETWEEN, IN (subquery|list), EXISTS
GROUP BY ... | GROUPING SETS (...) | ROLLUP (...) | CUBE (...)   HAVING ...
QUALIFY expr                      -- after WINDOW, before ORDER BY
ORDER BY expr [ASC|DESC] [NULLS FIRST|NULLS LAST], ...   -- ORDER BY 2 positional
LIMIT n | FETCH FIRST|NEXT n ROW|ROWS ONLY | OFFSET n [ROW|ROWS];

SELECT DISTINCT ON (expr, ...) ...  -- first row per key in ORDER BY order
SELECT ... TABLE t;                 -- the whole table (plus any trailing clauses)
VALUES (1, 'a'), (2, 'b');          -- column names col0, col1, ...

COUNT(DISTINCT x)                 -- inside aggregates
SUM(x) FILTER (WHERE ...)         -- filtered aggregates, window aggregates too
PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY x)   -- ordered-set aggregates:
PERCENTILE_DISC(0.9) WITHIN GROUP (ORDER BY x)   -- percentile_cont/disc, and
MODE() WITHIN GROUP (ORDER BY x)                 -- mode(); FILTER allowed too
SET VARIABLE x = 41;              -- session variable (per connection),
SELECT getvariable('x'), $x;      -- read back by getvariable or $x
SELECT ... UNION [ALL|DISTINCT] SELECT ...
SELECT ... INTERSECT [ALL] SELECT ...
SELECT ... EXCEPT [ALL] SELECT ...
EXPLAIN SELECT ...                -- the query plan
SHOW TABLES;  DESCRIBE t;         -- introspection

Joins

  • INNER, LEFT [OUTER], RIGHT [OUTER], FULL [OUTER] and CROSS joins; join conditions may be arbitrary expressions (non-equi predicates, composite ON a = b AND c = d, and multi-way chains are accepted). Equality predicates still take the hash-join fast path.
  • Outer joins NULL-extend the unmatched side's columns.
  • Cross-database joins work: db1.t JOIN db2.u.
  • A comma-separated FROM list is a chain of CROSS JOINs, so FROM a, b JOIN c ON a.x = c.z binds like DuckDB (the later ON sees the items left of the comma).
  • LATERAL subqueries are accepted in the FROM head position, after CROSS JOIN/JOIN and in the comma form. A derived plan has no outer scope, so a LATERAL subquery that references an earlier FROM item is refused by name (uncorrelated LATERAL only); a lateral table function is refused too.
  • TABLESAMPLE / USING SAMPLE takes n ROWS (exactly n, reservoir sampling) or n PERCENT, with the bernoulli, system or reservoir method, and REPEATABLE (seed) makes the draw reproducible (within pinkdb — the generator is its own, so a seed picks different rows than DuckDB's).

Subqueries and CTEs

  • Derived tables in FROM (alias required), including inside CTEs, views and other subqueries.
  • VALUES in FROM with column aliases ((VALUES (1, 'a'), (2, 'b')) t(x, y)), standalone (VALUES (1, 'a'), (2, 'b') — the columns are col0, col1, …) and as an INSERT source. Cells must be constants; each column takes the common type of its cells.
  • TABLE t is shorthand for SELECT * FROM t and takes the same trailing ORDER BY/LIMIT.
  • Scalar subqueries, IN (subquery) and EXISTS (subquery) — uncorrelated only; correlated subqueries are rejected.
  • WITH w AS (...) plus WITH w(a, b) AS (...) column aliases. CTEs shadow unqualified names only; a qualified name never resolves to a CTE.
  • WITH RECURSIVE r(i) AS (anchor UNION [ALL] step), evaluated semi-naively: the step sees the rows the previous round added, UNION (not ALL) also drops rows already produced, iteration stops when the step adds nothing, the step's columns are cast to the anchor's types, and recursion is bounded at 100 000 iterations and 10 000 000 rows — both are errors (recursive CTE "r" still produced rows after 100000 iterations), so a forgotten predicate cannot hang the engine.

Set operations and views

  • UNION, INTERSECT and EXCEPT (ALL keeps duplicates, the default deduplicates) with numeric type unification. An ORDER BY/LIMIT after the set operation applies to the whole result; branch-level clauses need parentheses and are unsupported today.
  • CREATE VIEW v [(cols)] AS ... — session-local and per-database; bodies are self-contained (the caller's CTEs never leak in) and rebound per use.

Prepared statements#

? placeholders are supported with bind-time type inference against the catalog; a CAST(? AS t) pins a parameter's type. Prepared statements run through the normal statement path with the bound values substituted as SQL literals, so durable stores log the substituted SQL and replay exactly.

Rust
use pinkdb::{PinkDb, Value};

let mut db = PinkDb::new();
let mut conn = db.connect();
let stmt = conn.prepare("INSERT INTO t VALUES (?, ?, ?)")?;  // parameter_count() == 3
let bound = stmt.bind(&db, "main", &[Value::Integer(1), Value::from("x"), Value::Null])?;
conn.execute_bound(&bound)?;   // run (repeatable; the bind is reusable)

The server protocol carries the same flow (Prepare / ExecutePrepared frames, protocol v6) and the C ABI has prepare/bind/execute entry points. The Python and Go wrapper ergonomics are queued as a follow-up wave.

Aggregates and window functions#

  • Aggregates: COUNT(*) / COUNT(x) / COUNT(DISTINCT x), SUM, AVG, MIN, MAX, each with an optional FILTER (WHERE ...) (SUM(x) FILTER (WHERE x > 0)); filtered rows contribute nothing, not a zero.
  • GROUP BY GROUPING SETS (...), ROLLUP (...) and CUBE (...), with GROUPING(x) / GROUPING(x, y) / GROUPING() to tell summary rows from detail rows (big-endian mask, DuckDB's set order: GROUPING(a, b) = 2 * g(a) + g(b); the zero-argument form is 0 for detail rows and 1 for the grand total). Plain group keys cross-product with the sets, and HAVING/ORDER BY/LIMIT apply once to the combined result.
  • Window functions: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, NTILE, FIRST_VALUE, LAST_VALUE, and aggregates OVER with PARTITION BY / ORDER BY / ROWS and RANGE frames (frames are validated; no nesting). The default frame is cumulative with ORDER BY and whole-partition without it.
  • Named windows: WINDOW w AS (PARTITION BY g ORDER BY a) then OVER w (also sum(a) OVER w; several definitions in one clause). A window that builds on another window is refused.
  • QUALIFY expr filters on the window output, so QUALIFY row_number() OVER (PARTITION BY g ORDER BY a) = 1 and ... WINDOW w AS (...) QUALIFY s > 10 (with s a select alias) need no extra subquery. It runs after WINDOW and before ORDER BY.
  • Window functions are allowed in the SELECT list, ORDER BY and QUALIFY (not in WHERE/GROUP BY/ HAVING).
  • Aggregates in ORDER BY need a select alias or position; general ORDER BY expressions must be aliases, positions, or GROUP BY keys.

Scalar functions and expressions#

  • Math: abs, round, ceil/ceiling, floor, sqrt, pow/power, sign, mod, greatest, least.
  • Arrays: array_value(…), array_extract(a, i), len(a)/array_length(a) (see ARRAY).
  • Strings: upper, lower, length, substr, trim/ltrim/rtrim, replace, concat.
  • CAST(x AS type): the numeric tower both ways (including DECIMAL and INTERVAL from/to text), bool ↔ numeric, varchar parse/format, date ↔ timestamp; bad input and out-of-range narrowing error. TRY_CAST(x AS type) is the same cast but returns NULL when it would fail, for every target type; a conversion that does not exist at all is still an error.
  • COALESCE(a, b, ...), NULLIF(a, b), IS [NOT] DISTINCT FROM (NULL-safe equality: two NULLs are not distinct), and LIKE/NOT LIKE with %/_ patterns — plus LIKE p ESCAPE 'x' (one escape character, or '' for none) and SIMILAR TO, which is the fully anchored regular expression DuckDB 2.0 really implements (% and _ are literals there; use .*), supporting ., [...]/[^...] classes, * + ? {m,n}, groups, alternation and ^/$. like_escape(s, p, esc) is also a scalar function.
  • Subscripts: a[2] on an ARRAY (1-based, forgiving — see ARRAY), v['a'], v[0] and v.a on a VARIANT (1-based array indices, 0 is an error, a missing key or an out-of-range index is NULL, chains like payload.b[2] work), and s[2] / s[2:4] / s[-1] on a VARCHAR (character-wise, negative counts from the end, out-of-range clamps).
  • Dates and timestamps: year, month, day, hour, minute, second, date_trunc(part, x) (with DuckDB part aliases like dow/doy/isodow/isoweek/ isoyear/week/quarter), extract(part FROM x)/date_part, and epoch/epoch_ms.
  • CASE WHEN c THEN v ... [ELSE e] END and the simple CASE x WHEN v ... form. NULL conditions never match; result types unify like COALESCE.
  • Extensions can add scalar functions at runtime — see Using extensions.

Coercion rules

  • INTEGER → BIGINT → DOUBLE; DECIMAL participates with DuckDB's width/scale promotion (string and numeric input coerce at INSERT/CSV/CAST boundaries).
  • int / int → DOUBLE (the DuckDB rule); DECIMAL / DECIMAL widens both sides to DOUBLE. % is integer-only.
  • Integer overflow is an error, like DuckDB (+/-/*, negation, abs, date ± n, narrowing casts); SUM over integers is exact and errors only when the final value does not fit BIGINT.
  • Integer division/modulo by zero is an error; 0.0 float division is IEEE.
  • Mixed DATE/TIMESTAMP comparison is rejected; timestamps never mix with integers — use date ± interval.

ARRAY

A fixed-size ARRAY column stores N values of one numeric element type per row: FLOAT[768], DOUBLE[1536], INTEGER[4], BIGINT[2]. It is where embeddings live — a 768-d or 1536-d vector is one flat buffer of rows × N elements, not a heap allocation per row — and it is the type the vss and embeddings extensions take and return. FLOAT[N] (and REAL[N]) stores 4-byte floats, so an embedding column costs 4 bytes per element; pinkdb has no FLOAT scalar, so a[i] widens an element to DOUBLE — the one deliberate difference from DuckDB, which returns a FLOAT. The DOUBLE[N] → FLOAT[N] cast follows DuckDB 2.0: round to nearest, a finite value that would become infinite is an error ("out of range for FLOAT"), underflow is silent, and the text path parses straight to f32 ('1e40' becomes inf).

SQL
CREATE TABLE docs (id INTEGER, v DOUBLE[3]);
INSERT INTO docs VALUES (1, [1.0, 2.0, 3.0]), (2, [0.5, 2.0, 3.0]), (3, NULL);
INSERT INTO docs VALUES (4, '[1.5, NULL, 3.5]');      -- VARCHAR parses
SELECT typeof(v) FROM docs LIMIT 1;                  -- DOUBLE[3]
SELECT v[2], array_extract(v, 2), len(v), array_length(v) FROM docs;
SELECT array_value(id, id + 1, -7) FROM docs;        -- per row, any expressions
SELECT v[1] FROM docs WHERE v = [1.0, 2.0, 3.0];     -- structural equality
SELECT id FROM docs ORDER BY v LIMIT 3;              -- lexicographic

Literals. [a, b, c] and array_value(a, b, c) are the same constructor: they build the array per row from any expression, columns included, and infer the element type with the numeric tower — all-INTEGER gives INTEGER[N], a BIGINT or DECIMAL element widens to BIGINT[N]/DOUBLE[N], and any DOUBLE makes it DOUBLE[N] ([1, 2.5] is a DOUBLE[2]). A NULL element is allowed; an empty or all-NULL literal needs a target type (CAST([NULL, NULL] AS DOUBLE[2])).

Element access. a[i] and array_extract(a, i) are 1-based and forgiving, like DuckDB: an index outside 1..=N, a NULL index, a NULL array and a NULL element all return NULL rather than erroring. len(a) and array_length(a) report N (NULL for a NULL array).

Casts. VARCHAR ↔ ARRAY ('[1.5, NULL]' round-trips; a wrong element count or a bad element is a clear error), ARRAY ↔ ARRAY between element types at the same length (INTEGER[3] → DOUBLE[3]; DOUBLE[3] → DOUBLE[4] is cannot CAST … : the array size is part of the type), ARRAY ↔ VARIANT (a VARIANT array of the exact length), and TRY_CAST.

Equality, ordering and grouping. Equality is structural and compares elements by value across element types (DOUBLE[3] = INTEGER[3]), including NULL elements: two NULLs at the same position are equal, so a = b is not three-valued for them. One total order serves ORDER BY, MIN and MAX: element-wise lexicographic, with a NULL element sorting after every value at that position and a NULL array last, like any nullable column. GROUP BY, DISTINCT and join keys hash a canonical key that agrees with = by construction, so -0.0/0.0 and every NaN fold together.

Persistence and encodings. .pink gained dtype tag 10 (element kind + length), default-value tag 10 and page-encoding tag 11: a rows | layout | element bitmap | values payload, row-major or byte-planed (whichever is smaller) behind the existing LZ frame; an ARRAY column carries no min/max statistics (an element-wise bound would not be a bound), only the null count. 100k × 768 pseudo-random DOUBLE rows insert in 0.31 s, scan in 0.31 s and occupy 585 MiB — exactly 8 bytes per element — while the same table as FLOAT occupies 292 MiB, exactly 4 bytes per element, and structured data still compresses (sin data 108×, a constant column 253×). The wire is protocol v13 (value tag 11, dtype tag 10, element byte 0–3); the C ABI exposes PINKDB_TYPE_ARRAY (tag 11, N × 8 bytes of little-endian f64) and PINKDB_TYPE_ARRAY_FLOAT (tag 12, N × 4 bytes of f32), each with the element count packed into the type tag, and never a NULL element — the ABI has no per-element NULL channel; the Node binding hands over a Float32Array/Float64Array, Python a list[float], Go a []float32/[]float64. Extension ABI minor 5 added ExtType::ArrayFloat and ExtType::ArrayDouble: borrowed pointer-plus-length views of the engine's element buffer with no per-element boxing.

Parquet and lakes. A column writes DuckDB 2.0's three-level LIST group (v OPTIONAL LIST → list REPEATED → element OPTIONAL), exactly N element slots per row, with the length in a pinkdb.array.<column> key-value entry (a LIST group has no length of its own). DuckDB reads our files and we read its FLOAT[3]/INTEGER[3] files; a variable-length list cannot be read back as an ARRAY and is refused with a message naming wave 107a2. .pink lake data files round-trip the column and the DuckLake catalog records it the way DuckDB records a nested type (a list parent row plus an element child row with parent_column, the real DOUBLE[3] in the pinkdb_column side row). A FLOAT[N] column writes an f32 element leaf. DuckDB cannot create an ARRAY column in DuckLake at all, but its reader matches data-file fields by field_id = ducklake_column.column_id, so pinkdb stamps exactly those ids on lake data files (top-level columns and the ARRAY child alike) and DuckDB reads the vectors through a pinkdb lake — including after pinkdb added or dropped a column. Standalone COPY … TO files carry no ids, as DuckDB's own do not.

Not in this wave. A variable-length LIST (T[]) is a parse error that names wave 107a2, and unnest, array slicing and the functions that build arrays from grouped rows belong to that same follow-up.

VARIANT#

VARIANT holds a value whose shape can differ from row to row — the semi-structured type DuckDB 2.0 and DuckLake define. Values are stored columnar in a binary encoding (a kind tag plus the payload, with object keys kept sorted), never as JSON text, so a query that does not mention a VARIANT column takes no new path.

SQL
CREATE TABLE events (id BIGINT, payload VARIANT);
INSERT INTO events VALUES
  (1, '{"a": 1, "b": [2, 2.5, "x"]}'),           -- VARCHAR parses as JSON
  (2, CAST(42 AS VARIANT)),                            -- any type widens
  (3, CAST('null' AS VARIANT)),                        -- a JSON null is a value
  (4, NULL);                                           -- SQL NULL is no value
SELECT id, typeof(payload), variant_type(payload) FROM events;
--      VARCHAR   VARIANT    OBJECT / BIGINT / NULL / NULL
SELECT payload, CAST(payload AS VARCHAR) FROM events;   -- JSON text
--      {"a": 1, "b": [2, 2.5, "x"]}   {"a": 1, "b": [2, 2.5, "x"]}

Casts. Every type casts to VARIANT (BOOLEAN, INTEGER/BIGINT, DOUBLE, DECIMAL, VARCHAR, DATE, TIMESTAMP, INTERVAL), and VARIANT casts back to every scalar type, erroring with the kind and the value when the shape does not fit:

SQL
CAST(CAST('"5"' AS VARIANT) AS INTEGER)      -- 5   (a JSON string like DuckDB)
CAST(CAST('1.9' AS VARIANT) AS INTEGER)      -- 2   (rounds half away from zero)
CAST(CAST('null' AS VARIANT) AS INTEGER)     -- NULL for every target except VARCHAR
CAST(CAST('null' AS VARIANT) AS VARCHAR)     -- 'null'  (keeps the text round trip exact)
CAST(CAST('{"a":1}' AS VARIANT) AS INTEGER)  -- Error: cannot CAST VARIANT(OBJECT) value … to INTEGER

pinkdb has no TRY_CAST; a failed cast is an error. JSON text and VARIANT round-trip losslessly for JSON's value model: keys come out sorted, unicode stays raw UTF-8, integral numbers stay integers and fractional ones stay exact decimals (1.0 and -1234567890123.456789 keep their digits); NaN, Infinity and -Infinity survive as those spellings. A DATE or TIMESTAMP inside a variant prints as an ISO string and reads back as a string, which is why the binary encoding — not JSON text — is what persistence and the wire use.

Functions

Subscripts reach inside a value without JSONPath and are 1-based like DuckDB: payload['a'], payload.a, payload['b'][2] (0 is an error). A comparison whose sides are a VARIANT and a scalar puts the scalar on VARIANT's side, so payload['a'] = 5 and variant_extract(payload, '$.kind') = 'buy' work; a literal string becomes a variant string (it is not JSON-parsed) and a non-literal VARCHAR is still a bind error. The JSON extension's functions also accept a VARIANT and see its JSON text (json_extract, json_array_length, json_valid, …).

Equality, ordering and grouping

  • Equality is structural. Numbers compare by value across kinds, so 1, 1.0 and 1.00 are equal and land in one group; a string that spells a number is a different value ('1' ≠ 1), and a DATE never equals a TIMESTAMP or a string.
  • One total order serves ORDER BY, MIN/MAX and the comparison operators: boolean < number < string < date < timestamp < array < object < JSON null, with SQL NULL last in both directions (like every other column). Arrays and objects order lexicographically.
  • GROUP BY, DISTINCT and join keys hash one canonical key that agrees with = by construction. A JSON null is its own group and is never equal to SQL NULL: SELECT DISTINCT over {1, 1.0, '1', true, JSON null, NULL} returns five rows while count(DISTINCT v) returns four.

Persistence and encodings. A VARIANT column survives save/open, WAL replay, checkpoint and ALTER TABLE … ADD COLUMN … DEFAULT (new .pink dtype tag). It crosses the wire protocol as a length-prefixed blob (protocol v11), the C ABI as its JSON text (PINKDB_TYPE_VARIANT), the extension ABI as the opaque binary encoding (ExtType::Variant, ABI minor 3), and the JS/WASM binding as a native JSON value. A .pink lake data file round-trips it.

Parquet, shredding and pruning

Parquet gets the specification's Variant logical type — a metadata dictionary shared by the row group, a residual value buffer and an optional typed_value group — so COPY … TO '….parquet' and read_parquet carry a VARIANT column both ways, and DuckDB 2.0 reads a pinkdb file while pinkdb reads a DuckDB file. Which object keys become typed columns is decided per column over its rows: a key is shredded when it appears in at least 32 rows and in half of them, every occurrence has the same primitive kind (BOOLEAN, BIGINT, DOUBLE, VARCHAR, DATE, TIMESTAMP), and at most eight keys qualify, most frequent first. Present-but-null keys and other shapes (nested objects, arrays, DECIMALs, a JSON null) stay in the residual buffer, so {} and {"a": null} remain distinct values.

Each shredded path gets exact min/max and null-count statistics, keyed the way DuckDB spells a path ("a", "user"."id"), so a filter on payload['a'] or variant_extract(payload, '$.a') skips files whose bounds exclude the value — in .pink and Parquet lakes alike. A catalog keeps those path facts in DuckLake's own ducklake_file_variant_stats table, written and deleted with the file's other statistics on pink:, sqlite: and Postgres catalogs. DuckDB 2.0 attaches a pinkdb lake and reads them, and pinkdb prunes on rows DuckDB wrote. On 1M rows of mixed shapes in ten Parquet files: 12.3 MB shredded against 14.4 MB unshredded (same data as JSON text: 12.0 MB), a selective path filter 0.027 s against 0.260 s (all files scanned) and 0.020 s against 0.209 s in a .pink lake. A full scan of the column is at parity with the unshredded layout in a lake and 1.18x it when read straight from the file. TPC-H Q1/Q6 over 10M rows are unchanged within noise.

Three-valued logic#

  • NULL fails WHERE: a comparison with NULL is never true.
  • COUNT(x), SUM and AVG skip NULLs; COUNT(*) counts rows.
  • NULL group keys group together; NULL join keys never match.
  • LEFT/RIGHT/FULL joins NULL-extend the unmatched side's columns.
  • CASE conditions that evaluate to NULL never match.

Databases and sessions#

Databases are named, case-insensitive namespaces (main by default). A session — the embedded PinkDb, or each Connection — has a current database; unqualified table names resolve there. USE db switches it and never affects other sessions: the shared store is untouched.

  • db.table qualifies any table reference in FROM/JOIN, INSERT, UPDATE, DELETE, CREATE TABLE, DROP TABLE, CREATE VIEW and DROP VIEW.
  • Three-part column references (db.table.col) resolve since wave 94. One consequence: a nested VARIANT path is spelled js.a['b'], because v.js.a reads as database v.
  • Views are per-database and session-local: created in the current database and resolved there, with their bodies resolving unqualified names in that database.
  • DROP DATABASE refuses the last database and switches a session that was using it to main (or the first remaining database). CREATE/DROP DATABASE and LOAD EXTENSION are refused inside a transaction.
  • USE, DATABASE, LOAD, EXTENSION and LEFT/RIGHT/OUTER/FULL/CROSS are reserved words; quote identifiers to use them as names ("use" works).

Stored procedures#

SQL
CREATE PROCEDURE bump(a INTEGER) AS $$
BEGIN
  DECLARE n INTEGER DEFAULT 0;
  UPDATE sales SET total = total + a WHERE region = 'west';
  RETURN a;
END
$$;
CALL bump(5);
DROP PROCEDURE bump;
  • Bodies support typed DECLARE/SET, IF/ELSIF/ELSE, WHILE, nested blocks, RETURN, RAISE and any ordinary SQL statement (recursion is bounded).
  • Parameters and variables bind as values, never spliced SQL — injection-shaped input is inert by construction — and every body statement rebinds against the live catalog (a procedure can create a table, then write to it).
  • CALL is statement-atomic and works inside transactions; procedures live per database, persist in .pink files and replay exactly from the WAL.
  • JavaScript procedures (LANGUAGE JAVASCRIPT) are refused cleanly in this build — the quickjs-ng engine binding is the queued follow-up.

Triggers#

SQL
CREATE TRIGGER audit AFTER INSERT OR DELETE ON sales
  FOR EACH ROW EXECUTE INSERT INTO audit_log VALUES ('change');
CREATE TRIGGER stamp BEFORE UPDATE OF total ON sales
  FOR EACH ROW WHEN (NEW.total < 0)
  EXECUTE DO $$ BEGIN SET NEW.total = 0; END $$;
CREATE TRIGGER totals AFTER UPDATE ON sales
  REFERENCING OLD TABLE AS o NEW TABLE AS n FOR EACH STATEMENT
  EXECUTE PROCEDURE recount(n);
DROP TRIGGER audit ON sales;
SHOW TRIGGERS ON sales;
  • {BEFORE|AFTER} × {INSERT|UPDATE [OF cols]|DELETE} × {ROW|STATEMENT}, with several events per trigger (INSERT OR UPDATE) and a WHEN condition.
  • FOR EACH ROW (the default) exposes OLD and NEW as columns in WHEN and in the body; a BEFORE row trigger may assign NEW.col and the table stores the modified image. OLD is read-only, and v1 has no row-skipping.
  • FOR EACH STATEMENT exposes REFERENCING OLD TABLE AS o NEW TABLE AS n as read-only relations (FROM o); transition tables are AFTER-only.
  • Triggers run inside the firing statement's transaction — an error rolls back the whole statement — and in creation order. A trigger's own DML fires triggers, bounded at 16 levels.
  • Creating one needs CREATE on the database; bodies run with invoker rights, so a trigger cannot exceed the firing user's privileges.
  • Definitions persist in .pink files and replay from the WAL by re-executing the firing statement, so its triggers fire again exactly once.
  • RETURNING on a triggered table reports the image the BEFORE row triggers left behind, not the one the statement proposed.
  • Refused: triggers on views and attached lake tables, and trigger DDL inside a transaction.

Materialized views#

SQL
CREATE MATERIALIZED VIEW totals REFRESH EVERY INTERVAL '5 minutes' AS
  SELECT region, SUM(total) AS t FROM sales GROUP BY region;
REFRESH MATERIALIZED VIEW totals;      -- manual (shorthand: REFRESH totals)
REFRESH MATERIALIZED VIEWS;            -- every view of the session database
SHOW MATERIALIZED VIEWS;               -- schedule, last refresh, staleness
DROP MATERIALIZED VIEW totals;
  • Views are stored as queryable tables plus their defining query — per-database, persisted and WAL-logged.
  • Refresh policies: MANUAL (default), EVERY INTERVAL '…', ON COMMIT. They are enforced **without background threads** at statement boundaries: the first statement after a view is due (or after a commit that dirtied its base tables) observes fresh data; nothing refreshes inside a transaction.
  • SHOW MATERIALIZED VIEWS reports the schedule, last refresh time/count and staleness; an automatic-refresh failure keeps the last good data, records the error and retries with backoff.

Full-text search#

A BM25 index (wave 108a, CLI/server feature fts) with DuckDB fts's surface. The index is ordinary tables in a database named fts_main_<table>, so it saves with the store and replays from the WAL, and the query side is a plain function — an MCP query tool can rank in a read-only session.

SQL
CREATE TABLE docs (id INTEGER, title VARCHAR, body VARCHAR);
INSERT INTO docs VALUES (1, 'Relational databases', 'Rows in tables'),
                        (2, 'Search engines', 'BM25 ranks documents');
CALL create_fts_index('docs', 'id', 'title', 'body');

SELECT id, match_bm25('docs', id, 'relational database') AS score
FROM docs ORDER BY score DESC;

CALL drop_fts_index('docs');
  • CALL create_fts_index(input_table, input_id, *input_values, stemmer := 'porter', stopwords := 'english', ignore := '(\\.|[^a-z])+', strip_accents := 1, lower := 1, overwrite := 0); CALL drop_fts_index(input_table). Replacing an existing index needs overwrite := 1. The default ignore is built in; any other pattern needs the fts-regex feature.
  • match_bm25(index, id, query, fields := NULL, k := 1.2, b := 0.75, conjunctive := 0) — id is the indexed id column, index the base table's name (a function cannot be schema-qualified); fields := 'title,body' is a comma-separated list; conjunctive := 1 keeps only documents with every query term; no matching term scores NULL.
  • stem(word) is the index's Porter (Snowball English) stemmer, and rrf(rank, k := 60) is 1 / (k + rank), so two ranked lists fuse with sum(rrf(rank)) grouped by id.
  • Scoring is DuckDB's BM25 (the same idf, k/b, per-field lengths), verified against an independent reference implementation. Text is lowercased, accent-stripped, split on the ignore pattern, filtered with DuckDB's english stopwords (the SMART list, 571 words) and Porter-stemmed.
  • On the server, match_bm25('docs', …) is checked as a read of docs: the session needs SELECT on the base table, so the function cannot expose text a session may not scan. Building or dropping an index is a CALL (ADMIN) and is refused in a read-only session, including the read-only MCP query tool.
  • Static, like DuckDB: after an INSERT/UPDATE/DELETE on the base table the index is stale until it is re-created with overwrite := 1. Incremental indexing is a follow-up.
  • Differences: CALL instead of PRAGMA, the index name as the first match_bm25 argument instead of a schema-qualified macro, fields as a VARCHAR (no LIST), and no phrase queries, snippets or per-field boosts.

Embeddings#

embed(text) returns a fixed-size FLOAT[N] vector from an OpenAI-compatible POST endpoint — wave 107c, CLI/server feature embeddings, off by default. It is a linked extension, so the model, the endpoint and the width are settings, not SQL: the width is PINKDB_EMBEDDINGS_DIMENSIONS and becomes the N of the type at bind time, so embed() is a scalar like any other and the result is an ordinary array column.

SQL
CREATE TABLE docs (id INTEGER, body VARCHAR, v FLOAT[1024]);
INSERT INTO docs VALUES (1, 'pinkdb is a mini DuckDB in Rust', NULL),
                        (2, 'BM25 ranks documents', NULL);

UPDATE docs SET v = embed(body);

WITH q AS (SELECT embed('an embedded database') AS v)
SELECT d.id, array_cosine_distance(d.v, q.v) AS distance
FROM docs d, q ORDER BY distance LIMIT 5;
  • Variables are read from the environment at call time: PINKDB_EMBEDDINGS_BASE_URL (required: any OpenAI-compatible /embeddings URL; there is no default provider), PINKDB_EMBEDDINGS_MODEL (required), PINKDB_EMBEDDINGS_DIMENSIONS (default 1024), PINKDB_EMBEDDINGS_API_KEY (required; no other provider's key is ever used), PINKDB_EMBEDDINGS_BATCH_SIZE (default 128), PINKDB_EMBEDDINGS_TIMEOUT_MS (default 30000) and PINKDB_EMBEDDINGS_CACHE_DIR. No .env is loaded and no SET reaches them; the key is never stored, logged or echoed.
  • A provider that answers another width is an error naming PINKDB_EMBEDDINGS_DIMENSIONS; restart pinkdb to change it.
  • Arguments are evaluated a chunk at a time, so a table costs requests per distinct text: NULLs make no request, duplicates inside a chunk are collapsed, and the rest go out 128 at a time (1000 rows with 300 distinct texts = 3 requests).
  • An in-process 64 MiB cache keyed by (base URL, model, dimensions, SHA-256 of the text) answers a repeated text without a request; PINKDB_EMBEDDINGS_CACHE_DIR keeps content-addressed files so the cache survives a restart. Nothing is written into the store.
  • embed() is never constant-folded or evaluated while binding, and WHERE false makes no call. It is not declared volatile in the WAL sense — UPDATE … SET v = embed(body) must work in a durable store — instead a logged statement's WAL record carries its embed() results (the replay memo): a crash replay is bit-identical, needs no key, and never contacts the provider. The price is WAL size: 1,000 rows at 1024 dimensions add about 4 KiB per distinct text.
  • A call is external I/O to a paid service: the read-only MCP query tool refuses it, and allow-files permits it. The refusal is enforced at the call site, so a batch, a macro, a view, a trigger action or a CALL/DO body cannot reach the provider under the read-only default.
  • NULL input gives NULL; an empty string is sent. 401 is not retried; 429 and 5xx are retried (three attempts, 250/500 ms). The model is a setting, not a second argument.

    • Vector search#

    Vector similarity search (wave 107b) has two halves. The distance functions are core SQL, so exact top-k works without an extension. The HNSW index is the linked vss extension (CLI/server feature vss, off by default). Vectors are fixed-length ARRAY columns.

    SQL
    CREATE TABLE docs (id INTEGER, v FLOAT[3]);
INSERT INTO docs VALUES (1, [1.0, 2.0, 3.0]), (2, [3.0, 2.0, 1.0]);

SELECT id, array_cosine_distance(v, [1.0, 2.0, 2.0]) AS d
FROM docs ORDER BY d LIMIT 1;

CREATE INDEX docs_vec ON docs USING HNSW (v)
  WITH (metric = 'l2sq', M = 16, ef_construction = 128, ef_search = 64);
-- EXPLAIN now shows: VectorTopK main.docs using docs_vec (l2sq, k = 1)
SET VARIABLE hnsw_ef_search = 128;    -- per session
SET VARIABLE hnsw_exact = true;       -- force brute force
CALL hnsw_compact_index('docs', 'docs_vec');
CALL hnsw_index_stats('docs', 'docs_vec');
    • array_distance(a, b) / array_l2_distance(a, b) is Euclidean (not squared); array_cosine_distance, array_cosine_similarity, array_inner_product and array_negative_inner_product cover the other metrics. Both arguments must be FLOAT[N]/DOUBLE[N] of the same N; INTEGER/BIGINT arrays are refused. A NULL array gives NULL; a NULL element is an error. DOUBLE/mixed inputs compute in f64; FLOAT/FLOAT computes in f32 and returns DOUBLE (pinkdb has no scalar FLOAT; DuckDB returns FLOAT).
    • CREATE INDEX … USING HNSW (col) WITH (metric, M, ef_construction, ef_search, M0) defaults to DuckDB vss's l2sq, M = 16, ef_construction = 128, ef_search = 64 and M0 = 2*M. metric is 'l2sq', 'cosine' or 'ip'. A DOUBLE[N] column is narrowed to f32 in the graph; exact mode keeps f64.
    • The optimizer rewrites exactly ORDER BY <distance>(col, constant) ASC LIMIT k over a native table's indexed column when the distance function matches the index metric and the dimension matches. DESC, a second sort key, a WHERE, or a metric/dimension/function mismatch falls back to the exact scan + top-k heap, never to a wrong answer. The result is approximate when the index is used; hnsw_exact forces exact. A filtered top-k uses the exact path, so it returns up to k rows (DuckDB's index path may return fewer).
    • Deletes are tombstones, an UPDATE of the vector is delete + insert, and CALL hnsw_compact_index('table', 'index') rebuilds without tombstones. Only native tables are indexed: a lake table, a view, a non-ARRAY column or a second index on the same column is refused by name. Index creation follows the ordinary CREATE INDEX privilege; a read-only MCP query session may run top-k but not create or compact an index.
    • The graph is stored in the .pink file (a new footer section), written at checkpoint and loaded on open when the vss package is available; opening without it leaves the graph opaque and falls back to exact. WAL replay applies inserts, updates and deletes. There is no experimental-persistence setting: the graph rides the ordinary checksummed, atomically replaced store section.
    • Differences from DuckDB vss: CALL hnsw_compact_index instead of PRAGMA hnsw_compact_index, SET VARIABLE hnsw_exact/hnsw_ef_search instead of SET hnsw_*, persistence always on, DOUBLE[N] columns accepted (narrowed to f32), and a filtered top-k uses the exact path. array_l2_distance is a pinkdb alias; DuckDB 2.0 names the function array_distance.

    Not supported yet#

    These are real gaps, listed so you can plan around them. Most are scheduled on the roadmap.

    • Correlated subqueries are rejected (uncorrelated subqueries and EXISTS work).
    • MySQL DML spellings — ON DUPLICATE KEY UPDATE and REPLACE INTO are refused by name; write ON CONFLICT … DO UPDATE SET or INSERT OR REPLACE. COPY is accepted as a statement, not as a CTE step.
    • Query forms — FOR UPDATE/FOR SHARE (pinkdb has no row locks; its MVCC already serializes writers), list literals and the LIST type, and slicing a VARIANT (that needs a LIST) — are refused by name. So is a LATERAL subquery that references an earlier FROM item, and (a, b) IN (SELECT ...) (compare the columns one by one). None of them degrades into a generic syntax error.
    • Indexes are equality hash indexes and, with the vss feature, HNSW vector indexes; there is no B-tree/range index yet.
    • Function packs — json, string, math and datetime as core extensions — are queued.
    • File-format extensions — parquet, Arrow and Iceberg — are queued (waves 70–72).
    • Limits today: expression nesting is capped at 24 levels and statement depth at 64 nodes (deeper input is a clean parse error, never a stack overflow); aggregates in ORDER BY need an alias or position; no nested transactions or savepoints.
