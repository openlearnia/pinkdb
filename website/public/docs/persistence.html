Persistence & encryption

Durable single-file storage with a write-ahead log — and optional at-rest encryption behind the encryption feature.

The .pink columnar format

db.save("x.pink") writes every database and table in a single-file columnar format; PinkDb::open("x.pink") loads it back (.save / .open in the REPL). Version 2 (PINKDB02) stores the full multi-database catalog; v1 files (PINKDB01, a flat table list) still load — their tables become the single main database. Views are session-local and never persisted.

use pinkdb::PinkDb;

db.save("x.pink")?;                 // or db.save_snapshot("copy.pink")?
let db = PinkDb::open("x.pink")?;   // plain open

let (db, info) = PinkDb::open_durable_with("x.pink", SyncPolicy::Sync)?;
  • Data is stored per-column in ≤2048-row chunks. Each chunk picks its smallest encoding: integers choose between raw, RLE, and bitpacking (min + width + packed bits); doubles raw or RLE; booleans bitpacked or RLE; strings raw, dictionary (u32 codes), or RLE. NULLs ride in a separate validity bitmap.
  • Round-trips are bit-exact, including -0.0 and NaN payloads; truncated or corrupt files return errors, never panics.
  • 1M-row sales table: 24.5 MB CSV → 14.0 MB .pink, saved in 0.16 s, reopened and queried in 0.25 s.

Write-ahead log and crash recovery

Durable opens add a sidecar write-ahead log. PinkDb::open_durable("x.pink") (the REPL's .open) loads the checkpoint, recovers an interrupted checkpoint, replays x.pink.wal, then logs each committed transaction unit — an autocommit statement individually, BEGIN..COMMIT as one record at COMMIT (a ROLLBACK or conflict abort logs nothing).

  • The WAL format is PINKWAL1 + version 2 + a generation number; rolled generations are named <wal>.<gen>.roll.
  • USE, CREATE DATABASE, and DROP DATABASE are logged like any other mutating statement. Because the WAL is shared by every connection while USE is per-session, records are made self-contained: a USE <db> statement is prepended when the replay session differs, so replay always reproduces each statement in the database it ran in.
  • SyncPolicy::Sync fsyncs every record; Batch fsyncs on flush_wal/checkpoint.
  • Recovery is idempotent, a crash inside recovery re-runs from the same files, and a torn WAL header (a file no longer than one header) is recreated while invalid magic/version on a file that carries records is a hard error.
  • A mid-file framing corruption (short record, bad CRC, or a non-continuous LSN) stops replay at the first bad record; later committed records are dropped and the discarded byte count is reported (RecoveryInfo::truncated_bytes). A CRC-valid record that fails to parse, bind, or execute is a hard error — committed data is never silently dropped.

Checkpoint state machine

A checkpoint writes x.pink.tmp (fsynced, directory fsynced), renames the live WAL to .wal.<gen>.roll, starts a fresh WAL of generation gen + 1, publishes .tmp with an atomic rename, then removes the roll. Recovery never removes anything before the recovered state is durable:

  1. .tmp present and the live WAL still has records: the live WAL is authoritative; .tmp (possibly a partial write) is discarded.
  2. .tmp present and the live WAL is empty/absent/torn: the checkpoint reached its WAL roll, which proves .tmp was fully written, so .tmp is published first and the rolls are removed afterwards.
  3. no .tmp: every roll is already folded into .pink; its generation (and the live WAL generation) must prove that — otherwise recovery refuses rather than delete uncertain records.

Durability notes

  • .save <bound path> checkpoints; the target is compared by filesystem identity, so ./x.pink, absolute paths, and case-only differences compare equal. .save <other> is a plain snapshot and is refused when the target has a sidecar WAL with committed records.
  • .import is made durable by a checkpoint before it returns (and is refused inside a transaction), so an import survives a crash immediately after it acknowledges.
  • A mutating statement that reads a session-local view is refused on durable databases: views are never persisted, so replaying its logged SQL could not rebuild it.
  • A database file is single-writer: no file locking is taken, so run one process per .pink path. The crash-test harness (bench/kill_loop.py) exercises recovery with repeated SIGKILL iterations.

At-rest encryption

At-rest encryption is opt-in: cargo build --features encryption links the audited RustCrypto crates aes-gcm (AES-256-GCM) and argon2 (Argon2id); the default build stays crypto-free and unencrypted files are byte-identical.

use pinkdb::{EncryptionKey, PinkDb};

let key = EncryptionKey::from_passphrase("correct horse battery staple");
db.save_with_key("x.pink", &key)?;                       // encrypted snapshot
let db = PinkDb::open_with_key("x.pink", &key)?;         // decrypts
let db = PinkDb::open_durable_with_key("x.pink", &key)?; // encrypted WAL

The REPL reads PINKDB_KEY from the environment: .save writes encrypted and .open decrypts (the durable WAL uses the same key). Unset, behavior is byte-identical to an unkeyed build. The value must be valid UTF-8: a set-but-non-UTF-8 variable is a hard error (exit 2) instead of a silent fallback to plaintext.

  • The container is a plaintext header (magic PINKENC1, version, cipher id, KDF id + parameters + salt, a random per-container nonce prefix, and an AEAD key-check block) followed by AEAD-sealed payloads: 1 MiB segments for a checkpoint, one unit per WAL record (with the LSN bound into the AAD). The nonce is prefix || counter, with counters unique per container.
  • A keyed open rebuilds the WAL with a fresh random prefix on every open (re-sealing intact records atomically), so a discarded record's (key, nonce, AAD) can never be handed out again. Checkpoint containers end with a terminal zero-length segment, so a container cut at a segment boundary is rejected instead of loading a silently shorter database.
  • The key is a raw 32-byte key or a passphrase stretched with Argon2id (defaults m=19 MiB, t=2, p=1; salt and parameters live in the header, so raising the defaults later keeps old files readable). Header parameters are validated on read against a small multiple of the defaults, so a crafted header cannot make an open burn minutes deriving.
  • A wrong key (or tampered header) fails the key-check block with a clear wrong key error, never “corrupt file”. Encrypted and plaintext artifacts never mix: a keyed open refuses a plaintext checkpoint/WAL and a plaintext open refuses an encrypted one, so a key can never be silently ignored.
  • Nothing but the header is readable in the clear — payloads (rows, SQL text) are always ciphertext.
  • Release binary sizes: pinkdb 2.21 MB default, 2.28 MB with --features encryption (Apple Silicon, thin LTO).
One process per file, still

On an encrypted database, two writers appending under the same container prefix would seal two records under one (key, nonce) — keystream reuse, not merely corruption. The keyed open shrinks but does not remove that race; the single-writer precondition is documented and enforced by convention.
