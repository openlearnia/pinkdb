SQL reference

The SQL surface pinkdb implements today — DDL/DML, joins, CTEs, subqueries, window functions, aggregates, prepared statements and transactions — plus an honest list of what is not supported yet.

DDL and DML

CREATE TABLE t (id BIGINT, name VARCHAR, price DOUBLE);
CREATE TABLE db1.t (...);            -- qualified: any db.table target works
CREATE TABLE t2 AS SELECT ...;       -- CTAS
CREATE TABLE IF NOT EXISTS t (...);  -- IF [NOT] EXISTS on CREATE/DROP TABLE
INSERT INTO t VALUES (1, 'x', 9.5), (2, NULL, 3.0);
INSERT INTO t SELECT ...;            -- INSERT ... SELECT
UPDATE t SET price = price * 1.1 WHERE id > 1;   -- SET exprs see pre-update values
DELETE FROM t WHERE price IS NULL;               -- NULL never matches
BEGIN; UPDATE t SET price = 0; ROLLBACK;         -- flat snapshot transactions
CREATE DATABASE db1;                 -- new, empty database
DROP DATABASE db1;                   -- the last database cannot be dropped
USE db1;                             -- per-session current database (default: main)
DROP TABLE t;  DROP VIEW v;
CREATE VIEW v [(cols)] AS SELECT ...;  -- session-local, rebound per use
CHECKPOINT;                          -- persist + roll the WAL (durable databases)

Declarative constraints are accepted in column and table form (PRIMARY KEY, UNIQUE, NOT NULL, REFERENCES u(x) / FOREIGN KEY ... REFERENCES ..., with an optional CONSTRAINT name prefix):

CREATE TABLE orders (
  id     INTEGER PRIMARY KEY,          -- implies NOT NULL
  code   VARCHAR UNIQUE,
  user_id INTEGER NOT NULL REFERENCES users(id),
  note   VARCHAR,
  CONSTRAINT uq UNIQUE (user_id, code)
);

The declarations are validated at DDL time like DuckDB's (the referenced table must exist and the referenced columns must be exactly one of its PRIMARY KEY or UNIQUE constraints), but they are metadata only: writes never enforce them, and DESCRIBE reports them (PRI/UNI markers plus nullability). The optimizer uses a declared foreign key for conservative FK→PK join elimination — declarations are trusted, not verified.

UPDATE and DELETE are statement-atomic: the statement sees the pre-update values and either applies completely or not at all. BEGIN / COMMIT / ROLLBACK run on a whole-store snapshot: commits to disjoint tables all succeed, and overlapping writes abort the second committer with a write-conflict error instead of a silent lost update.

duckdb conventions

Integer overflow is an error (not a wrap), int / int is a DOUBLE, DOUBLE → integer casts round half away from zero, and SUM over integers is computed exactly. DECIMAL arithmetic follows DuckDB's promotion rules: + - * keep the scale with 38-digit caps, / widens to DOUBLE.

SELECT

SELECT [DISTINCT] expr [AS alias], ...
FROM t [JOIN u ON t.x = u.y]      -- INNER / LEFT / RIGHT / FULL [OUTER], CROSS
  | FROM a JOIN b ON ... JOIN c ON ...   -- multi-way (n-ary) joins
  | FROM db1.t                    -- qualified tables resolve in that database
  | FROM (SELECT ...) AS s         -- derived tables (alias required)
  | WITH w AS (SELECT ...) ...     -- CTEs, incl. WITH w(a, b) AS column aliases
WHERE expr                        -- IS [NOT] NULL, BETWEEN, IN (subquery|list), EXISTS
GROUP BY ... HAVING ...
ORDER BY expr [ASC|DESC] [NULLS FIRST|NULLS LAST], ...   -- ORDER BY 2 positional
LIMIT n [OFFSET m];

COUNT(DISTINCT x)                 -- inside aggregates
SELECT ... UNION [ALL|DISTINCT] SELECT ...
SELECT ... INTERSECT [ALL] SELECT ...
SELECT ... EXCEPT [ALL] SELECT ...
EXPLAIN SELECT ...                -- the query plan
SHOW TABLES;  DESCRIBE t;         -- introspection

Joins

  • INNER, LEFT [OUTER], RIGHT [OUTER], FULL [OUTER] and CROSS joins; join conditions may be arbitrary expressions (non-equi predicates, composite ON a = b AND c = d, and multi-way chains are accepted). Equality predicates still take the hash-join fast path.
  • Outer joins NULL-extend the unmatched side's columns.
  • Cross-database joins work: db1.t JOIN db2.u.

Subqueries and CTEs

  • Derived tables in FROM (alias required), including inside CTEs, views and other subqueries.
  • Scalar subqueries, IN (subquery) and EXISTS (subquery) — uncorrelated only; correlated subqueries are rejected.
  • WITH w AS (...) plus WITH w(a, b) AS (...) column aliases. CTEs shadow unqualified names only; a qualified name never resolves to a CTE.

Set operations and views

  • UNION, INTERSECT and EXCEPT (ALL keeps duplicates, the default deduplicates) with numeric type unification. An ORDER BY/LIMIT after the set operation applies to the whole result; branch-level clauses need parentheses and are unsupported today.
  • CREATE VIEW v [(cols)] AS ... — session-local and per-database; bodies are self-contained (the caller's CTEs never leak in) and rebound per use.

Prepared statements

? placeholders are supported with bind-time type inference against the catalog; a CAST(? AS t) pins a parameter's type. Prepared statements run through the normal statement path with the bound values substituted as SQL literals, so durable stores log the substituted SQL and replay exactly.

use pinkdb::{PinkDb, Value};

let mut db = PinkDb::new();
let mut conn = db.connect();
let stmt = conn.prepare("INSERT INTO t VALUES (?, ?, ?)")?;  // parameter_count() == 3
let bound = stmt.bind(&db, "main", &[Value::Integer(1), Value::from("x"), Value::Null])?;
conn.execute_bound(&bound)?;   // run (repeatable; the bind is reusable)

The server protocol carries the same flow (Prepare / ExecutePrepared frames, protocol v6) and the C ABI has prepare/bind/execute entry points. The Python and Go wrapper ergonomics are queued as a follow-up wave.

Aggregates and window functions

  • Aggregates: COUNT(*) / COUNT(x) / COUNT(DISTINCT x), SUM, AVG, MIN, MAX.
  • Window functions: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, NTILE, FIRST_VALUE, LAST_VALUE, and aggregates OVER with PARTITION BY / ORDER BY / ROWS and RANGE frames (frames are validated; no nesting). The default frame is cumulative with ORDER BY and whole-partition without it.
  • Window functions are allowed in the SELECT list and ORDER BY only (not in WHERE/GROUP BY/HAVING).
  • Aggregates in ORDER BY need a select alias or position; general ORDER BY expressions must be aliases, positions, or GROUP BY keys.

Scalar functions and expressions

  • Math: abs, round, ceil/ceiling, floor, sqrt, pow/power, sign, mod, greatest, least.
  • Strings: upper, lower, length, substr, trim/ltrim/rtrim, replace, concat.
  • CAST(x AS type): the numeric tower both ways (including DECIMAL and INTERVAL from/to text), bool ↔ numeric, varchar parse/format, date ↔ timestamp; bad input and out-of-range narrowing error.
  • COALESCE(a, b, ...), NULLIF(a, b), and LIKE/NOT LIKE with %/_ patterns.
  • Dates and timestamps: year, month, day, hour, minute, second, date_trunc(part, x) (with DuckDB part aliases like dow/doy/isodow/isoweek/ isoyear/week/quarter), extract(part FROM x)/date_part, and epoch/epoch_ms.
  • CASE WHEN c THEN v ... [ELSE e] END and the simple CASE x WHEN v ... form. NULL conditions never match; result types unify like COALESCE.
  • Extensions can add scalar functions at runtime — see Using extensions.

Date and interval operations: date ± integer adds/subtracts days, date - date yields BIGINT days, date ± interval and interval ± interval work with DuckDB's month-end clamping, and intervals scale with *// by numbers. CSV import auto-detects YYYY-MM-DD as DATE and YYYY-MM-DD HH:MM:SS[.f] as TIMESTAMP.

Coercion rules

  • INTEGER → BIGINT → DOUBLE; DECIMAL participates with DuckDB's width/scale promotion (string and numeric input coerce at INSERT/CSV/CAST boundaries).
  • int / int → DOUBLE (the DuckDB rule); DECIMAL / DECIMAL widens both sides to DOUBLE. % is integer-only.
  • Integer overflow is an error, like DuckDB (+/-/*, negation, abs, date ± n, narrowing casts); SUM over integers is exact and errors only when the final value does not fit BIGINT.
  • Integer division/modulo by zero is an error; 0.0 float division is IEEE.
  • Mixed DATE/TIMESTAMP comparison is rejected; timestamps never mix with integers — use date ± interval.

Three-valued logic

  • NULL fails WHERE: a comparison with NULL is never true.
  • COUNT(x), SUM and AVG skip NULLs; COUNT(*) counts rows.
  • NULL group keys group together; NULL join keys never match.
  • LEFT/RIGHT/FULL joins NULL-extend the unmatched side's columns.
  • CASE conditions that evaluate to NULL never match.

Databases and sessions

Databases are named, case-insensitive namespaces (main by default). A session — the embedded PinkDb, or each Connection — has a current database; unqualified table names resolve there. USE db switches it and never affects other sessions: the shared store is untouched.

  • db.table qualifies any table reference in FROM/JOIN, INSERT, UPDATE, DELETE, CREATE TABLE, DROP TABLE, CREATE VIEW and DROP VIEW.
  • Three-part column references (db.table.col) are not supported — use an alias (SELECT x.col FROM db.table AS x).
  • Views are per-database and session-local: created in the current database and resolved there, with their bodies resolving unqualified names in that database.
  • DROP DATABASE refuses the last database and switches a session that was using it to main (or the first remaining database). CREATE/DROP DATABASE and LOAD EXTENSION are refused inside a transaction.
  • USE, DATABASE, LOAD, EXTENSION and LEFT/RIGHT/OUTER/FULL/CROSS are reserved words; quote identifiers to use them as names ("use" works).

Not supported yet

These are real gaps, listed so you can plan around them. Most are scheduled on the roadmap.

  • Correlated subqueries are rejected (uncorrelated subqueries and EXISTS work).
  • Indexes (CREATE INDEX), materialized views and stored procedures are planned (waves 42–44).
  • Function packs — json, string, math and datetime as core extensions — are queued.
  • File-format extensions — parquet, Arrow and Iceberg — are queued (waves 70–72).
  • Limits today: expression nesting is capped at 24 levels and statement depth at 64 nodes (deeper input is a clean parse error, never a stack overflow); aggregates in ORDER BY need an alias or position; no nested transactions or savepoints.
