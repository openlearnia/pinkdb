Server

pinkdb-server is a separate workspace crate (so the core stays lean): a TCP server plus a blocking client over a compact framed binary protocol. One thread per connection, zero async, no external dependencies.

Build and run

# in-memory server on 127.0.0.1:5433
cargo run --release -p pinkdb-server

# durable server: same checkpoint + WAL guarantees as the embedded path
cargo run --release -p pinkdb-server -- --file sales.pink

# explicit bind address and port (0 picks an ephemeral port)
cargo run --release -p pinkdb-server -- --host 127.0.0.1 --port 5433

The full flag list:

Usage: pinkdb-server [--host HOST] [--port PORT] [--file PATH.pink]
        pinkdb-server [--host HOST] [--port PORT] --catalog CATALOG --data DIR
                     [--max-connections N] [--idle-timeout SECS]
                     [--allow-load-extension]

  --host HOST            bind address (default 127.0.0.1)
  --port PORT            TCP port; 0 picks an ephemeral port (default 5433)
  --file PATH            durable database (checkpoint + WAL); in-memory when omitted
  --catalog CATALOG      keep the store in a pink-lake lake (wave 96b): engine
                         metadata in the catalog database, rows in --data
                         (pink:PATH, sqlite:PATH, or a postgres: URL; the
                         backends are build features)
  --data DIR|s3://…      the lake's data location; required with --catalog
  --max-connections N    concurrent clients served (default 128)
  --idle-timeout SECS    disconnect clients idle this long; 0 = never (default 300)
  --allow-load-extension let clients run LOAD EXTENSION (loads native code on
                         the server host; off by default)

On startup the server prints its listening address and runs until terminated. Both durable modes share the embedded durability path: with --file, committed transactions are replayed from the WAL on the next start, and rows acknowledged to a client survive a server crash. --file and --catalog are mutually exclusive; --data requires --catalog; without either the server is in memory.

Stateless mode: metadata in the catalog, rows in a lake

With --catalog the server holds no durable state of its own: the engine catalog — databases, table definitions with constraints and defaults, views, macros, materialized views, procedures, triggers, users/roles/grants, loaded extension sources — goes into the lake catalog database, and the rows go into the lake data files. Restart the server (or start it on another machine) on the same catalog and data URL and you get the identical store.

# metadata in the catalog database, rows in ./warehouse
cargo run --release -p pinkdb-server -- \
    --catalog sqlite:./warehouse.catalog --data ./warehouse

# S3 data, and a Postgres or SQLite catalog with the matching features
cargo run --release -p pinkdb-server --features lake-s3 -- \
    --catalog sqlite:./warehouse.catalog --data s3://bucket/warehouse

The ducklake_* tables stay exactly what DuckDB expects; the engine catalog is one row of pinkdb_engine_catalog beside them, an image of the engine's own catalog with the row pages omitted. Every committed statement publishes at most one catalog transaction — data files, lake delta and metadata image together — and a metadata-only statement (CREATE VIEW, GRANT, LOAD EXTENSION) publishes the image without minting a lake version. Passwords are still stored only as Argon2id hashes.

Phase 1 serves one server per catalog: a lease row with a 2 s heartbeat makes a second server fail with already served by … until the first stops or its heartbeat goes stale (6 s), which is how a crashed server is taken over. Shared catalogs need fencing tokens and cache invalidation, scoped as phase 2 in docs/wave-96b-plan.md.

The mode needs the catalog feature; the default build links no lake, SQLite, Postgres or S3 code. A backend the build lacks is refused with the feature to rebuild with (catalog, catalog-sqlite, catalog-postgres, lake-s3).

Remote CLI mode

cargo build --release -p pinkdb-cli --features client
./target/release/pinkdb --host 127.0.0.1:5433

Every SQL statement is sent to the server and rendered with the same box-drawn output and timing line as the embedded REPL. SQL — including USE, CREATE DATABASE and BEGIN/COMMIT — works unchanged.

Protocol

One TCP connection is one session. Every message is a frame: a u32 little-endian length prefix + a u8 message type + body. The protocol version is 6 (Hello is the required first request; a mismatched version is rejected with a clear error).

DirectionFrames
Requests Hello { protocol_version }, Execute { sql }, Prepare { sql }, ExecutePrepared { handle, params }, Ping
Responses HelloOk { server_version, protocol_version }, Prepared { parameter_types }, Pong, and per statement one result group: ResultSet { names, types } → chunked Rows { count, columns, values... } → Done { kind }
Batch terminator exactly one BatchDone { statements } after a successful Execute batch, so neither side parses SQL to count statements; a failing statement ends the batch with one Error { message } and the connection stays open

Rows are encoded as typed values (a tag byte plus payload for NULL/BOOL/I32/I64/F64/VARCHAR/DATE/TIMESTAMP/DECIMAL/INTERVAL), with a DataType tag byte. Prepared statements are connection-local handles (capped at 1024 per connection; unknown handles and bind/type errors are ordinary errors). The client reconstructs pinkdb's public QueryResult/Value types, so remote results render exactly like local ones. Each connection gets its own Connection, so USE and transactions are isolated per TCP client.

Robustness

  • 16 MiB stack per connection thread. The engine's depth guards (24 levels of nesting, 64 AST nodes) reject hostile statements before they can recurse.
  • Transient accept errors never stop the server. EMFILE/ENFILE/ECONNABORTED and friends are logged and retried with a 10 ms → 1 s backoff, so an fd spike no longer kills the process.
  • 128 concurrent connections by default; over the cap the server sends a best-effort Error frame and closes, bounding fds and threads.
  • Panics are isolated. A panic while executing one statement is caught, logged and reported as an Error frame; the connection and every other client stay alive.
  • Frames are not trusted. Frames larger than 64 MiB are rejected before allocation, and every inner length is validated against the bytes remaining in the frame; bodies are buffered as bytes arrive, never pre-sized from the length prefix.
  • Idle timeout (default 300 s). A client that stalls between requests or while reading a result is disconnected, so stalled peers cannot pin the connection cap.

Security posture

Authenticated with RBAC — TLS is opt-in

A fresh server with an empty catalog trusts every connection (it says so at startup); once a user exists, connections log in and every statement is checked against that user's grants — table SELECT/INSERT/UPDATE/DELETE, database CREATE and global ADMIN. A build with the tls feature can encrypt the transport (--tls-cert/--tls-key; clients use --tls + --tls-ca-cert) — without it, login passwords cross the wire in cleartext. The server binds 127.0.0.1 by default: keep it on localhost or a trusted network. Embedded use (Rust API, FFI, wasm) is trusted by design and does not consult the catalog.

  • LOAD EXTENSION is refused for remote clients unless the server runs with --allow-load-extension: the statement makes the server process load and run a native library from its own filesystem, which without authentication would be remote code execution. WAL replay at startup still re-loads extensions a durable database recorded.
  • pinkdb-server has no encryption-key option: its --file must be a plaintext database (an encrypted one is refused at startup), and PINKDB_KEY is ignored by the server.
  • In remote CLI mode, PINKDB_KEY is reported as inert instead of being silently ignored.
