Guide: S3 / R2 lakes

Put a lake in object storage and read it back: AWS S3, Cloudflare R2, MinIO or any S3-compatible endpoint, using the blocking SigV4 client behind the optional s3 feature.

1. Build with lake + S3

# pinklake over object storage (4.7 MB binary)
cargo build --release -p pinkdb-cli --features pinklake,s3

# vortexlake over object storage (~47.3 MB binary)
cargo build --release -p pinkdb-cli --features vortexlake,s3
# `--features s3` alone adds the storage client but no `.lake` commands

2. Configure credentials

Everything comes from the environment — no profiles, no instance metadata. For Cloudflare R2:

export AWS_ACCESS_KEY_ID=<r2-token-key-id>
export AWS_SECRET_ACCESS_KEY=<r2-token-secret>
export AWS_ENDPOINT_URL=https://<account>.r2.cloudflarestorage.com
export AWS_REGION=auto

For AWS S3 the endpoint/region variables are optional (the client derives them). MinIO uses its own endpoint URL plus path-style addressing, which is the default with a custom endpoint (AWS_S3_FORCE_PATH_STYLE=1 forces it). A dotted bucket name needs path-style addressing.

The bucket must already exist

pinkdb never creates buckets. Create my-bucket (and an R2/S3 API token with read/write access) first; an unknown bucket fails with the bucket does not exist (or is not visible to these credentials).

3. Save, list, reopen

pinkdb> .import sales_1m.csv sales
pinkdb> .lake save s3://my-bucket/lakes/demo
pinkdb> .lake versions s3://my-bucket/lakes/demo
pinkdb> .lake tables   s3://my-bucket/lakes/demo
pinkdb> .lake info     s3://my-bucket/lakes/demo
# a fresh process, reading straight from the bucket
./target/release/pinkdb

pinkdb> .lake open   s3://my-bucket/lakes/demo
pinkdb> .lake attach s3://my-bucket/lakes/demo
pinkdb> SELECT COUNT(*) FROM sales;   -- statistics fast path, 0 column decodes

Every write is a single atomic PutObject; a reader sees the old or the new bytes, never a mix. Snapshot publication is create-only (If-None-Match: *) and the catalog replace is conditional (If-Match: <etag>), so two racing saves cannot fork the version chain — on AWS S3 and R2 those conditionals are evaluated atomically with the write.

4. The same lake from Rust

use pink_lake::{Lake, save_store_url};
use pinkdb::PinkDb;

let mut db = PinkDb::new();
db.execute("CREATE TABLE t (a INTEGER); INSERT INTO t VALUES (1), (2);")?;

let version = save_store_url(&db, "s3://my-bucket/lakes/demo")?;
let mut lake = Lake::open_url("s3://my-bucket/lakes/demo")?;
let tables = lake.tables()?;

// explicit configuration instead of the environment:
// let config = S3Config::new("my-bucket").with_prefix("lakes/demo")
//     .with_region("auto").with_endpoint(endpoint).with_credentials(key, secret);
// let lake = Lake::open_s3(config)?;

Gotchas

  • One PutObject per object — no multipart uploads, so a single table's data file must be ≤5 GiB; the client refuses larger bodies before sending. No lifecycle rules, no server-side copy, no lake-side GC: old versions stay, exactly like local.
  • Concurrent writers are unsupported unless the endpoint enforces conditionals. AWS S3 and R2 do. On an endpoint that rejects conditional writes (HTTP 501 or NotImplemented), writes are refused by default; PINKDB_S3_ALLOW_DEGRADED=1 accepts a check-then-put fallback that is single-writer only.
  • Retries are conservative. 429/503 are retried for every request; transport errors only for idempotent requests. An ambiguous conditional PUT is never retried — after a failure, reopen the lake and check .lake versions before retrying.
  • Requests time out after 120 s (connect + transfer), and the host clock must be within S3's ~15-minute SigV4 skew.
  • Lake data is plaintext: PINKDB_KEY does not encrypt lake objects. Credentials come only from the environment or an explicit S3Config.
  • PINKDB_S3_ALLOW_HTTP=1 permits a plain http:// endpoint for local test servers — never for real credentials.
