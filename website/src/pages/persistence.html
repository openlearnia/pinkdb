Persistence & encryption

Single-file columnar storage, a write-ahead log for durability, multi-process writers, and optional at-rest encryption — all in one database file you can copy anywhere.

The .pink columnar format

db.save("x.pink") writes every database and table to one file; PinkDb::open("x.pink") loads it back (.save / .open in the REPL). The current format is v5 (PINKDB05), ending in a CRC-32 of the whole image. Views are session-local and are never persisted.

use pinkdb::PinkDb;

db.save("x.pink")?;                 // write the store
let db = PinkDb::open("x.pink")?;   // plain open (no WAL)

// durable: checkpoint + sidecar WAL, replayed on open
let (db, info) = PinkDb::open_durable_with("x.pink", SyncPolicy::Sync)?;
  • Data is stored per column in ≤2,048-row chunks. Each chunk picks its smallest encoding: integers choose between raw, RLE, bitpacking and DELTA_BITPACK; doubles raw, RLE or ALP (bit-exact exceptions); booleans bitpacked or RLE; strings raw, dictionary, RLE or DICT_BITPACK; DECIMAL rides as 128-bit fixed point and INTERVAL as months/days/microseconds.
  • v5 adds the DECIMAL/INTERVAL dtype tags and an optional per-table constraint section (declarative PRIMARY KEY / UNIQUE / FOREIGN KEY / NOT NULL metadata, gated by a flags word) — a constraint-free v5 body is byte-identical to v4.
  • An LZ frame (a hand-rolled LZ77, no dependencies) wraps a chunk when it saves space — text corpora shrink 3–5×: a JSON-like corpus went 70.4 MB → 15.7 MB, logs 118.7 → 44.5 MB, URLs 103.5 → 41.4 MB. Random data and numeric tables stay byte-identical.
  • Round-trips are bit-exact, including -0.0 and NaN payloads. Truncated or corrupt files return errors, never panics: a damaged file fails its CRC-32 before any decoding.
  • Measured: a 1M-row sales table (24.5 MB CSV) becomes 2.68 MB .pink, saved in 0.03 s and reopened in 0.03 s; the same table at 10M rows is 26.8 MB.
  • Files are forward-incompatible on purpose: a newer format is refused with a clean “newer format” error, never guessed at. Older files stay readable: v1 (a flat table list), v2 (the databases layout), v3 (v2 + the CRC trailer) and v4 (the flags word + typed codecs) all load; v1 tables become the single main database.

Durable databases and the WAL

A durable open — PinkDb::open_durable("x.pink"), or the REPL's .open — loads the checkpoint, recovers an interrupted checkpoint, replays the sidecar x.pink.wal, and then logs each committed transaction unit: an autocommit statement individually, BEGIN..COMMIT as one record at COMMIT (a ROLLBACK or conflict abort logs nothing).

  • The WAL format is PINKWAL1 version 4: a generation, a fresh 16-byte wal_id per file creation (so a replaced file is never mistaken for the old one), a header CRC, two 24-byte commit slots, and a per-frame touched-object set (the new v4 payload — what optimistic multi-writer commits validate against). Rolled generations are named <wal>.<gen>.roll.
  • Recovery is idempotent: a mid-file framing corruption stops replay at the first bad record and reports the discarded byte count. A CRC-valid record that fails to parse, bind or execute is a hard error — committed data is never silently dropped. A failed WAL append is fail-stop: later statements are refused until reopen, which recovers exactly the durable prefix.
  • SyncPolicy::Sync fsyncs every record; SyncPolicy::Batch fsyncs on flush_wal/checkpoint.
  • USE, CREATE DATABASE and DROP DATABASE are logged like any other mutating statement; a record is made self-contained (a USE <db> prefix) whenever the replay session could differ.

Multi-process writers

Durable databases are multi-process: any number of local processes may open the same database read-write. Writers serialize on a short-held per-operation write lease — an exclusive flock on x.pink.lock — held from refresh through execute, append, fsync and publish (or from BEGIN to COMMIT/ROLLBACK for transactions). The OS releases the lease on exit or crash, so there is no stale-lock cleanup.

  • Readers never block. Each process keeps a full in-memory store and checks the lock file's publication epoch with one pread; only when it changed does it replay the WAL frames it has not applied. Refresh runs at statement boundaries and before BEGIN — never mid-statement.
  • A busy database waits up to the busy timeout — 5 s by default — then fails with a clear database is busy error. Configure it with PINKDB_BUSY_TIMEOUT_MS (CLI), DurableOpenOptions.busy_timeout or Database::set_busy_timeout.
  • Cross-process transactions serialize on the lease; BEGIN..COMMIT runs on a private snapshot, committing writes to the WAL under the lease.
  • Optimistic commits. A commit validates its frame's touched-set (and, for writes computed from reads, the read-set) against what other writers published since its snapshot: disjoint writes commit, overlapping ones abort with a write conflict. The CLI retries a conflicting one-call transaction automatically (PINKDB_TXN_RETRIES, default 3; 0 reports the first conflict instead) — see the multi-process guide.
  • An open on a filesystem that reports locking unsupported fails closed (LockMode::Required, the default); LockMode::UnsafeSingleProcess is the explicit opt-out. There is no NFS/SMB detection, and Windows is untested.

There is a walkthrough in Guide: multi-process writers.

Checkpoints

A checkpoint writes x.pink.tmp (fsynced, directory fsynced), rolls the live WAL to .wal.<gen>.roll, starts a fresh WAL of generation gen + 1, publishes .tmp with an atomic rename, then removes the roll. Recovery never removes anything before the recovered state is durable:

  1. .tmp present and the live WAL still has records: the live WAL is authoritative; .tmp (possibly a partial write) is discarded.
  2. .tmp present and the live WAL is empty/absent/torn: the checkpoint reached its WAL roll, which proves .tmp was fully written, so .tmp is published first and the rolls are removed afterwards.
  3. No .tmp: every roll is already folded into .pink; its generation must prove that — otherwise recovery refuses rather than delete uncertain records.
  • CHECKPOINT (SQL, from any front-end) persists the store and rolls the WAL; it is a no-op in memory and is refused inside a transaction. A committed write checkpoints automatically once the WAL passes 64 MiB (set_auto_checkpoint_bytes, None disables).
  • A checkpoint refreshes from other processes first, under the lease, so it can never publish a state that omits another process's committed records.
  • .save <bound path> checkpoints; the target is compared by filesystem identity, so ./x.pink, absolute paths and case-only differences compare equal. .save <other> is a plain snapshot and is refused when the target has a sidecar WAL with committed records.
  • .import is made durable by a checkpoint before it returns (and is refused inside a transaction), so an import survives a crash immediately after it acknowledges.

Encryption

At-rest encryption is opt-in: cargo build --features encryption links the audited RustCrypto crates aes-gcm (AES-256-GCM) and argon2 (Argon2id). The default build stays crypto-free and unencrypted files are byte-identical.

use pinkdb::{EncryptionKey, PinkDb};

let key = EncryptionKey::from_passphrase("correct horse battery staple");
db.save_with_key("x.pink", &key)?;                       // encrypted snapshot
let db = PinkDb::open_with_key("x.pink", &key)?;         // decrypts
let db = PinkDb::open_durable_with_key("x.pink", &key)?; // encrypted WAL
  • The container is PINKENC1 (version 2): a plaintext header with the KDF parameters, salt, a per-container nonce prefix and an AEAD key-check block, followed by AEAD-sealed payloads. WAL containers carry a small plaintext publish block so the multi-process refresh works. Nothing but the header is readable in the clear — rows and SQL text are always ciphertext.
  • The key is a raw 32-byte key or a passphrase stretched with Argon2id (defaults m=19 MiB, t=2, p=1; parameters live in the header, so raising the defaults later keeps old files readable). Header parameters are validated on read, so a crafted header cannot make an open burn minutes deriving.
  • A keyed open rebuilds the WAL with a fresh random prefix on every open, so a discarded record's (key, nonce) pair is never handed out again.
  • A wrong key (or a tampered header) fails the key-check block with a clear wrong key error, never “corrupt file”. Encrypted and plaintext artifacts never mix: each refuses the other, so a key can never be silently ignored. Without the feature, opening an encrypted file reports file is encrypted; build with the encryption feature.
  • In the REPL, PINKDB_KEY drives .save and .open (the durable WAL uses the same key). See Guide: encrypted databases.

Known limits

  • No nested transactions or savepoints; BEGIN..COMMIT uses whole-store snapshots with write-conflict detection (snapshot isolation, no predicate tracking).
  • A durable commit refuses statements that read a session-local view or an attached lake table — neither is persisted, so the logged SQL could not rebuild it.
  • The lake is plaintext: PINKDB_KEY does not encrypt lake data files. Encrypted databases and lake snapshots are separate stories.
  • Multi-process locking assumes flock is honored; network filesystems are not detected and Windows is untested.
