The pinkdb agent

pinkdb contains no model code. The MCP bridge lets an outside agent run the tools; the pinkdb agent goes one step further and runs the loop itself — asking a model what to run, executing the warehouse tools through the host, and keeping the whole conversation in the store, so a killed run resumes and a finished one can be forked. It is a native extension (pinkdb-agent), so the engine, the CLI and the server still contain no model or HTTP client code.

Setup

# build the agent next to the CLI
cargo build --release -p pinkdb-cli -p pinkdb-agent

# export the provider's own key; pinkdb never reads a .env file itself
set -a; . ./.env; set +a
# …or:
export ZAI_API_KEY=…

# ask one question against a store, naming the provider
./target/release/pinkdb --agent sales.pink "Who are the top 3 customers by revenue?" \
    --agent-provider zai
macOS 27: "mis-aligned LINKEDIT string pool"

macOS 27's loader refuses a library whose symbol string table is not 8-byte aligned, and the linkers (Apple's ld and LLD) can write one; whether a build hits it changes with the code. The library is otherwise fine: run python3 scripts/macos-align-linkedit.py target/release/libpinkdb_agent.dylib once after building (it does nothing to a library that is already aligned), and LOAD EXTENSION names the script when it sees the error.

Providers

There is no default provider. Every run names one — provider <name> on the run, --agent-provider on the command line, or PINKDB_AGENT_PROVIDER — and a run that names none fails with no provider: pass provider <name> or set PINKDB_AGENT_PROVIDER (one of: …). The agent never guesses a provider from whichever key happens to be exported. The built-in table lives in pinkdb-llm, a crate the agent-memory extension will share:

“—” means the run must name a model (model <name>, --agent-model or PINKDB_AGENT_MODEL); a run argument beats the environment. The protocol appends /chat/completions (OpenAI-compatible) or /messages (the Anthropic Messages API) to the root. Each provider's root is overridden only by its own variable (PINKDB_AGENT_ANTHROPIC_BASE_URL points anthropic at a proxy or gateway and moves nobody else); PINKDB_AGENT_BASE_URL is custom's alone and every built-in provider ignores it, so a root exported for a custom endpoint can never receive ANTHROPIC_API_KEY. .agent providers prints the table with each row's override variable, the root in effect, and key: set, key: missing or no key needed — never a key or any part of one.

Both protocols stream SSE parsed by hand. 429, 5xx and Anthropic's 529 (overloaded) are retried three times with backoff; reasoning traces (reasoning_content, thinking_delta) are dropped, never recorded or sent back. Anthropic requests hoist the system prompt into system, send tool calls and results as tool_use / tool_result blocks with alternating roles, and carry max_tokens (8192; PINKDB_AGENT_MAX_TOKENS overrides it) with no extended thinking. --agent loads libpinkdb_agent from the install directory, like --mcp; --agent-allow-writes and --agent-allow-files start the run under a looser policy.

Key isolation. A key variable is only ever read for, and sent to, its own provider: ANTHROPIC_API_KEY never reaches z.ai, a z.ai key never reaches OpenRouter, and PINKDB_AGENT_API_KEY belongs to custom alone. The key goes in the header its protocol names (Authorization: Bearer or x-api-key) and nowhere else.

The key never lands anywhere. It is not in a table, not in the WAL, not in a log line, not in an error and not in Debug output — the extension holds it in memory for the run — and there is no SET that reaches it. A 401 or 403 stops the run with “the zai provider rejected the API key (HTTP 401); check ZAI_API_KEY or Z_API_KEY”, which names the provider and its variable and nothing else.

Commands

.agent ask "<question>" [provider <name>] [model <name>] [allow-writes] [allow-files] [max-steps N] [tokens N]
.agent resume <session> [provider <name>] [model <name>]
.agent sessions
.agent show <session>
.agent fork <session> <step> [provider <name>] [model <name>] ["<new question>"]
.agent providers

Each one dispatches to the loaded extension; without it the run commands print the LOAD EXTENSION hint (and .agent rows|cols|cell|budget|timeout|hint keeps its wave-99 meaning). A resume keeps the policy and budgets the session started with, because the transcript records them, and continues on the session's recorded provider and model unless it names others.

The tools

The agent has the same eight warehouse tools as the MCP bridge — query, describe, tables, databases, explain, lake_tables, lake_versions, lake_changes — from one shared crate (extensions/warehouse-tools), so the two cannot drift. There is no shell, no file editing, no web fetch and no LOAD EXTENSION: a data agent, not a coding agent. Results are the wave-99 compact Markdown with truncation notices; the host, not the model, enforces the row, byte and time budgets.

Two policies

The model's tool calls run through the host statement callback under the same read-only policy as MCP: only queries, DESCRIBE, SHOW and EXPLAIN, with no external files or URLs, until the run is started with allow-writes. File access stays a separate decision (allow-files).

On top of that, the agent's own database is off-limits to the model even with allow-writes: pinkdb_agent holds the transcript the run resumes from, so a prompt injection that talks the model into INSERT INTO pinkdb_agent.messages … must fail. The extension writes that transcript through a second, internal channel that may only write pinkdb_agent — so it cannot touch user data either. Both directions are tested.

Sessions

A session lives in the pinkdb_agent database of the store it ran against: sessions, messages, tool_calls, checkpoints and usage. Every step — the model turn, its tool calls, their results and the next checkpoint — commits together, so a kill -9 costs at most the step in flight. .agent resume re-requests an interrupted stream, reuses every recorded tool result, and re-runs only the read-only (replay-safe) tools.

.agent fork <session> <step> copies the transcript up to that step into a new session, records origin and origin_step, leaves the original untouched, and optionally continues the fork with a new question. A fork may switch provider: the transcript is stored provider-neutral, so a z.ai session forked onto Anthropic is the same messages re-encoded for the other protocol (a switched provider without a model gets its own default, never the old provider's model). sessions records the provider and usage the provider and model of every step, so comparing two providers' cost is a GROUP BY. Because the history is plain SQL, SELECT * FROM pinkdb_agent.tool_calls is the audit trail and a client can watch a run with CDC.

pinkdb> .agent sessions
pinkdb> .agent show a1f2c3d4e5f6
pinkdb> .agent fork a1f2c3d4e5f6 2 provider anthropic "Now break that down by region"

Budgets

A run stops at 20 steps by default, after an optional token budget, or when a statement hits the wave-99 ExecLimits; all three are set per run (max-steps N, tokens N, the .agent timeout|budget settings) and the transcript records which limit stopped it. Token usage is summed from the provider's usage chunks and committed per step.

Under the hood

The command entry point is an additive ABI capability (minor 4): an optional pinkdb_ext_command(api, host_ctx, args, sink, sink_ctx) export, detected by symbol presence, whose sink callback streams the answer or a diagnostic, plus a PinkdbHostApi::execute_internal field that answers machine-readable JSON rows for the extension's own reads. Every v1 and minor-2 extension — and all four SDK smokes — load unchanged. The provider client is blocking ureq with rustls (the same crate and features pinkdb-httpfs locks) with a hand-written SSE parser: no async runtime, no client crate, no new third-party crate in Cargo.lock. Measured on one machine, the release binaries grew by 0.76% (pinkdb, 5,035,312 → 5,073,504 bytes) and 0.03% (pinkdb-server, 4,668,016 → 4,669,264 bytes); the agent itself is 2,471,632 bytes. The second protocol and the provider table (wave 106b) added 76,272 bytes: the release libpinkdb_agent.dylib is 2,548,240 bytes, still with no new crate.

Tests run against a recorded mock provider — a localhost server replaying checked-in SSE fixtures in both protocols — so CI is deterministic and free: a single answer, a multi-step tool loop, arguments split across chunks, an interrupted stream, 429/529-then-success, 401, kill-and-resume, fork (also from z.ai onto Anthropic), the refusals, key isolation with four sentinels exported at once, a leftover PINKDB_AGENT_BASE_URL mock that a provider anthropic run never contacts, provider precedence and a TPC-H top-3 question end to end. The live runs are opt-in and name their provider: PINKDB_AGENT_LIVE=1 cargo test -p pinkdb-cli --test agent_run -- --ignored runs the z.ai one with ZAI_API_KEY and the Anthropic one with ANTHROPIC_API_KEY.
