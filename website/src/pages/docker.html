Docker

The public multi-arch image contains pinkdb-server (TLS + async transport) and the pinkdb CLI. It runs as a fixed non-root user, keeps the durable database on a /data volume, and has a protocol-level health check — no curl, shell or extra tools in the probe. Images are published to GHCR from v* tags for linux/amd64 and linux/arm64.

Quick start

# server on 0.0.0.0:5433, durable /data/pinkdb.pink, non-root
docker run -p 5433:5433 -v pinkdb-data:/data ghcr.io/openlearnia/pinkdb

# the image's own CLI, remote mode, against the published port
docker run --rm -it ghcr.io/openlearnia/pinkdb pinkdb --host host.docker.internal:5433

The server is durable by default: rows acknowledged to a client survive a container restart because the checkpoint and WAL live on the named volume. docker stop/docker rm the container without removing the volume to keep the data. The entrypoint passes through when the first argument is pinkdb, so the CLI and the server share one image.

docker run --rm -it ghcr.io/openlearnia/pinkdb pinkdb
docker run --rm ghcr.io/openlearnia/pinkdb pinkdb --version

Health check

The image's HEALTHCHECK runs

pinkdb-server --health-check

which connects, speaks the protocol Ping, prints healthy and exits 0, or exits 1 within a short timeout. Without an explicit address it reads PINKDB_HEALTHCHECK_ADDR, then PINKDB_HOST/PINKDB_PORT, then 127.0.0.1:5433; a wildcard bind is mapped to loopback. PINKDB_HEALTHCHECK_TIMEOUT_MS bounds the probe (default 2000 ms). The same probe is available from the shell, and a dead port is a nonzero exit:

docker exec <name> pinkdb-server --health-check
docker exec <name> pinkdb-server --health-check 127.0.0.1:1   # exit 1

If you override the port with a CLI flag rather than PINKDB_PORT, pass a matching --health-cmd or set PINKDB_HEALTHCHECK_ADDR, because the built-in probe follows the environment.

Security posture

Non-root, but authentication is per store

The container runs as UID/GID 10001 and only /data is writable by convention. That is OS isolation, not database authentication: the served store decides. A fresh store with no users trusts every connection and says so at startup; once a user exists, connections must log in and every statement is checked against that user's grants. LOAD EXTENSION and COPY … TO stay off unless the matching opt-in and root are set.

-- bootstrap over the wire; the catalog, not the image, is the switch
CREATE USER alice PASSWORD 'a long passphrase';
GRANT ADMIN TO alice;

Publishing 5433 to an untrusted network before the store has users is remote shell-level access to the database; bind to a trusted network first. For encrypted transport, mount a certificate/key pair and start the server with PINKDB_TLS_CERT/PINKDB_TLS_KEY (TLS is supported by the default sync transport only; the async transport refuses those flags). TLS identifies the server, not the client — login is what gates statements.

Build the image yourself

docker build --build-arg VARIANT=default -t pinkdb:default .
docker build --build-arg VARIANT=lake -t pinkdb:lake .
scripts/docker/smoke.sh --image pinkdb:default --variant default
scripts/docker/smoke.sh --image pinkdb:lake --variant lake

The Dockerfile builds both binaries from source in a pinned Rust builder and publishes the smaller runtime that passes the smoke test. The smoke test starts the container, waits for healthy, runs the image's own CLI in remote mode (pinkdb --host), creates/inserts/selects, restarts the container to prove persistence, checks --health-check exit codes, and on the lake variant runs .lake save/.lake open on the volume. See Install for the non-container binaries and Server for the full protocol and security reference.
