Roadmap

What pinkdb ships today, what is being worked on, and what is planned. This page is the product view; the change-by-change engineering log — with measurements and benchmark notes — lives in ROADMAP.md on GitHub, and the wave-by-wave summary in the changelog.

Shipped

  • Analytical engine

    Columnar vectors, vectorized execution over ≤2,048-row chunks, and parallel operators. CSV import with per-column type inference.

  • SQL surface

    DDL/DML, inner/outer/full/cross and multi-way joins, CTEs, derived tables and uncorrelated subqueries, window functions (lag/lead/ ntile/frames), aggregates, CASE/CAST/COALESCE/LIKE, dates and timestamps, DECIMAL and INTERVAL, set operations, views, snapshot transactions, transactions, multiple databases, EXPLAIN/SHOW/ DESCRIBE, and prepared statements (? placeholders with a bind API). Differentially tested against DuckDB.

  • Keys

    Declarative PRIMARY KEY/UNIQUE/NOT NULL/ REFERENCES constraints, validated at DDL time like DuckDB and reported by DESCRIBE. Metadata-only (never enforced on writes), with conservative FK→PK join elimination in the optimizer.

  • Persistence

    Single-file .pink v5 columnar format (delta, dictionary, ALP and LZ encodings; constraint metadata; DECIMAL/INTERVAL); bit-exact round trips; a write-ahead log (v4, touched-object sets) with atomic checkpoints and crash recovery.

  • Multi-process databases

    Any number of local processes can open a durable database read-write; writers serialize on a per-operation write lease, readers refresh from the WAL, and optimistic commits validate their touched/read sets — conflicting ones abort or retry (bounded), never a silent lost update.

  • At-rest encryption

    Optional PINKENC1 containers — AES-256-GCM with Argon2id key derivation — covering the checkpoint and the WAL.

  • Lake layer

    JSON catalog (format_version 4) plus immutable per-version manifests; incremental commits (append-only data files and positional deletes, never rewriting published files), writable attachments (.lake attach … write + .lake commit), time travel (AT (VERSION => n) / AT (TIMESTAMP => ts)), per-version records (.lake snapshots), retry/backoff parity with DuckLake, and statistics-fast read-only attach. Vortex or lean .pink data files.

  • Object storage

    s3:// lakes on AWS S3, Cloudflare R2 and other S3-compatible endpoints, with atomic conditional writes for conflict detection.

  • Network server

    pinkdb-server over a framed binary protocol (version 6, with prepared-statement frames) and a remote CLI mode, durable --file mode, connection caps and idle timeouts.

  • Bindings

    Rust natively; a C ABI (v1) with a hand-written header (prepared-statement entry points included); dependency-free Python (ctypes) and Go (cgo) wrappers.

  • Extensions

    Runtime-loadable native scalar functions (ABI v1), in-repo C/C++ and Go SDKs, and the hosted extension catalog with one-command .install.

In progress

  • DuckLake parity, part two (waves 65–68). Incremental commits (format_version 4) and time travel are shipped; next: schema evolution on lake tables (ALTER TABLE with catalog schema versions), partition splits with per-file zone-map pruning, maintenance/compaction, and inlined small writes.

Planned

SQL and the engine

  • Indexes: CREATE INDEX/DROP INDEX, equality hash indexes plus zone-map shortcuts, and an optimizer index-vs-scan choice.
  • Materialized views: CREATE MATERIALIZED VIEW and on-demand full refresh.
  • Stored procedures: a small SQL procedural language (plus an optional JavaScript engine, WAL-replay safe).

Server security and operations

  • TLS for the network server (rustls + certificate configuration), so remote clients can connect over an encrypted transport.
  • RBAC: users and roles with Argon2id password hashes, CREATE USER/CREATE ROLE/GRANT/REVOKE on databases and tables, session login and per-connection enforcement; grants persisted and WAL-logged.
  • Async I/O at the boundary: an optional async storage layer (object stores / S3) and/or async server variant, feature-gated — a documented carve-out where only the I/O boundary goes async; the executor stays synchronous.

Extensions and distribution

  • Rust extension SDK: a safe wrapper and registration macros for first-party extensions (including a deterministic/volatile flag so the engine never WAL-logs volatile calls).
  • Core extensions: json, string, math and datetime function packs.
  • File-format extensions: parquet (read/write with statistics pushdown), Arrow (IPC files + the C Data Interface), and Iceberg v2 reads with time travel — as separate crates/extensions.
  • Extension trust: Ed25519 artifact signatures, SQL INSTALL, Linux artifacts.
  • Extensions on wasm: a pluggable loading model for wasm targets (native dlopen cannot work in the sandbox).
  • Packaging: a Python wheel and a standalone Go module.

Performance

  • Recurring tuning rounds against the committed query benchmark, following the existing profile-first approach.

Deferred

Not currently scheduled:

  • JS/wasm, Node-native and Java bindings.
