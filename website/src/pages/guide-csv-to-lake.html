Guide: CSV to a lake

Take a CSV file, shape it with SQL, publish it as an immutable lake snapshot, reopen it in a fresh process, and attach it read-only. Total time: a few minutes.

1. Build a lake-enabled CLI

# pinklake: .pink data files, 6.65 MB binary
cargo build --release -p pinkdb-cli --features pinklake

cargo build --release -p pinkdb-cli --features pinklake
./target/release/pinkdb

2. Import the CSV

Any CSV works; the repository's deterministic generator produces a 1M-row sales file if you want something bigger:

python3 bench/gen_sales.py            # -> sales_1m.csv (~24 MB)
pinkdb> .import sales_1m.csv sales
Imported 1000000 rows in 0.025s

Check what was inferred and shape the table you want to publish:

pinkdb> .schema sales
pinkdb> SELECT region, COUNT(*) AS n, AVG(total) AS avg_total
   ...>   FROM sales GROUP BY region ORDER BY n DESC;

3. Save the lake

pinkdb> .lake save mylake
pinkdb> .lake info mylake
pinkdb> .lake versions mylake
pinkdb> .lake tables mylake

Each save is a full snapshot: fresh immutable data files and one catalog transaction. The catalog is a pink: database by default (mylake means pink:mylake, with data in mylake.files/); use sqlite: or postgres:// for a shared catalog, and data <dir|s3://…> to keep data elsewhere. The first save of an empty store creates version 1 and publishes version 2 with your data.

4. Reopen in a fresh process

./target/release/pinkdb     # new process, empty store
pinkdb> .lake open mylake
pinkdb> SELECT COUNT(*) FROM sales;
pinkdb> .lake open mylake 2      -- an earlier published version, if you have one

.lake open replaces the in-memory store with a published version and resets the session database to main. A bare path is a pink: catalog; .lake open mylake 2 time-travels.

5. Attach read-only (the fast path)

pinkdb> ATTACH 'lake:mylake' AS sales_lake (READ_ONLY);
pinkdb> SELECT COUNT(*), MIN(total), MAX(total) FROM sales_lake.sales;  -- from stored statistics
pinkdb> SHOW DATABASES;    -- sales_lake: storage lake, its version
pinkdb> SELECT * FROM pinkdb_lake_decodes();   -- 0 data files decoded
pinkdb> DETACH sales_lake;

A read-only lake database decodes no column data for the statistics fast paths; anything else materializes the table lazily, decoding only the columns the query references. Without READ_ONLY the lake is writable: every committed statement publishes one incremental lake version.

Gotchas
  • Saving again rewrites every table — plan disk and time for full snapshots, not appends. Old versions and their files are kept; there is no GC.
  • .lake save, .lake open, ATTACH and DETACH are refused inside a transaction.
  • Every build writes and reads .pink data files. A lake saved with the removed (wave 104) data format is refused with a clear re-save error; there is no converter.
  • A second writer holding a stale handle gets another writer published version N; reopen the lake on save — or use .lake save in a fresh shell.
