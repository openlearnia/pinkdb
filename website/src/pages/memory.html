Agent memory

An agent that remembers: pinkdb-memory keeps a conversation's turns, the facts distilled from them, the projects those facts belong to and one long-term profile per principal — in pinkdb tables, under pinkdb's users and roles, read back layered and budgeted. It is a native extension (like the agent): the engine, the CLI and the server contain no model code, and the memory extension contains no model either — model calls go through the shared pinkdb-llm client.

The four layers

layerstored inwhat it is
L0 conversationl0_turnsthe turn as it happened — speaker, text, tag, conversation
L1 atomsatomsone standalone fact, with confidence, tag, its source turns and superseded_by
L2 scenariosscenariosa titled summary that names the atoms it groups
L3 personapersonasthe long-term profile; the latest row wins, older ones stay

Everything lives in one database, pinkdb_memory, in the state store next to the store (warehouse.state.pink, or --state PATH), never in the store a user's SQL reaches; every row carries the same identity columns: owner, team, visibility, an ACL of users, roles and agents, and agent. Nothing is hard-deleted. forget sets status = 'forgotten' and appends an audit row; update writes a new atom that supersedes the old one, so show still answers what you believed last week.

Setup

# the extension, next to the CLI
cargo build --release -p pinkdb-cli -p pinkdb-memory

./target/release/pinkdb sales.pink
pinkdb> LOAD EXTENSION 'target/release/libpinkdb_memory.dylib';
pinkdb> .memory add my warehouse is TPC-H SF1 --tag tpch
pinkdb> .memory add I always read EXPLAIN before a big join --tag style

# distillation is a model call, and only here; name the provider
set -a; . ./.env; set +a                     # exported, never read by pinkdb
pinkdb> .memory distill --provider zai

pinkdb> .memory search how big is my warehouse
pinkdb> .memory show                        # counts per layer, persona, recent rows
macOS 27: "mis-aligned LINKEDIT string pool"

macOS 27's loader refuses a library whose symbol string table is not 8-byte aligned, and the linkers (Apple's ld and LLD) can write one; whether a build hits it changes with the code. The library is otherwise fine: run python3 scripts/macos-align-linkedit.py target/release/libpinkdb_memory.dylib once after building (it does nothing to a library that is already aligned), and LOAD EXTENSION names the script when it sees the error.

There is no default provider, exactly as with .agent: a distill without one fails with no provider: … while add and search keep working.

Distillation

add never calls a model. It appends an L0 turn (plus a queue row when PINKDB_MEMORY_DISTILL_EVERY=N says so) and returns. distill drains the queue, one model call per step:

  1. turns → atoms. The prompt carries the undistilled turns and the owner's active atoms, and asks for {"atoms":[{"text":…,"confidence":…,"tag":…,"supersedes":…}]}.
  2. atoms → a scenario. Atoms no scenario names yet become {"scenarios":[{"title":…,"summary":…,"atoms":[ids],"tag":…}]}; a scenario that names no known atom is dropped rather than stored empty.
  3. scenarios → the persona. One call over the scenario summaries answers {"persona":…}, appended as a new row.

Every answer is validated against that contract before a single row is written: required fields, types, length caps, confidence in range, and every referenced atom id must exist and be visible to the owner. A malformed answer writes nothing, records the error on the queue row and is retried later; the attempt count stops at three, and an operator's next .memory distill resets failures to pending. A contradicting fact supersedes the atom it contradicts in the same batch as the insert, so the two never both look current.

Who can read what

Visibility is a row filter the extension applies on every read — search, persona, show and the distillation input — not a grant the client could skip:

visibilityreadable by
privatethe owner
teamthe owner and the members of the owner's role
restrictedthe owner and the users, roles and agents named in --acl u:bob,r:ops
agentthe named agent identity only

The memory tables are granted to nobody. A non-admin's SELECT * FROM pinkdb_memory.atoms fails with the engine's permission denied: … needs the SELECT privilege …, and the memory tools come back with only the rows that principal may see. An administrator can always read the tables directly — that is the audit escape hatch, documented rather than hidden. A served session is refused a statement that reads pinkdb_memory at all, so even an admin's MCP client goes through the tools. On an embedded store without users there is no identity to protect: the trusted session is the operator, and it answers as the implicit principal pinkdb.

The extension's own channel is confined too. It skips the privilege check (that is what lets it write its own state), so the serve policy is what limits it: a read allow-list over pinkdb_memory, checked against the bound plan — a view, a CTE or a macro cannot reach around it, and a table function or bare path is refused before it binds — with external services (embed()) allowed on their own switch and files off. Writing that test found a latent engine hole: a served session over a connection skipped every catalog-based policy check, so a channel that named only pinkdb_memory could read main.secret. It is closed (Session::check_store), and the read mask now applies on that path as well.

Identity comes from the engine. This wave added SELECT current_user() and SELECT current_roles() — the logged-in principal and its transitive roles, comma-joined. They are bound to constants at bind time, they are refused in a statement the engine WAL-logs (as any session state is), and the extension asks the host on its own confined channel, so a tool argument cannot spoof who is asking. No extension ABI version changed, so every loaded extension and all four SDKs are untouched.

Retrieval

memory_search answers in layers, because a bootstrap should be cheap: the caller's persona, then the best-matching scenarios (a term-overlap score over title and summary), then atoms and turns ranked by BM25 and fused with RRF — DuckDB's constants, computed inside the extension so a fresh write is ranked without rebuilding an index. When the embeddings package and a provider are available, the same query is embedded, atoms are ranked by array_distance over a lazily created atom_vectors table, and the two lists are fused the same way; the answer names its mode (bm25, hybrid) and, when it falls back, why.

Three budgets stop retrieval and each one is reported: --items N, --chars N and --timeout-ms MS. Persona and scenarios count against the same budget — a bootstrap that ignores the budget is not budgeted. Every hit carries its layer, id, fused score, source (bm25, vector, bm25+vector) and visibility.

Commands and tools

.memory add <text> [--visibility private|team|restricted|agent] [--tag <name>]
                   [--acl u:bob,r:ops] [--speaker user|agent] [--conversation <name>]
                   [--agent <identity>]
.memory search <query> [--items N] [--chars N] [--timeout-ms MS]
.memory update <atom> <text>      -- a new atom that supersedes the old one
.memory forget <id>               -- soft delete plus an audit row
.memory distill [--provider <name>] [--model <name>]
.memory persona
.memory show
.memory serve [stdio | http <port>] [allow-memory] [allow-writes] [allow-files]

The MCP side is the same operations plus the warehouse tools the MCP bridge has, served by the memory extension itself (an extension cannot call another extension, and memory reads must use the host's confined channel): memory_add, memory_search, memory_update, memory_forget, memory_distill, memory_persona. A read-only bridge lists and runs the two read tools only; the four write tools need allow-memory, and even then the host's policy lets them write only pinkdb_memory.

With the memory extension loaded, an .agent run records its question and its answer as two L0 turns under the caller's identity. The two extensions cannot call each other, so the CLI host — which owns both — is the seam; a memory failure cannot fail a finished run.

Tests

Everything runs against a scripted provider and a loopback embeddings server: a short conversation distilled end to end into atoms, a scenario and a persona, then searched; every visibility class against real users and roles; a refused direct SELECT; supersession and forget with their audit rows; each of the three budgets; hybrid RRF against hand-computed scores; a malformed answer, a 429 then success, and a failure that stops at the attempt cap; the write switch; and a sentinel that greps a durable store's bytes for the embeddings key. The one live test is opt-in and names its provider: PINKDB_MEMORY_LIVE=1 cargo test -p pinkdb-memory --test live -- --ignored. The plan, including what this wave deliberately did not build, is docs/wave-109-plan.md.
