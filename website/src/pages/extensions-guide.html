Using extensions

pinkdb can load shared libraries that register scalar SQL functions at runtime — no recompilation of the engine. Extensions are a versioned C ABI (v1), separate from the pinkdb-ffi embedding ABI.

Loading an extension

LOAD EXTENSION '/abs/path/to/math_ext.dylib';
-- Extension math_ext loaded.
SELECT ext_clamp(CAST(5 AS BIGINT), CAST(0 AS BIGINT), CAST(10 AS BIGINT));  -- 5
  • The path is a string literal and resolves against the process's working directory at load time; absolute paths are recommended.
  • A successful load prints Extension <name> loaded., and the declared name is pinned: loading the same extension again is a clear extension "x" is already loaded error.
  • Loaded functions resolve case-insensitively like built-ins and cannot shadow one. Arguments must match the registered types exactly — write CAST(...) for another numeric type; NULL literals pass through as NULL.
  • Extensions are process-level: they are not stored in .pink snapshots and not part of a transaction. LOAD EXTENSION is refused inside BEGIN..COMMIT.
  • WebAssembly targets: native dlopen cannot work in the wasm sandbox, so wasm builds use linked registration — extensions compiled into the host register through a safe-Rust API, and LOAD EXTENSION '<name>' resolves a registered name (unknown names fail with an actionable error). The JS / wasm-bindgen host contract is documented in docs/wasm-extensions.md.

Installing from the extension repository

The CLI can install published artifacts with one command (needs the repo feature, which keeps the default binary lean):

cargo build --release -p pinkdb-cli --features repo
pinkdb> .install math_ext
Installed math_ext 0.1.0 (darwin-arm64)
  repository: https://pinkdb-ext-repo.defaultcms.workers.dev
  path:       /Users/you/.pinkdb/extensions/math_ext/0.1.0/darwin-arm64/math_ext.dylib
  sha256:     38abc8b345466e0710bf9c2497a99b0b5c0a3e906874cae1c3323ee3e754b9b2
Extension math_ext loaded.
  • Artifacts land under $PINKDB_HOME/extensions/<name>/<version>/<platform>/ (PINKDB_HOME defaults to ~/.pinkdb), are written atomically, and are verified against the catalog's SHA-256 before the rename — a mismatch is refused and leaves nothing behind. Installing the same coordinates again reuses the verified copy.
  • .install <name> picks the highest version for this platform with ABI v1; .install <name>@<version> is exact.
  • .repositories list | add <url> | remove <url> manage an ordered repository list in $PINKDB_HOME/repositories.json; the first repository with a match wins. When the file is absent, the official repository is the default. .installed lists the cache.
  • Browse what is published in the extension catalog (name, version, platform, ABI, SHA-256, download).

Writing an extension

The in-repo SDKs provide a vendored ABI header, a commented template and worked examples:

SDKDirectoryStatus
C / C++ ext-sdk/c/ (examples: numeric, string, C++) shipped
Go (cgo, -buildmode=c-shared) ext-sdk/go/ shipped
Rust ext-sdk/rust/ (safe wrapper + macros) shipped (safe wrapper + pinkdb_extension! macros)

An extension exports three symbols; init registers scalar functions through the host API:

uint32_t    pinkdb_extension_abi_version(void);   /* PINKDB_EXT_ABI_VERSION */
const char *pinkdb_extension_name(void);          /* UTF-8, non-empty, <=256 bytes */
int32_t     pinkdb_extension_init(const PinkdbHostApi *api, void *host_ctx);
static int32_t hello_add(void *user_data, const pinkdb_ext_value *args,
                         size_t n_args, pinkdb_ext_value *out) {
    (void)user_data; (void)n_args;
    if (args[0].is_null || args[1].is_null) { out->is_null = 1; return 0; }
    out->type_tag = PINKDB_EXT_TYPE_BIGINT;
    out->is_null = 0;
    out->int64 = args[0].int64 + args[1].int64;
    return 0;
}

int32_t pinkdb_extension_init(const PinkdbHostApi *api, void *host_ctx) {
    static const int32_t arg_types[2] = {
        PINKDB_EXT_TYPE_BIGINT, PINKDB_EXT_TYPE_BIGINT
    };
    return api->register_scalar(host_ctx, "hello_add", 2, arg_types,
                                PINKDB_EXT_TYPE_BIGINT, hello_add, NULL);
}
make -C ext-sdk/c                 # build the examples
./ext-sdk/c/smoke.sh              # build + load + query, end to end
make -C ext-sdk/go && ./ext-sdk/go/smoke.sh
make -C ext-sdk/rust && ./ext-sdk/rust/smoke.sh

Contract highlights (the header is complete):

  • Deterministic vs volatile: a function may declare itself volatile (clock/random-like); the engine then refuses to call it in any statement it WAL-logs (replay could diverge) with an explicit error. Deterministic is the default.
  • Thread safety: callbacks run concurrently on the executor's rayon workers — a function may be invoked on several threads at once, so its state must be guarded (atomics, locks, TLS). register_scalar is only valid inside pinkdb_extension_init.
  • Typing: ABI v1 is strictly typed; the result must carry the registered type tag.
  • VARCHAR results must be allocated with api->alloc(size); the host copies text_len bytes and frees them with api->free immediately after the call — on every path. A rejected registration fails the whole load atomically.
  • Errors: a non-zero return aborts the enclosing statement with a message naming the function and code; callbacks must not panic across the ABI boundary (in C++: catch everything).

Extensions and durable databases

  • A durable database WAL-logs LOAD EXTENSION, and every logged record that calls an extension is prefixed with the LOAD EXTENSION '<path>' it needs. Replay therefore re-loads exactly what the replayed records use; a missing file at replay time is a hard error naming the path, never a silent drop. Prefer absolute, stable paths.
  • A checkpoint rolls the WAL and never writes an extension into the .pink file: after a reopen, the first record that touches one re-loads it by path.
  • On pinkdb-server, LOAD EXTENSION loads native code into the server process and is refused for remote clients unless the server runs with --allow-load-extension.
