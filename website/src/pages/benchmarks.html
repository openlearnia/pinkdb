Benchmarks

Every number here comes from bench/suite, the suite in this repository, run on one quiet machine. pinkdb is compared with DuckDB v2.0.0 on the same data, the same thread count and the same warm cache. The suite records the machine, the git commit, the load average and every raw timing, so any table below can be reproduced or disputed.

Wave 111c: join residuals and a parallel aggregate merge

A hash join can carry a residual now: a predicate on a candidate key match, evaluated on that pair before anything is materialized, where a pair that fails it is not a match (an inner join drops the pair; a semi/anti join treats it as absent). A correlated EXISTS with a non-equality condition therefore keeps the cheap shape instead of falling back to body ⨯ Distinct(Project(outer)) — Q21's 36-column outer chain used to be cloned and deduplicated three times and is now one chain with two joins. The duplicate-eliminated key side also carries the enclosing filters now, so Q20's 800k keys became 11k, and the merge of a parallel aggregation's partial tables is hash-partitioned and runs in parallel, where it used to be a serial walk over 6 M entries. Nothing about an answer changed: all 22 TPC-H queries still match DuckDB's rows and checksums at SF 0.01, 0.1 and 1, and two new differential tests compare the new join and aggregate paths with a hand-written reference.

Wave 122: statistics and join filters

pinkdb keeps per-column statistics now — row and NULL counts, min/max, a HyperLogLog distinct estimate — and per-chunk zone maps, maintained on every write and persisted in the .pink footer. ANALYZE recomputes them exactly, pinkdb_column_stats() shows them, the optimizer prices filters and joins with them, and a scan skips chunks whose bounds cannot satisfy a filter. An inner or semi hash join also builds a range and a Bloom filter from its build keys and hands them to the scan under its probe side, so non-matching rows are dropped before their columns are read. Left/right/full and anti/mark joins are excluded — they owe rows an output that a probabilistic filter cannot promise. Nothing about an answer changed: all 22 TPC-H queries still match DuckDB's rows and checksums.

Wave 123a: selection vectors and fixed-width kernels

A filter used to copy the rows that survived it out of the chunk, and a comparison against a DECIMAL column used to box both sides into a value object row by row. Neither happens now. WHERE evaluation produces a selection — the row indices that survive — directly from typed comparison kernels; AND narrows it progressively so later conjuncts only look at survivors, and OR only at the rows its left side did not take. A GROUP BY above the filter folds the chunk through that selection instead of a compacted copy, and copies only when fewer than one row in eight survives. Decimals compare against doubles, integers and differently-scaled decimals in a typed loop, and decimal arithmetic writes into a pre-sized payload instead of per-row. No answer changed: all 22 TPC-H queries still match DuckDB's rows and checksums at SF 0.01, 0.1 and 1, and a seeded fuzz compares the selection path against a row-at-a-time reference evaluator over seven types, NULLs, type extremes, and division-by-zero and decimal overflow.

Method

The suite generates TPC-H with DuckDB's built-in dbgen, writes the eight tables to Parquet, and loads that same Parquet into a .pink store and into a DuckDB database. Each query runs in a fresh process against the warm store; the suite discards one warm-up run and reports the median of five. Both engines get eight worker threads (RAYON_NUM_THREADS and SET threads). Row counts and a checksum of every answer are compared across the two engines, so a fast wrong answer cannot enter the table.

The machine was an Apple M4 (10 cores, 17 GB RAM, macOS 27.0.1, rustc 1.97.1, DuckDB v2.0.0 d54cbbe3df). Load average stayed between 1.8 and 4.3 and is recorded in the JSON. DuckDB's timer has 1 ms resolution, so its smallest figures are upper bounds; pinkdb's column is reported the same way, rounded to the millisecond.

Where pinkdb is slower, and why

The join operator is the honest answer for TPC-H. pinkdb copies rows into new vectors at every hash-join probe; DuckDB's probe writes only the surviving selection vector. The optimizer now reorders comma chains by cost (a query graph with foreign-key-aware cardinalities, a subset DP up to twelve relations, anchored at the query's own filtered relation, and the smaller input builds the hash table from exact row counts), and it derives per-table filters from an OR of conjunctions, including IN lists inside the branches — that is what took Q7 from 133× to 27× and Q19 from 246× to 11×.

Q21 is the worst gap left (75×) and it is the query itself now: two 6 M-row lineitem scans with a date filter and a match table built for each. Filtering the join key inside the scan is the next lever there — wave 122's dynamic filter only skips whole chunks by zone bounds. Q2 (44×) is a different story: its correlated subquery body is ordered before decorrelation removes the outer column, so it joins partsupp-first (115 ms against 9 ms for the same relations ordered region-first) and copies 19 columns to use one. Q18 (11×) is the aggregate's phase one now that the merge is parallel, and Q9/Q5 (29×/41×) are the row-copying join probe.

Ingest is mixed: pinkdb's CSV reader is faster than DuckDB's on a wide lineitem file, while its Parquet reader is about 4.6× slower because DuckDB reads and decodes in larger parallel batches. The durable-write numbers have no DuckDB comparison: DuckDB has no per-statement WAL with fsync policies, so there is nothing to compare against.

Reproduce it

# the default: TPC-H SF 0.1, every family, about ten minutes
bench/suite/run.sh

# one family at SF 1 (needs ~1 GB per engine and a quiet machine)
bench/suite/run.sh --only tpch --scale 1

# the CI guard: 60k rows, no DuckDB, compares against the committed baseline
python3 bench/suite/run.py --only ci

Results land in bench/suite/results/<date>-<commit>.json with a Markdown summary beside it. --only takes any comma-separated subset of tpch,ingest,durable,lake,search,footprint,ci; --work-dir keeps the generated stores for a rerun. Nothing in the suite downloads data or installs a DuckDB extension.

What is not measured

DuckDB's fts and vss extensions need INSTALL, which this project does not run without an explicit go-ahead, so the search family has no cross-engine comparison yet. A shared materialized key side for several correlated subqueries of one statement (a delim join), scan-level Bloom filtering of a join key, join ordering after decorrelation, and a perfect-hash phase one for low-cardinality aggregation are the known next steps; each is a ROADMAP row, not a hidden caveat in these tables.
