SQL dialect

pinkdb's SQL dialect targets DuckDB compatibility: the committed differential corpus (171 probes) runs against both engines and must match. This page is the quick reference for what the dialect accepts, what it differs on, and what is intentionally absent — the reasoning behind every row lives in the SQL reference and the roadmap.

Known divergences from DuckDB

  • Correlated subqueries are rejected (DuckDB runs them) — the dialect's largest deliberate gap; uncorrelated subqueries and EXISTS behave like DuckDB.
  • JOIN … USING and NATURAL JOIN are parse errors — write the ON condition.
  • Three-part column references (db.table.col) are not supported — alias the table (SELECT x.col FROM db.table AS x).
  • AT on CTEs: DuckDB silently ignores it; pinkdb refuses (a wrong-answer trap avoided on purpose).
  • ILIKE, TRY_CAST, SIMILAR TO, LIKE … ESCAPE are absent (use LOWER(x) LIKE …).
  • EXPLAIN prints pinkdb's plan format, not DuckDB's tree rendering.
  • Extension surfaces differ: no SQL COPY, SET, ATTACH or table functions yet — files come in via .import, configuration via environment, lakes via .lake commands (see the statement table).
  • Defaults worth knowing: ORDER BY defaults to NULLS LAST; int / int is DOUBLE; integer overflow is an error; SUM over integers is exact.
