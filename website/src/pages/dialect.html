SQL dialect

pinkdb's SQL dialect targets DuckDB compatibility: the committed differential corpus (171 probes) runs against both engines and must match. This page is the quick reference for what the dialect accepts, what it differs on, and what is intentionally absent — the reasoning behind every row lives in the SQL reference and the roadmap. The exhaustive form-by-form matrix — supported, divergent, and every refusal with its exact error, batch by batch — is docs/sql-conformance.md.

Queries and clauses

FeatureStatusNotes
INNER/LEFT/RIGHT/FULL/CROSS joins✅multi-way and composite conditions (ON a = b AND c = d); conditions can be arbitrary expressions (equality takes the hash fast path)
JOIN … USING (…), NATURAL JOIN✗rejected with a parse error
Subqueries: scalar, IN, EXISTS✅uncorrelated only — correlated subqueries are rejected (the main deliberate gap)
WITH (CTEs), column aliases✅
WITH RECURSIVE r(…)✅anchor UNION [ALL] step, evaluated semi-naively (the step sees the rows the last round added; UNION also drops rows already produced); bounded at 100 000 iterations / 10 000 000 rows — both are errors, so runaway recursion cannot hang
Window functions✅ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, NTILE, FIRST_VALUE, LAST_VALUE, aggregates OVER; PARTITION BY/ORDER BY, ROWS and RANGE frames (validated; no nesting; SELECT list and ORDER BY only)
QUALIFY expr✅after WINDOW, before ORDER BY; may name select aliases, aggregates and window functions
Named WINDOW w AS (…) clauses✅OVER w resolves them; a window may build on another (OVER (w ORDER BY x), WINDOW v AS (w ROWS …)): the base's PARTITION BY/ORDER BY are inherited, a clause the base already has cannot be overridden, and a framed base cannot be copied (DuckDB's wording)
Aggregate FILTER (WHERE …)✅with DISTINCT too, and on a window aggregate (sum(a) FILTER (WHERE …) OVER (…) skips the non-matching rows of the frame); on a non-aggregate window function it is refused by name, like DuckDB
Ordered-set aggregates WITHIN GROUP (ORDER BY …)✅percentile_cont/percentile_disc (also quantile_*) and mode(); a constant fraction in [0, 1], one ordered expression, FILTER before or after; not windowable
DISTINCT ON (…)✅first row per key in ORDER BY order; the key need not be selected
VALUES (…), (…) and TABLE t as queries✅standalone, in FROM with column aliases ((VALUES …) t(x, y)), or as an INSERT source; column names col0, col1, … without aliases
FETCH FIRST n ROWS ONLY, OFFSET n ROWS✅LIMIT and FETCH FIRST together are refused
UNION/INTERSECT/EXCEPT [ALL]✅numeric type unification; a trailing ORDER BY/LIMIT applies to the whole set (branch-level clauses need parentheses and are unsupported)
GROUP BY / HAVING / COUNT(DISTINCT …) / DISTINCT✅
GROUPING SETS / ROLLUP / CUBE + GROUPING()✅DuckDB's set order and big-endian mask (GROUPING(a, b) = 2·g(a) + g(b)); plain keys cross-product with the sets; implemented as a union of aggregates, so HAVING/ORDER BY/LIMIT apply once
ORDER BY … [NULLS FIRST|LAST], positional✅general expressions must be select aliases, positions or GROUP BY keys; the engine default is NULLS LAST
LIMIT / OFFSET✅OFFSET n ROW|ROWS accepted
PIVOT/UNPIVOT✗not scheduled
TABLESAMPLE / USING SAMPLE≈n ROWS (reservoir, exactly n) or n PERCENT, with bernoulli, system or reservoir; REPEATABLE (seed) is reproducible within pinkdb — each engine has its own generator, so a seed picks different rows than DuckDB
LATERAL subqueries≈accepted in the head position, after CROSS JOIN/JOIN and in the comma form; uncorrelated only — a subquery that references an earlier FROM item is refused by name (derived plans have no outer scope), and a lateral table function is refused
Comma-separated FROM list✅a CROSS JOIN in the same left-deep chain, so a later ON sees the items left of the comma (DuckDB's rule)
Row constructors ROW(a, b) / (a, b)✅in comparisons and IN lists, field-wise with NULL-as-a-value semantics (DuckDB's answers); a standalone row is refused (no STRUCT type), and so is (a, b) IN (SELECT …)
INSERT … ON CONFLICT/OR REPLACE/OR IGNORE, UPDATE … FROM, DELETE … USING, RETURNING, MERGE (incl. WHEN NOT MATCHED BY SOURCE), data-modifying CTEs✅DuckDB 2.0 semantics: excluded, first-wins clause order, last source row wins for UPDATE … FROM, MERGE's multiple-match error, the body of a DML CTE runs once at the top level; INSERT OR REPLACE keeps unlisted columns; the MySQL spellings (ON DUPLICATE KEY UPDATE, REPLACE INTO) are refused by name
FOR UPDATE / FOR SHARE✗refused by name: pinkdb has no row locks (its MVCC already serializes writers); DuckDB 2.0 is a syntax error there
AT TIME ZONE, timezone(zone, ts)≈no TIMESTAMPTZ and no time zone database: a UTC-family zone (UTC, GMT, Z, Etc/UTC, +00:00) is the identity on the naive TIMESTAMP, any other zone is refused by name
JSON mutators json_set/json_insert/json_replace/json_remove≈in the engine, on JSON text or VARIANT (the result keeps the document's kind); a superset of DuckDB, which needs ::JSON arguments and refuses VARIANT ones; json_insert never overwrites, json_replace never creates, json_remove takes two arguments
SET VARIABLE x = …, getvariable('x'), $x✅the value is bound once per statement and spliced in as a literal; the state is per connection (one client cannot read or overwrite another's), never persisted or logged, and a logged statement may not read one; getvariable of an unset name is NULL while $x errors (DuckDB's split)
List literals [1, 2], the LIST type, slicing a VARIANT✗refused by name — a LIST type is the missing piece
AT (VERSION => n) / AT (TIMESTAMP => ts)✅ lake-onlyattached lake tables (literal targets, capped at the attached version); store tables, CTEs and views are refused — DuckDB silently ignores AT on CTEs, pinkdb errors

Known divergences from DuckDB

  • Correlated subqueries are rejected (DuckDB runs them) — the dialect's largest deliberate gap; uncorrelated subqueries and EXISTS behave like DuckDB.
  • JOIN … USING and NATURAL JOIN are parse errors — write the ON condition.
  • Three-part column references (db.table.col) work since wave 94 (aliases still hide the original table name), which means a nested VARIANT path has to be spelled js.a['b'] rather than v.js.a (that reads as database v).
  • AT on CTEs: DuckDB silently ignores it; pinkdb refuses (a wrong-answer trap avoided on purpose).
  • ILIKE is absent (use LOWER(x) LIKE …); SIMILAR TO follows DuckDB 2.0's anchored-regex behaviour, so a malformed repetition such as a{1,2,3} is literal text here and an error there, and SIMILAR TO … ESCAPE is refused by both.
  • 1.e2 is a parse error (write 1.0e2); DuckDB reads it as a float.
  • EXPLAIN prints pinkdb's plan format, not DuckDB's tree rendering.
  • Extension surfaces differ: no SQL COPY, SET, ATTACH or table functions yet — files come in via .import, configuration via environment, lakes via .lake commands (see the statement table).
  • Defaults worth knowing: ORDER BY defaults to NULLS LAST; int / int is DOUBLE; integer overflow is an error; SUM over integers is exact.
