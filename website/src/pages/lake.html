Lake

A lake is a catalog database plus immutable data files. The catalog uses DuckLake v1.1's tables on a durable pink: database, SQLite or Postgres; data lives on local disk or S3. Incremental commits, time travel and statistics-only attach included.

What a lake is

The catalog is one of:

pink:lake.pink                       durable pinkdb catalog (default)
sqlite:/srv/lakes/sales.db           SQLite catalog (catalog-sqlite)
postgres://user@host/db?schema=lake  Postgres catalog (catalog-postgres)
pink+s3://bucket/prefix              catalog on object storage (catalog-s3)

Catalog on object storage (pink+s3://)

With the opt-in catalog-s3 feature the catalog database itself lives in the bucket — no database server, nothing durable on local disk. The durable state is a .pink database split across immutable objects: prefix/catalog/log/<seq> holds a transaction's committed WAL records, one object each (a delta; its size does not grow with the number of data files), and prefix/catalog/checkpoint/<seq>.pink is a full image every 100 records (PINKDB_CATALOG_S3_CHECKPOINT_INTERVAL). prefix/catalog/head names the newest checkpoint for operators; readers find checkpoints by listing. Data defaults to s3://bucket/prefix/data/.

Writers race on conditional creates of the next log object; the loser reloads the records it missed and retries through the usual conflict path. An endpoint without conditional writes is read-only — never check-then-put. A keyed lake seals both object kinds in PINKENC1. Expired snapshots prune folded log objects; commits never delete. Checkpoint images are cached locally by bucket/prefix/sequence, so a reopen downloads only newer logs.

DuckDB's DuckLake extension cannot attach this catalog (it speaks only DuckDB, SQLite and Postgres catalogs). Migrate by saving the loaded lake to a new catalog (.lake save pink:… or sqlite:…) and back.

All of them hold the same ducklake_* rows. A commit inserts its typed delta and one snapshot row — the commit point — instead of rewriting a JSON catalog. A bare path means pink:<path>, and its data defaults to <path>.files/. The catalog records the data location, so later opens need only the catalog.

mylake.pink                          catalog database
mylake.pink.files/data/<table>/…     immutable data files
                                     (.pink or Parquet)

Metadata and data may live apart: a catalog on local disk or Postgres, data on S3. A lone s3://… URL is not a lake — always give the catalog and put the data there.

Save, open, attach

pinkdb> .lake save pink:lake.pink data s3://bucket/prefix
pinkdb> .lake save postgres://user@host/db?schema=lake data s3://bucket/prefix
pinkdb> .lake open pink:lake.pink
pinkdb> .lake versions pink:lake.pink
pinkdb> .lake tables pink:lake.pink
pinkdb> .lake info pink:lake.pink
pinkdb> ATTACH 'lake:pink:lake.pink' AS lk (READ_ONLY);
pinkdb> SELECT COUNT(*) FROM lk.t;   -- from the catalog, no data read

A save writes immutable data files first, then one catalog transaction. A crash leaves the previous version or the new one, never a mix. Time travel (.lake open <catalog> <version>) reads the same rows with an older begin_snapshot boundary.

Incremental commits

pinkdb> ATTACH 'lake:pink:lake.pink' AS lk;   -- writable: holds the lake's lease
pinkdb> INSERT INTO lk.t VALUES (…);           -- one lake version
pinkdb> BEGIN; DELETE FROM lk.t WHERE …; INSERT INTO lk.t …; COMMIT;   -- one version
pinkdb> DETACH lk;

A lake is a database (wave 124): CREATE DATABASE name (TYPE LAKE, CATALOG '…', DATA '…') creates one, a writable lake database publishes every committed statement or transaction, and one lake has one writer at a time (a lease in its catalog). The lake's one schema is the database.

Append-only commits add data files (inlined rows stay in the catalog when they are small). Deletes use positional delete files; merge/rewrite bake them in when asked. Maintenance commands (.lake merge, rewrite, expire, cleanup, orphans) operate on the typed snapshots, not a rendered manifest.

Data formats

  • .pink (PINKDB07) is always available and carries a statistics block per file.
  • Parquet with the parquetlake feature (and DuckDB interop).

Either format prunes whole files with the statistics block: exact min/max, null count and NaN count per column, and for a VARIANT column one entry per shredded path, keyed the way DuckDB spells a path ("a", "user"."id" — every key double-quoted, joined by .), so WHERE payload['a'] = 5 or variant_extract(payload, '$.a') = 5 skips files whose bounds exclude the value.

A catalog stores those path facts in DuckLake's own ducklake_file_variant_stats table: one row per shredded path per data file, with variant_path, shredded_type, value and null counts and plain-text min_value/max_value. The rows are written in the same catalog transaction as ducklake_file_column_stats and deleted with their data file by expire and cleanup, on every catalog backend (pink:, sqlite:, and a Postgres catalog). Both directions of the DuckDB interop are tested: DuckDB 2.0 attaches a pinkdb-written lake and reads the rows, and pinkdb prunes files using rows DuckDB wrote.

Each table pins its provider; appends keep it. A build without a table's provider lists the table as unavailable and refuses only that table — other tables still load.

Encryption

PINKDB_KEY (or the *_with_key constructors) enables per-file encryption. Every data/delete file becomes a PNKLAKE1 container sealed with its own random 256-bit key, recorded in the catalog. A pink: catalog may itself be an engine-encrypted pinkdb database; SQLite/Postgres catalogs rely on their server/filesystem. Metadata rows stay plaintext, as in DuckLake.

Rust API

use pink_lake::{Lake, EncryptionKey};

let mut lake = Lake::create("lake.pink")?;             // pink:lake.pink, data lake.pink.files/
lake.write_from_store(&db)?;

let mut lake = Lake::create_with_catalog("sqlite:lake.db", "s3://bucket/prefix")?;
let mut lake = Lake::open("lake.pink")?;
let mut lake = Lake::open_with_catalog("postgres://…", None)?;
let mut lake = Lake::create_with_catalog_with_key("pink:lake.pink", "data", key)?;

No legacy layout

Pre-103 JSON-layout lakes (a JSON catalog plus snapshot and commit files) do not open in this build and there is no converter. Re-save such a lake with an older pinkdb build, then open the new catalog here.
