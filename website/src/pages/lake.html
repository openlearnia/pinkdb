Lake

A lake keeps metadata and data storage decoupled: a small JSON catalog, an immutable manifest per published version, and immutable data files that are appended, never rewritten — on local disk or in an S3/R2 bucket. Incremental commits, writable attachments and time travel included.

What a lake is

A lake is a directory (or, with the s3 feature, an s3://bucket/prefix key prefix) with exactly this layout:

mylake/
├── catalog.json                       current state (the authoritative "latest")
├── snapshots/<version>.json            immutable manifest per published version
├── commits/<version>.json              per-version delta manifest (what the commit added)
├── data/<table>/<uuid>.vortex          immutable data files (full lake)
├── data/<table>/<uuid>.pink            lean data files (no Vortex; still readable)
└── data/<table>/<uuid>.pinkdel          positional delete files (merge-on-read)

Every published version is immutable: snapshots/<version>.json is create-only (a hard link locally, If-None-Match: * over S3) and every data file is written once under a fresh name. catalog.json is always byte-identical to the snapshot of its version, and publication order (files → delta manifest → snapshot → catalog) means a crash leaves either the old version or the new one, never a mix — so every version ever published still loads.

Incremental commits

.lake save still publishes a full snapshot (every table rewritten to fresh files). A commit publishes only the difference:

.lake attach mylake write      # materialize the pinned version into the session store
UPDATE t SET ...;              # ordinary SQL accumulates in the store
DELETE FROM t WHERE ...;
INSERT INTO t VALUES (...);
.lake commit mylake            # publish exactly the difference as one new version
.lake detach mylake
  • Appends write new files. Each commit adds one new immutable data file per changed table, listed after the existing files with its exact row count; scans union the file list in order. Previously published files are never rewritten — a 1M-row lake committed 4 rows in 7.6 KB / 0.54 s with 0 bytes rewritten (a full save of the same table writes 2.6 MB).
  • Deletes are positional files. DELETE records the dropped positions in a .pinkdel file bound to the data file it targets; readers apply it at read time (merge-on-read), and UPDATE is a delete + append.
  • Every version writes commits/<v>.json, a delta manifest listing the data and delete files the commit added plus its row movement (audit; the snapshot stays authoritative for loading).
  • Concurrent writers retry with rebase. A commit whose base changed publishes again on the new head, bounded by DuckLake's writer controls — max_retry_count (default 10), retry_backoff (1.5) and retry_wait_ms (100, the wait grows by the backoff factor each attempt). The CLI overrides them with PINKDB_LAKE_MAX_RETRY_COUNT, PINKDB_LAKE_RETRY_BACKOFF and PINKDB_LAKE_RETRY_WAIT_MS. A delta whose base file the head no longer contains, or positions another commit already deleted, is refused — never re-applied.
  • Durable sessions are crash-safe. .lake attach … write checkpoints the materialized tables and .lake commit flushes the WAL before publishing, so a recovered session re-attaches by adoption and commits idempotently: a change that already reached the lake publishes nothing, and one that never did publishes exactly once.
  • Writable attachments are content-sync, not op-replay. A commit reconciles the table to the session's content; if another writer appended to an in-scope table meanwhile, the next diff refuses instead of silently dropping their rows (re-attach prints a reconciliation note when adopted content differs). New tables created in the session are outside the attachment's scope — a .lake save publishes them.

Time travel

Attached lake tables can be queried as of a published version:

SELECT * FROM t AT (VERSION => 2);
SELECT * FROM t AT (TIMESTAMP => TIMESTAMP '2026-10-17 12:30:36.029');
SELECT COUNT(*) FROM t AS old AT (VERSION => 1) JOIN t ON old.id = t.id;
  • The clause works on the first FROM source or any joined source, with an optional alias before it; targets are literals (a version number, or a timestamp literal / string in either the engine format or the manifest's ISO-8601 UTC form).
  • Timestamps resolve inclusively: the newest snapshot published at or before the given time. Unknown versions, a timestamp before the first snapshot, and tables that did not exist at the target version are clean errors — nothing is produced.
  • An attachment reaches versions 1..=the attached version (.lake attach dir 3 never sees a later version); store tables are refused with “has no snapshot history”, and so are CTEs and views.
  • Statistics fast paths work per version: exact COUNT(*)/MIN/MAX over AT (VERSION => n) decode no data file, and projected scans decode only the columns they reference.
  • .lake snapshots <dir> lists every version's record — publish time, author, commit message, (tables, rows) and a change summary — and .lake save … author '<name>' message '<text>' (or Lake::set_commit_message) attaches metadata to the next published version. (DuckLake's ducklake_default_version has no pinkdb counterpart on purpose: it selects a new-catalog storage format, not a read default.)

Two data formats, one lake API

There are two builds of the lake layer with the same commands:

Build (CLI feature)Data filesCatalogRelease size
lean lake (lake-lite) .pink v5 (the engine's single-table bytes, with a per-file statistics block in the manifest) format_version 4 2.69 MB
full lake (lake) Vortex (the default lake format) format_version 4 45.3 MB
  • Both builds write and read the current format — catalog format_version 4 — and both support incremental commits and time travel. Older lakes stay readable: v1–v3 catalogs (single-file Vortex v2/v3 and lean v1) load and migrate on the next save, leaving old files untouched.
  • The lean build decodes .pink data files only and refuses a Vortex lake with a clear “rebuild with lake” error. A lake written by the lean build opens bit-exactly in a full build.
  • s3 implies lake-lite; use lake,s3 for the full Vortex lake over S3/R2.

Using a lake

.lake save mylake              -- publish a full snapshot of the store
.lake save mylake message 'added orders'   -- with commit metadata (author too)
.lake versions mylake          -- published versions (the current one is marked)
.lake snapshots mylake         -- per-version records: time, author, message, changes
.lake tables mylake            -- current version's db.table names + row counts
.lake info mylake              -- format version, current version, snapshots, commits, tables
.lake open mylake              -- replace the in-memory store with the latest
.lake open mylake 3            -- or with a specific published version
.lake attach mylake            -- attach read-only (see below)
.lake attach mylake 2 write    -- or writable, pinned to a version (see commits above)
.lake commit mylake            -- publish the writable attach's changes
.lake detach mylake [force]
.lake attached

From a program, the same operations live in the pink-lake crate:

use pink_lake::{Lake, save_store};
use pinkdb::PinkDb;

let mut db = PinkDb::new();
db.execute("CREATE TABLE t (a INTEGER); INSERT INTO t VALUES (1), (2);")?;

let version = save_store(&db, "mylake")?;  // creates the lake, publishes v2
let mut lake = Lake::open("mylake")?;      // v1 is the create-time empty catalog
lake.set_commit_message(Some("alice".into()), Some("two rows".into()));
let v3 = lake.write_from_store(&db)?;      // full snapshot, version 3

// Incremental: append rows as one new immutable data file (nothing else is
// rewritten) and/or record positional deletes.
let mut commit = pink_lake::Commit::new();
commit.append("main.t", std::sync::Arc::new(appended_rows));  // same schema
commit.delete_positions("main.t", "data/main.t/<uuid>.vortex", &[0]);
let report = lake.commit(&commit)?;

let tables = lake.tables()?;
let versions = lake.versions()?;
let records = lake.snapshots()?;           // per-version time/author/message/changes
let old = lake.load(Some(2))?;             // rebuild a specific version

.lake save, .lake open and .lake attach are refused inside a transaction, and .lake open refuses to detach a durable session. Every <dir> argument also accepts an s3://bucket/prefix URL when the build has the s3 feature.

Read-only attach

.lake attach <dir|s3://…> [version] attaches a lake for the session without loading any table into memory. No column data is decoded:

  • In a full (Vortex) build it reads the catalog, the manifest and each data file's footer, metadata and statistics — no column decode.
  • In a lean build it reads a CRC-32-protected per-column statistics block that every lean save publishes, so no data file is opened at all. A lake saved before that block existed refuses attach with a re-save message, never a guess.
  • Exact COUNT(*), COUNT(col), MIN and MAX answers come from the stored statistics under strict gates (exact null counts, exact min/max, no ambiguous ±0.0 stat; a multi-aggregate query is all-or-nothing). Anything unproven materializes the one table the query touches, decoding only the columns it references.
  • Once positional deletes exist on a table, per-column facts fall back — row counts and COUNT(*) stay exact, the rest materializes.
  • Attached tables are session-local; read-only attachments refuse every mutation. .lake save skips attached tables with a note.
  • Measured: a cold attach plus COUNT/MIN/MAX takes ~2.6 ms at 1M rows and ~2.3 ms at 10M rows in the lean build; the attach overhead (~0.1–0.2 ms) is constant in file size.

Writer semantics and conflicts

  • One live writer handle per lake (there is no file locking between lake writers; concurrent readers of published versions are fine). A handle that saves after another writer published a version fails with another writer published version N; reopen the lake before replacing the catalog — unless it retries: incremental commits rebase under the retry settings above.
  • Publishing the same version twice is impossible: the snapshot is create-only, so of two racing writers exactly one wins. catalog.json is always byte-identical to the snapshot of its version.
  • The CLI additionally tracks each lake's version baseline per session: .lake save [force] — force overrides the stale-baseline conflict check.
  • Full saves rewrite every table; plan for the disk/time cost of a snapshot, or commit incrementally. Schema changes, partitioning and compaction are in progress (lake-parity waves 65–68); data inlining (tiny commits kept in metadata) is queued too.

S3 / R2 object storage

With the s3 feature, any lake location can be an s3://bucket/prefix URL — AWS S3, Cloudflare R2, MinIO, or any S3-compatible endpoint. It is a small, blocking SigV4 client; there is no async runtime and no AWS SDK.

cargo build --release -p pinkdb-cli --features lake,s3

export AWS_ACCESS_KEY_ID=<r2-token-key-id>
export AWS_SECRET_ACCESS_KEY=<r2-token-secret>
export AWS_ENDPOINT_URL=https://<account>.r2.cloudflarestorage.com
export AWS_REGION=auto

./target/release/pinkdb
#   .lake save     s3://my-bucket/lakes/demo
#   .lake attach   s3://my-bucket/lakes/demo
#   .lake versions s3://my-bucket/lakes/demo
VariableMeaning
AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY credentials (required for the environment-based URL form)
AWS_SESSION_TOKEN optional temporary-credential token (used with the environment's credential pair)
AWS_ENDPOINT_URL (or …_S3) non-AWS endpoint, e.g. the R2 S3 API URL
AWS_REGION (or AWS_DEFAULT_REGION) SigV4 region (auto requires a custom endpoint)
AWS_S3_FORCE_PATH_STYLE force path-style addressing (the default with a custom endpoint; dotted bucket names need it)
PINKDB_S3_ALLOW_HTTP allow a plain http:// endpoint (local tests only — credentials travel unencrypted)
PINKDB_S3_ALLOW_DEGRADED accept the single-writer check-then-put fallback on endpoints that reject conditional writes (see below)
PINKDB_S3_RETRIES retries after a retryable failure (default 3; 0 disables)
  • Conflict detection is built on conditional writes. A snapshot is published with If-None-Match: * (a published version is never replaced) and catalog.json is replaced with If-Match: <etag>, evaluated atomically with the write on AWS S3 and R2 — so concurrent saves cannot fork the version chain.
  • Endpoints that reject conditional writes are refused by default. Set PINKDB_S3_ALLOW_DEGRADED=1 to accept a check-then-put fallback with a documented race window — it is single-writer only. Errors are specific: a missing catalog is not a pink-lake directory, a wrong version is has no snapshot version N, a lost race is a write conflict.
  • One PutObject per object: no multipart uploads, so a single table's data file must be ≤5 GiB (checked client-side). No bucket creation, no lifecycle rules, no lake-side GC — old versions stay, exactly like local. Lake data is plaintext (PINKDB_KEY does not encrypt it).
  • Requests have a 120 s whole-request timeout; retryable statuses (429/503, and idempotent-request transport errors) back off with jitter. A conditional PUT that failed ambiguously is never retried.
after a failed save

Reopen the lake and inspect with .lake versions before retrying. A failed save can leave unreferenced data files (harmless), a stray unpublished snapshot (the next save refuses rather than clobber it), or a published version whose response was lost. Never blindly re-run the save on the old handle.

Which build should I use?

  • Just a database file? Skip the lake — the default build's .pink + WAL is the whole story.
  • Versioned snapshots, local disk, lean binary? Use lake-lite: all the commands (incremental commits and time travel included), statistics-only attach, and a 2.69 MB binary.
  • Vortex data files and footer-based attach? Use the full lake build, at the cost of a 45.3 MB binary. The data-size gap is small: on the reference sales corpus the lean build's .pink files are only about 1.6–1.8% larger; the binary size, not the data size, is the trade-off.
  • Object storage? Add s3: lake-lite,s3 (4.70 MB) or lake,s3 (≈47.3 MB).
