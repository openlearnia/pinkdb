# pinkdb docs website

Product documentation for pinkdb: a fully static, zero-dependency site (no CDNs, no
third-party requests of any kind; type is vendored and self-hosted) generated by a
small Python 3 stdlib-only script, deployed to Cloudflare Workers static assets. One
page — **Extensions** — ships a small inline script that renders the extension
catalog fetched at runtime from the repository Worker
(`https://pinkdb-ext-repo.defaultcms.workers.dev/index.json`; the Worker sends CORS
`*` for it).

## Art direction — "soft data-zine"

The site reads like a warm-paper zine about data: paper `#F7F1E8`, warm ink
`#241F1C`, one desaturated pink accent `#C9557A` (plus ink blue `#2C4A66` for
links), warm-tinted greys only, a fixed paper-grain overlay, hard offset shadows
from a single top-left light source, dashed "cut lines", sticker badges, tape
strips, index-card code blocks, margin notes, sketchy inline SVG diagrams, and a
ticker strip on the landing and Extensions pages.

Type is self-hosted (see `src/assets/fonts/README.md` for provenance and the
subsetting commands):

| Face | Role | File | Bytes |
|---|---|---|---|
| Bricolage Grotesque (variable) | display / headings | `fonts/bricolage-grotesque.woff2` | 35,852 |
| Public Sans (variable) | body text | `fonts/public-sans.woff2` | 23,928 |
| Public Sans Italic (variable) | body emphasis | `fonts/public-sans-italic.woff2` | 25,596 |
| JetBrains Mono (variable) | code, tables, data | `fonts/jetbrains-mono.woff2` | 28,156 |

All four are SIL Open Font License 1.1; the licence texts sit next to them.
`font-display: swap`, tabular numerals on every data surface, and every
animation is behind a `prefers-reduced-motion` guard.

Docs pages render in a `.docs-shell` grid: a sticky sidebar with the grouped nav
(collapsible on narrow screens via a checkbox disclosure), the article, and —
when the page opts in and there is room (≥74rem) — a generated "on this page" TOC
in a sticky right rail. The top bar keeps the brand, the Extensions catalog link
and GitHub; the sidebar marks the active page with
`class="active" aria-current="page"`.

## Layout

```
├── tools/

├── src/

│   ├── assets/

│   │   └── fonts/           # vendored OFL woff2 files + licence texts + README

└── public/             # generated output (build.py writes this)
```

## Build

```sh
python3 build.py
```

This wipes and regenerates `public/`:

- `pages/index.html` → `public/index.html`
- `pages/404.html` → `public/404.html`
- `pages/extensions.html` → `public/extensions.html` (so the catalog is served at
  `/extensions`)
- `pages/extensions-guide.html` → `public/docs/extensions.html` (the usage guide)
- every other fragment → `public/docs/<name>.html`
- `src/assets/` → `public/assets/`

Fragments contain page content only. `src/layout.html` supplies the page shell and
uses these placeholders, filled by `build.py`:

| Placeholder | Filled with |
|---|---|
| `{{title}}`, `{{description}}` | per-page metadata (from `PAGES` in `build.py`) |
| `{{url}}` | the page's canonical URL on the live origin |
| `{{main}}` | the assembled main column (sidebar + fragment + optional TOC) |
| `{{root}}` | relative path to the site root (`""` or `"../"`) |
| `{{nav-<key>}}` | active-link attributes in the top bar, empty elsewhere |

The build fails if any `{{...}}` placeholder is left unexpanded, or if a page's
`nav` key or a `NAV` entry's output path does not match a fragment.

## Adding a page

1. Create the fragment in `src/pages/` (content only — an `<h1>`, sections, no
   `<html>` shell).
2. Add an entry to `PAGES` in `build.py`:
   ```python
   "my-page.html": {
       "out": "docs/my-page.html",
       "nav": "my-page",          # a key used by an item in NAV
       "toc": True,               # optional: generate an "on this page" TOC
       "title": "My page — pinkdb",
       "description": "One sentence for <meta name=\"description\"> and OpenGraph.",
   },
   ```
3. Add the item to the `NAV` structure in `build.py` (grouped sidebar order).
   That is all — the sidebar, active marking and relative links are generated.

`toc: True` rewrites the fragment's plain `<h2>` headings to add unique `id`s and
builds the sticky right rail from them (three or more headings required; headings
that already carry an `id` are left alone). Use `"layout": "home"` or
`"layout": "narrow"` to opt out of the sidebar shell.

## Preview locally

Use `wrangler dev` so the local preview matches production exactly (the site
links extensionless paths like `docs/sql`, which Workers' asset handling
resolves and a plain file server does not):

```sh
python3 build.py
wrangler dev          # then open the printed http://localhost:8787/
```

With a plain file server (`python3 -m http.server -d public`) only the
explicit `.html` paths (e.g. `docs/sql.html`) resolve, and the 404 page is
served plainly — useful for a quick look, not a faithful preview.

## Deploy to Cloudflare Workers

```sh
# from website/, with wrangler installed and authenticated
python3 build.py
wrangler deploy
# or just:
./deploy.sh
```

`wrangler.toml` serves the `public/` directory as static assets and uses
`not_found_handling = "404-page"`, so unknown paths return the generated
`404.html`.

Validate the deploy without publishing anything:

```sh
wrangler deploy --dry-run --outdir <scratch-dir>
```

## Content notes

- The pages are **product documentation**: what pinkdb is, how to use it, its APIs
  and guides, plus a product roadmap. Facts (feature lists, sizes, formats, flags)
  come from the repository README, the CLI's help text, headers and crate sources —
  reuse only numbers that exist in the repo, and keep them sparse and current.
- No internal process jargon: no wave numbers, no agent/evidence tables, no test
  counts. The per-change engineering log is linked once, from the roadmap page, to
  `ROADMAP.md` on GitHub.
- Content links to `github.com/openlearnia/pinkdb` are fine; do not add external
  stylesheets, scripts or image assets. Fonts live in `src/assets/fonts/`
  (self-hosted, OFL, licence texts committed) and are the only binary assets
  besides the generated favicon/OG images. The one deliberate exception to
  "no scripts" is `pages/extensions.html`, whose inline script fetches the
  extension catalog from the repository Worker (which sends CORS `*`) and renders
  it with the site's own CSS classes; keep that script inline too, and keep it the
  page's first `<script>` (the verifier lifts its pure section).
- Sketch diagrams are inline SVG (`<svg>` with `sk-*` classes defined in
  `style.css`) — no image files, and they scale/scroll instead of breaking
  the layout.
- The Extensions catalog page is checked by `ext-repo/worker/verify-ui.mjs`: keep
  its `#ext-intro` / `#catalog` ids, the `for="filter"` label, the `data-copy`
  affordances and the inline `<script>` (with its `fetch(INDEX_URL` call) intact,
  and keep exactly one `Extensions` link in the first `<nav>` of every page.

## Regenerating the raster assets

`src/assets/favicon.png` and `src/assets/og.png` are generated (and
committed) by a stdlib-only script with a tiny supersampled rasteriser:

```sh
python3 tools/make-assets.py
```

## Verifying the live site

After deploying (and after the repository Worker is deployed — the Extensions
page fetches it):

```sh
node verify-browser.mjs        # headless Chrome over the live docs + Worker
```

It renders `/extensions` in headless Chromium, exercises the filter, the
details hash route and the not-found state, checks the design system (fonts
load from the docs origin, the sidebar marks the active page on `/docs/sql`,
margin notes and the ticker render, readable text column, no third-party
requests, no horizontal overflow at 390px/1280px, reduced-motion handling),
loads the Worker `/` info page (palette, favicon, script-free, `/index.json`
from the page context with CORS `*`), and fails on any console error.
`ext-repo/worker/verify-ui.mjs` additionally checks the generated
`public/extensions.html` statically, asserts the vendored fonts + licences +
meta/OG/favicon on every page, and runs the lifted pure helpers against the
live catalog.
