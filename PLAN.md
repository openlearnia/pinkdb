# pinkdb — v1 Plan

A mini DuckDB: an embedded **analytical** SQL database in Rust — in-memory columnar
storage, vectorized execution, SQL with aggregates and joins, CSV import.
Ships as both a **library crate** (`pinkdb`) and a **CLI REPL** (`pinkdb-cli`).

## Decisions (locked with user, Oct 2026)

| Decision | Choice |
|---|---|
| Language | Rust (edition 2021, zero async, no unsafe) |
| Interface | Library + REPL (CLI is a thin consumer of the library) |
| v1 scope | In-memory storage + CSV import (no persistence, no UPDATE/DELETE) |
| Deps | `csv` (lib), `rustyline` (cli) only — hand-written SQL lexer/parser |

## Architecture

```
SQL text
  → Lexer + recursive-descent parser → AST
  → Binder (resolve tables/columns, assign types)
  → Logical plan (scan → filter → join → aggregate → project → sort → limit)
  → Optimizer (predicate pushdown, constant folding)
  → Vectorized executor (pull/Volcano; operators exchange DataChunks of ≤2048 rows)
  → In-memory columnar storage
```

### Core design decisions

1. **Vectors, not rows.** `Vector` = typed column chunk (`enum VectorData`:
   `Boolean(Vec<bool>)`, `Int32(Vec<i32>)`, `Int64(Vec<i64>)`, `Float64(Vec<f64>)`,
   `VarChar(Vec<String>)`) + a **validity bitmask** (`Vec<u64>`, bit set = valid),
   DuckDB-style. Every operator processes a whole `DataChunk` per call.
2. **Selection vectors.** `WHERE` produces a selection vector (no row copying);
   `Vector::gather` applies it downstream.
3. **Types for v1:** BOOLEAN, INTEGER (i32), BIGINT (i64), DOUBLE (f64), VARCHAR.
4. **Storage:** `DataTable` = per-column `Vec<Vector>` chunks of CHUNK_SIZE=2048;
   `PinkDb` catalog maps table names → tables. Single connection, single thread.
5. **CSV inference:** per column over all non-empty cells: i64-fits-i32 → INTEGER,
   i64 → BIGINT, f64 → DOUBLE, true/false (ci) → BOOLEAN, else VARCHAR.
   Empty cell → NULL.
6. **Executor:** pull-based operators — Scan, Filter, Project, HashAggregate,
   HashJoin (inner, equi), Sort, Limit. Expression evaluation vector-at-a-time.
7. **Optimizer (v1):** predicate pushdown + constant folding. (Pruning later.)

### SQL surface for v1

```sql
CREATE TABLE t (id BIGINT, name VARCHAR, price DOUBLE);
INSERT INTO t VALUES (...);
SELECT [DISTINCT] expr [AS alias], ...
FROM t [JOIN u ON t.x = u.y]     -- inner hash join
WHERE expr                        -- incl. IS [NOT] NULL, BETWEEN
GROUP BY ... HAVING ...
ORDER BY expr [ASC|DESC], ...     -- NULLS LAST; positional ORDER BY 2
LIMIT n;
```

- Aggregates: `COUNT(*)`, `COUNT(x)`, `SUM`, `AVG`, `MIN`, `MAX`
- Scalar functions: `abs`, `round`, `upper`, `lower`, `length`, `substr`
- Numeric coercion: INTEGER + DOUBLE → DOUBLE; int `/` int → DOUBLE (DuckDB rule)
- SQL three-valued logic: NULL fails WHERE; HAVING filters after aggregation

### CLI

- REPL prompt `pinkdb> `, rustyline line editing, multi-line until `;`.
- Dot-commands: `.help`, `.quit`/`.exit`, `.tables`, `.schema <t>`,
  `.import <file.csv> [table]`.
- Box-drawn result tables with a type row (DuckDB-style) + `Run Time (s): real X.XXX`.

## Lake benchmark note (Vortex vs DuckLake, Oct 2026)

`bench/lake_bench.py` (stdlib-only) compares pink-lake (Vortex) with DuckLake
(DuckDB v1.5.5 `ducklake` extension) on the same CSV and the same four
queries, both storing `lake.sales`: 1M rows — pink-lake ingest 0.243 s vs
0.125 s, stored 3.12 MB vs 13.26 MB, cold open 0.061 s (eager) vs ATTACH
≈3 ms (lazy), first-query cold wall 0.077 s vs 0.036 s, queries best-of-5
<1/10/5/3 ms (count/group-by/filter/order-by) vs 7/12/11/12 ms printed
(36–41 ms as fresh-process wall); 10M rows — 1.943 s vs 0.368 s ingest,
31.1 MB vs 97.1 MB stored, cold open 0.724 s vs 0.036 s, group-by 93 ms vs
37 ms, filter 48 ms vs 24 ms, order-by 30 ms vs 28 ms, `COUNT(*)` <1 ms vs
8 ms. So at 10M DuckLake wins ingest, cold start and three of four queries
while pink-lake keeps the compactness (≈3× smaller) and the in-session
`COUNT(*)` fast path. Caveat: architectures differ — pink-lake eagerly
loads Vortex into the in-memory engine at `.lake open`, DuckLake scans
Parquet lazily at query time; not an apples-to-apples product comparison.
Reproduce: `python3 bench/lake_bench.py --rows 1000000 --runs 5` (add
`--rows 10000000` for the larger run). Follow-up candidate for wave 40:
Vortex scan/decode speed at 10M (the engine's in-memory scans lose to
Parquet for filter/group-by/order-by there).

## Real-S3 integration harness (Oct 2026, wave 36 follow-up)

`crates/pink-lake/tests/s3_docker.sh` (new; bash + python3 + Docker, not
wired into `cargo test`) is the independent, real-socket counterpart of the
hermetic `mock_s3.rs` suite. It manages its own `adobe/s3mock:latest`
container (`pinkdb-s3mock-itest`, initial bucket `pinklake`; auto-picks a free
host port when 9090 is busy; removed on exit, while `KEEP=1` leaves it for the
next run to reuse), waits for an unsigned PUT/GET readiness probe, probes the
server's conditional-write behaviour (sequential semantics + a concurrency
**atomicity** probe), then drives the release CLI
(`cargo build --release -p pinkdb-cli --features lake,s3`): a typed-CSV
round-trip (NULL/`-0.0`/BIGINT/DATE/TIMESTAMP/multibyte) with a fresh-process
`.lake open` exact-value compare and an unsigned REST object listing; a
3-writer × 3-round race plus a deterministic slow-vs-quick same-version
conflict with a settle save afterwards (win-xor-conflict per attempt, gapless
catalog chain, exactly one winner for the controlled version,
`catalog.json` == `snapshots/<v>.json` bytes via curl + `cmp`); and the
snapshot-exists refusal (planted stray snapshot, then a clean save after
removing it). First full runs on this machine: 493/493 default `cargo test`
still green (36 binaries, 1 ignored); harness runs ~5–8 s each, four clean
runs incl. `KEEP=1` reuse and a default-port-9090 run, container removed each
time.

**Finding (the reason the harness probes first):** s3mock evaluates a
conditional PutObject's precondition *outside* its per-object lock
(`ObjectController.putObject` → `verifyObjectMatching` → `putObject`), so two
truly concurrent conditional PUTs can both be answered 200 — its documented
conditional semantics are sequential-only, unlike AWS S3 / R2, whose
evaluation is atomic with the write commit (what the single-writer contract
relies on). Measured: 60/60 raw curl trials (fresh key, two parallel
`If-None-Match: *` PUTs → both 200) and 3–4/4 in the harness's per-run probe;
in the 3×3 race this shows up as 0–3 duplicate claims per run depending on
writer overlap. The harness therefore reports duplicate race publications as
the measured server limitation (probe evidence + source reference in
`s3_docker_notes.md`), enforces the one-winner assertion on servers that can
uphold it (the in-repo atomic mock pins the client logic today;
`PINKDB_S3_LIVE=1` is the real-service check), and asserts the deterministic
same-version conflict + final-version `catalog.json` == `snapshots/<v>.json`
bytes on any server. MinIO images are not anonymously pullable right now
(Docker Hub: `pull access denied … may require 'docker login'`; quay.io:
`401 UNAUTHORIZED`), so s3mock is the documented recipe.

**Wave 41 follow-up — `SERVER=s3mock|seaweedfs|rustfs`:** the harness now
runs against three real servers and derives its enforcement policy from
per-endpoint capability probes (unsigned PUT → 403? sequential conditionals?
bounded two-writer `If-None-Match: *`/`If-Match` races, 4+4 trials). s3mock
stays the lenient default (no SigV4 verification, check-then-act conditionals:
duplicates reported). `SERVER=seaweedfs` and `SERVER=rustfs` are **strict**: on
those the one-winner-per-version race assertion, the raced
`catalog.json == snapshots/<v>.json` byte check, and the unsigned-must-403
signature check are hard failures. Measured on this machine (2026-10-14):
both strict servers reject unsigned and wrong-key PUTs with 403, evaluate
conditionals atomically (0/4 both-200 trials in the harness probe; 0/20 in the
raw two-writer race), and both full runs pass under the strict policy
(typed-CSV round-trip; 3×3 race → one winner per version, gapless 1..6 with the
settle save; slow-vs-quick conflict; planted-stray refusal;
`catalog.json == snapshots/{2,3,5,6}.json` via `cmp`). Two measured surprises:
(1) **SeaweedFS's default `server -s3` config does not verify SigV4 at all**
(unsigned and even garbage-signed PUTs → 200), so `SERVER=seaweedfs` probes a
pre-existing `pk-seaweed`, reports it as anonymous, leaves it untouched, and
starts its own identity-configured `pinkdb-seaweed-itest` (`-s3.config`;
unsigned → 403, any configured key pair accepted) — a `pk-seaweed` that does
enforce SigV4 is reused; (2) the deterministic slow-vs-quick pair needed a
wider conflict window: a local RustFS saves 400k rows in ~0.085 s, so the
quick writer read the catalog after the slow publish (two clean saves of
*different* versions, no race) — `SLOWROWS` now defaults to 4 000 000 (≈1.5 s
of encoding on RustFS) with a 0.3 s head start, and a missed window is
reported as a harness timing miss, not a client bug. Container lifecycle:
`KEEP=1` unchanged; a container this run started is removed on exit, a reused
one (`pk-rustfs`, a SigV4-verifying `pk-seaweed`) is left running, and the
script never touches another server's container. The CLI never creates
buckets; the harness creates `BUCKET` up front (signed on the strict servers),
tolerating 409/200-already-exists. `cargo test -q` unchanged: 494 passed /
0 failed / 1 ignored; the s3mock regression run stays green.

Packaging principles:
- New capabilities ship as separate workspace crates and/or opt-in cargo features; the default
  `cargo build` stays lean (~2 MB) and links no crypto/TLS/format code.
- Every wave reports per-artifact release binary size; gates grow a build matrix (default,
  each feature, each crate) plus a wasm check for the core (`pinkdb` and `pinkdb-parquet`
  must stay wasm32-compatible; the server is target-gated out of wasm builds).
- No hand-rolled crypto; audited RustCrypto crates only.
- Zero-unsafe holds for the core; the C ABI crate is the first, contained exception.
- Compile-time engine components ship as separate crates/features (waves 22-28) — distinct from
  waves 29+ loadable extensions, which use a versioned C ABI and a runtime loader (the loader
  crate is the second contained-`unsafe` location after `pinkdb-ffi`).

## Known sharp edges (planned handling)

- GROUP BY keys incl. strings: encode keys as `Vec<u8>` → `HashMap<Vec<u8>, AggState>`.
- NULL ordering: NULLS LAST in sorts; NULL keys group together.
- Type coercion matrix across arithmetic/comparison operators.
- INTEGER overflow in SUM: accumulate integers in i64; document overflow policy.
- Extensions are native-only by construction: the `pinkdb-ext-loader` dependency of
  `crates/pinkdb` is target-gated under `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`,
  the dynamic-function registry/binder/executor paths are cfg'd out on wasm32, and
  `PinkDb::load_extension` is a stub returning "extensions are not supported on wasm
  targets" there, so `cargo build -p pinkdb --target wasm32-unknown-unknown` works
  (wave 29B). Extension functions are also strictly typed in ABI v1: no implicit casts,
  callers write `CAST(...)` (implicit widening is wave-30+ SDK/ABI work).

Post-v1 roadmap: see "Roadmap (post-wave 21)" above.
